## 2.2 星云 IoT Core 的整体架构

上一节已经确定了星云 IoT Core 的定位。接下来先不急着讨论 MQTT、数据库或微服务，而是把整个平台摊开来看。

从最粗的层次上说，一个 IoT 平台一直在连接两个世界。

一边是真实世界中的设备。灯、空调、门锁、传感器、摄像头和网关不断产生状态和事件，也等待来自系统的控制、配置和升级。

另一边是使用这些设备能力的软件。消费者 App、运营后台、行业应用、第三方开发者和其他业务系统，并不希望分别理解每种设备的通信细节，而是希望通过相对统一的方式知道设备是谁、现在怎样、能够做什么，以及自己有没有权限操作。

星云 IoT Core 就位于两者之间。

它一方面要面对复杂而不稳定的设备世界，另一方面又要向应用提供相对稳定的平台能力。可以先用一张简化的图理解它的位置。

```text
┌──────────────────────────────────────────────┐
│                 上层产品与系统                │
│                                              │
│  消费者 App   运营后台   行业应用   第三方系统 │
└──────────────────────┬───────────────────────┘
                       │ API / Event / SDK
                       ▼
┌──────────────────────────────────────────────┐
│                星云 IoT Core                  │
│                                              │
│  产品与设备        用户、组织与权限           │
│  设备模型          状态与设备数据             │
│  接入与连接        自动化与规则               │
│  消息与控制        OTA 与生命周期             │
│  网关与拓扑        运维、诊断与开放能力       │
└──────────────────────┬───────────────────────┘
                       │
                       ▼
┌──────────────────────────────────────────────┐
│                 设备与边缘世界                │
│                                              │
│  直连设备   网关   子设备   边缘节点   现场系统 │
└──────────────────────────────────────────────┘
```

这张图并不是最终的软件架构，更不是微服务列表。它首先是一张**责任地图**。

图中的每一块都在回答一个问题：星云需要长期理解和管理哪些事情，而这些事情之间怎样协作。

### 2.2.1 最下面，是复杂的设备与边缘世界

星云最先面对的是设备。

最简单的情况是一台设备直接连接平台。例如，一只 Wi-Fi 插座通过互联网连接云端，完成认证以后持续上报状态，并接收远程控制。

但现实不会永远这么简单。

一只 Zigbee 温度传感器可能自己无法连接云端，需要先连接网关；一栋楼里的 Modbus 设备可能通过现场边缘服务器统一接入；某些设备平时由本地网络控制，只在必要时与云端同步状态。

因此，在整体架构中，设备侧不能被简单画成一个“Device”。

它至少包含几种不同角色：可以直接连接平台的设备、承担代理能力的网关、隐藏在网关之后的子设备，以及拥有一定计算和运行能力的边缘节点。

这些对象的连接方式可能完全不同，但进入星云以后，都应该逐渐转换为平台能够理解的统一对象。

例如，一只温度传感器究竟通过 Wi-Fi 直连，还是通过 Zigbee 网关接入，不应该改变上层应用读取温度的基本方式。连接方式属于设备接入问题，而“这是一只温度传感器，它当前报告 26.3℃”属于平台需要向上层稳定表达的设备语义。

所以，星云架构中的第一项重要工作就是：

**把复杂的设备连接方式，逐渐转换成平台内部稳定的设备身份和能力表达。**

### 2.2.2 接入和消息是设备进入平台的入口

设备能够通过网络到达服务器，并不意味着它已经真正进入 IoT Core。

平台首先需要知道连接来自谁。

设备可能使用证书、密钥或其他凭证证明身份，平台则需要确认它是否合法、属于哪个产品，以及是否允许建立连接。

连接建立以后，设备会不断产生消息。

其中可能有温度、电量、开关状态，也可能是告警、日志、控制回复和升级进度。不同设备使用的协议和消息格式并不一定相同，因此平台不能把“收到一段网络数据”直接等同于“知道设备发生了什么”。

接入层和消息处理负责完成这种转换。

它们处理网络连接、认证、会话、协议和消息路由，再把底层通信转换成更稳定的平台事件。例如：

> 设备 `A123` 报告属性 `temperature = 26.3`

到了这一步，后面的设备管理、状态服务和自动化模块不应该再关心这条数据最初来自 MQTT、HTTP，还是某个边缘网关。

这种分离非常重要。

因为协议会变化，网络会变化，接入方式也会变化，而设备身份和平台语义应该尽量保持稳定。

### 2.2.3 产品、设备和模型构成平台理解设备的基础

仅仅知道消息来自哪台设备还不够。

平台还需要知道：

26.3 到底表示什么？

它的单位是什么？

这台设备还能提供哪些能力？

某个控制参数是否合法？

这些问题需要依靠产品和设备模型来回答。

在星云中，产品定义描述一类设备共享的约定，设备实例则表示现实中的某一台具体设备。设备模型进一步描述这类设备能够报告哪些状态、产生哪些事件，以及接受哪些操作。

因此，产品、设备和模型构成了 Core 理解设备世界的基础。

没有这一层，平台看到的只是大量主题、字段和 JSON；有了这一层，系统才能知道某个字段代表温度，某个操作代表开灯，某个事件代表烟雾告警。

这一层也会成为很多其他能力的依据。

App 生成控制界面需要知道设备能做什么；规则引擎需要知道哪些状态可以参与判断；控制服务需要校验参数；设备数据服务也需要知道收到的数据怎样解释。

换句话说，**模型让平台从“传递消息”进一步走向“理解设备”。**

具体怎样描述设备能力，是后面的重点内容。现在只需要先把它放到整体架构中的正确位置。

### 2.2.4 状态、控制和自动化让设备真正参与业务

设备接入平台以后，最常见的两个方向分别是上报和控制。

设备不断把现实世界发生的事情告诉平台。例如当前温度、开关状态、电池电量、门锁是否打开。这些信息进入星云以后，一部分会形成设备当前状态，一部分会成为历史数据或事件，再提供给 App、运营系统和其他业务使用。

另一个方向则相反。

用户在 App 中点击“开灯”，行业系统调整空调温度，或者规则引擎自动关闭一台设备，都会产生控制请求。平台需要判断谁正在操作、是否有权限、设备当前怎样连接，再把命令送到正确的设备，并继续处理后续结果。

于是，状态和控制形成了 IoT Core 中最基本的一组双向关系：

**设备告诉平台发生了什么，平台又通过设备影响现实世界。**

自动化则建立在这两种能力之上。

例如，当人体传感器报告有人进入房间时，规则可以自动打开灯；温度超过某个阈值时，可以产生告警或调整空调。

因此，自动化并不是一套完全独立的能力。它实际上是在使用已有的设备状态、事件和控制能力，把原本需要人手工完成的动作连接起来。

### 2.2.5 用户、组织和权限决定谁能够使用这些能力

一旦平台能够远程控制现实设备，权限就不再是附属功能。

同一台设备可能被不同角色访问。消费者可以控制自己家里的灯，家庭成员可能只有部分权限；学校的普通教师可以查看教室环境，但只有后勤人员能够修改设备配置；第三方系统可能只允许读取某类设备数据，却不能执行控制。

因此，星云还需要理解设备之外的另一组关系：

谁正在访问平台，他属于哪个租户或组织，能够访问哪些资源，又允许进行什么操作。

这些能力并不只服务登录页面。

它们会贯穿设备查询、控制、配置、OTA、数据访问和开放 API。

因此，在整体架构中，用户、组织和权限更像一项横向能力。设备管理会使用它，控制服务会使用它，开放平台也会使用它。

后面讨论核心对象时，我们还会进一步区分用户、账号、组织、空间和应用。此时先记住一点即可：

**平台不仅要知道设备是谁，也必须知道正在使用设备能力的是谁。**

### 2.2.6 OTA、运维和生命周期负责让设备长期运行

如果只画一条“设备连接—上报—控制”的链路，很容易把 IoT 平台理解成一个实时消息系统。

但设备真正交付以后，平台要面对的是多年运行。

固件会升级，配置会变化，设备可能长期离线，也可能出现批量故障。售后人员需要查询日志，运营人员需要知道版本分布，一次升级失败以后还需要知道哪些设备受到影响。

因此，OTA、设备配置、日志、告警、诊断、批量任务和生命周期管理也是 Core 的重要部分。

它们不一定出现在每一次实时控制链路中，却决定了设备能不能在真实世界中长期维护。

一套能够连接十万台设备的平台，并不一定就是一套能够运营十万台设备的平台。

前者关心连接能不能建立、消息能不能送达；后者还需要知道设备现在运行得怎么样、发生问题以后能不能定位、版本能不能安全升级，以及设备最终怎样退出系统。

这也是星云为什么不仅是一个连接平台。

### 2.2.7 Core 上面，是不同形态的产品和应用

星云 IoT Core 最终不会直接面对大多数终端用户。

普通消费者使用的可能是品牌 App，企业客户面对的是智慧楼宇或智慧学校系统，设备运营人员使用的是后台控制台，合作伙伴则可能直接调用 API。

这些产品看到的是同一个 Core 的不同侧面。

消费者 App 关心自己的设备和空间；

运营后台关心设备搜索、故障、OTA 和批量管理；

行业系统关心组织、空间和业务场景；

第三方开发者则关心 API、事件订阅和授权。

因此，Core 的一个重要目标就是避免让这些上层产品直接依赖底层设备协议和内部实现。

App 不应该因为设备从 MQTT 换成另一种通信方式就重新实现业务逻辑；学校系统也不应该为了读取某个传感器的数据去理解设备原始报文。

Core 位于中间，把底层设备世界的差异吸收下来，再向上提供相对稳定的能力。

这也是平台最重要的价值之一：

**下层可以复杂，上层可以多样，但中间需要有一套长期稳定的共同语言。**

### 2.2.8 Core 周围还有很多重要能力，但不必都放进核心

这张整体架构还需要留出一些边界。

例如，摄像头可以作为设备进入星云，但实时视频、转码和录像可以由独立媒体系统处理；企业用户可以通过星云的权限访问设备，但员工身份仍可能来自企业自己的 SSO；设备数据可以进入星云，也可以进一步流向数据仓库和分析平台。

Device SDK、App SDK、OEM App 和运营后台同样可以属于整个星云产品体系，却是围绕 Core 构建的产品，而不是 Core 内部必须承担的全部责任。

因此，更完整的关系可以理解为：

```text
                  ┌─────────────────────┐
                  │   行业与业务系统     │
                  │ App / SaaS / 后台   │
                  └──────────┬──────────┘
                             │
           ┌─────────────────▼─────────────────┐
           │            星云 IoT Core          │
           │                                   │
           │  设备、模型、连接、状态、控制     │
           │  权限、生命周期、数据、运维、开放 │
           └─────────────────┬─────────────────┘
                             │
                  ┌──────────▼──────────┐
                  │ 设备 / 网关 / 边缘   │
                  └─────────────────────┘

         ↔ IAM / 视频 / 数据平台 / ITSM 等专业系统

         Device SDK / App SDK / 开发工具等围绕 Core 提供
```
