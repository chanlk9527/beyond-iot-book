# 1.8 从 IoT 世界地图走向平台：共同问题与基本概念

[返回第 1 章：IoT 世界地图](../01-iot-world.md)

晴川的灯进入酒店以后，设备能力可以沿用，安装、入住和维护关系却发生了变化。平台需要在这些变化之间保持一套清楚的记录：这是谁的设备，安装在哪里，谁可以使用，最近观察到了什么，以及控制请求进行到了哪一步。

本节把这些问题所涉及的基本概念放到一起。这里先确定词语指向的对象与边界，具体的数据结构和处理规则由后续章节展开。

<span id="平台把重复出现的问题变成共同能力"></span>

## 1.8.1 平台把重复出现的问题变成共同能力

灯、摄像头和传感器的业务功能不同，却都可能需要身份、接入、状态、授权和维护能力。平台的任务是组织其中可以复用的部分，并为产品差异留下明确接口。

共同能力并不意味着所有产品都采用相同流程。酒店可以在施工时批量安装，家庭用户可以自行添加设备；二者都需要确认设备身份和使用关系，却不必经过相同的页面和步骤。平台需要统一的是身份、关系和授权的含义，应用则按交付方式组织流程。

[第二章](../02-nebula-iot-platform.md)将据此界定星云 IoT Core 的职责，以及它与设备、应用和边缘节点怎样协作。

<span id="账号和用户不是完全一回事"></span>

## 1.8.2 账号和用户不是完全一回事

账号是登录与身份认证所管理的记录及其关联信息；用户则是参与业务关系的人所对应的主体。一个人可以使用手机号或企业统一身份登录，登录方式变化，不应自动改变他在酒店工程团队中的角色。

因此，确认“谁登录了”和判断“他可以管理哪些设备”是相邻但不同的工作。前者提供可信身份，后者还要结合成员关系、角色和当前授权条件。不能因为登录成功，就允许访问平台上的所有设备。

<span id="家庭、空间和组织描述的是不同关系"></span>
<span id="家庭-空间和组织描述的是不同关系"></span>

## 1.8.3 家庭、空间和组织描述的是不同关系

家庭和组织描述共同管理或参与业务的范围，空间描述设备的安装或作用位置。一盏灯可以由酒店管理，安装在 302 房间；工程人员因组织角色获得检修权限，住客则因有效入住关系获得临时使用权限。

房间里有人，并不自动证明他拥有控制权限；用户退出一个组织，也不表示设备离开了原来的房间。把管理关系、位置和授权分开，才能解释这些不同的变化。平台内部可以按场景建立它们之间的关联，但不应把它们当成同一个对象。

<span id="租户是平台资源隔离的一种边界"></span>

## 1.8.4 租户是平台资源隔离的一种边界

租户用于划定平台资源和数据的隔离、管理范围。如果一套 SaaS 平台同时服务晴川和另一家照明企业，可以分别为它们建立租户，限定各自能够访问的资源。

租户与组织不必一一对应。晴川一个租户内可以服务多家酒店，各酒店继续维护自己的组织与空间；另一种交付安排也可以为不同客户分别建立租户。应先确定隔离与管理需求，再决定映射方式，不能仅凭现实中存在一家企业，就推导出必须新增一个租户。

本书在第二章说明平台隔离边界，组织、空间和细粒度授权由后续专题展开。第一章只要求读者分清：租户划定平台边界，组织描述业务关系，两者需要明确关联。

<span id="产品和设备回答的是-一类-和-一个"></span>

## 1.8.5 产品和设备回答的是“一类”和“一个”

前面讨论的商业产品，是用户买到的商品与服务。进入星云设计后，**平台产品**是组织一类设备的技术定义、接入和管理约定的对象；对这些范围和约定的描述称为产品定义。它不必与销售包装或型号严格一一对应。

**设备模型**描述属性、事件和操作等能力。平台产品可以关联相应的模型，具体设备则需要记录自己支持的能力及版本。共享一个平台产品，不代表所有实例都在运行相同固件，也不证明所有可选能力均已实现。

**设备实例**是被单独识别和管理的对象。改变 302 房间一盏灯的亮度，只影响这台设备；修改能力定义，则会影响平台怎样解释相关设备的数据和操作。两类变化的范围不同，不能由同一条记录承担。

[第三章](../../part-02-iot-core/03-device-connect.md)主讲设备身份与接入，[第四章](../../part-02-iot-core/04-device-model.md)主讲设备模型及演进。模型怎样关联、版本怎样生效，将在那里建立规则。

<span id="在线、可用和可控也不是同一件事"></span>
<span id="在线-可用和可控也不是同一件事"></span>

## 1.8.6 在线、可用和可控也不是同一件事

在线是根据会话、心跳或最近通信作出的连接判断；可用是某项功能在当前条件下能够提供服务；可控是特定主体具备请求设备执行某项操作的权限与运行条件。

摄像头可能保持连接，但因成像模块故障无法提供视频。灯可以正常照明，但当前住客没有权限控制其他房间。设备也可能无法连接云端，却仍按本地规则工作。这些判断需要分别表达，并说明针对哪项功能、哪位主体和哪条路径。

平台掌握的报告状态还带有观察时间。昨晚报告“灯已关闭”，不能直接证明此刻的物理状态；界面与业务判断都需要考虑信息是否仍然有效。第四章会进一步区分报告状态与平台推断，第五章再把这些区别用于交互结果判断。

<span id="数据采集和设备控制是两个方向"></span>

## 1.8.7 数据采集和设备控制是两个方向

数据采集和状态上报提供设备的观察；设备控制表达系统要求设备执行的动作。操作是模型声明的能力，命令则是一次具体控制请求的载体。灯支持“调节亮度”，与某次“把亮度设为指定值”的命令，是能力与请求两个层次。

平台受理、消息送达、设备执行和随后观察到的状态，也分别提供不同证据。不能把“已发送”显示成“已执行”，也不能仅凭一个恰好符合目标的值，就断定某条命令完成。[第五章](../../part-02-iot-core/05-message-state-control.md)将说明消息关联、命令结果与状态同步的规则。

<span id="把这些概念放在一起"></span>

## 1.8.8 把这些概念放在一起

沿着酒店照明这个案例，进入平台设计前需要形成以下共同问题。

表 1-8 从业务关系到平台问题。

| 现场变化 | 需要区分的对象或事实 | 平台设计要回答的问题 |
| --- | --- | --- |
| 工程人员换了登录方式 | 账号与用户 | 身份变化是否影响原有业务关系？ |
| 住客退房，灯留在房间 | 用户、空间与授权 | 哪项权限应结束，哪些记录应保留？ |
| 平台服务多家企业 | 租户与组织 | 隔离在哪一层成立，组织怎样映射？ |
| 同型号设备分批升级 | 平台产品、模型与设备实例 | 怎样知道具体设备支持什么能力？ |
| 灯断网后恢复连接 | 身份、绑定与连接状态 | 哪些关系保持，哪些观察需要更新？ |
| 用户点击调光 | 操作、命令与报告状态 | 凭什么确认这次请求的进展与结果？ |

第一章交付的是这张责任与关系地图：参与者怎样分工，产品承诺怎样产生平台需求，技术组合在哪些边界提供能力，以及设备长期变化时需要留下什么记录。下一章转向星云的整体设计，把这些问题落实为平台范围、组件职责和协作路径。
