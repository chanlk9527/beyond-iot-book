# 1.8 从 IoT 世界地图走向平台：共同问题与基本概念

[返回第 1 章：IoT 世界地图](../01-iot-world.md)

走到这里，我们已经从不同角度看过一件 IoT 产品。

设备负责感知和执行，连接负责传递信息，应用把这些能力变成具体功能；在产业中，又有芯片、模组、制造商、品牌、平台供应商、渠道、集成商和运营者共同参与。

如果一家企业只有一种产品、几百台设备，很多问题都可以直接写进产品后台。

但随着设备从几百台增加到几十万台，产品从一种增加到几十种，一些问题会不断重复出现：

每台设备都需要被识别；

每种设备都要说明自己能做什么；

设备会持续产生状态、事件和数据；

应用需要向设备发送控制；

用户和设备之间存在不同的关系和权限；

设备还会经历配网、安装、转移、升级、故障和退役。

如果每个产品团队都分别解决这些问题，很快就会出现多套设备身份、多套权限体系、多种数据格式和彼此独立的后台系统。

于是，一个更重要的问题出现了：

**哪些能力属于具体产品，哪些能力其实是许多 IoT 产品都会重复需要的？**

后者，就是 IoT 平台需要解决的主要问题。

## 平台把重复出现的问题变成共同能力

IoT 平台并不是简单地在设备和 App 之间增加一层软件。

它更重要的作用，是把不同产品反复遇到的问题组织成共同能力。

例如，一款灯和一台摄像头的具体功能完全不同，但它们都可能需要：

识别设备是谁；

知道设备属于哪个用户或项目；

保存设备当前状态；

接收设备产生的数据；

向设备发送控制；

管理升级和生命周期；

限制哪些人可以进行哪些操作。

这些共同问题一旦被平台统一处理，新产品就不必从零重新建设一套后台。

因此，平台真正需要管理的，不只是一批设备，还包括设备与产品、用户、空间和业务之间的关系。

这也是为什么进入平台设计以后，一些看起来相似的概念必须开始被区分。

## 账号和用户不是完全一回事

用户使用 App 时通常先登录账号，因此日常交流中经常把“账号”和“用户”混在一起。

但从平台角度看，两者关注的问题不同。

**账号**主要解决“怎样登录并证明你是谁”。

它可能对应手机号、邮箱、第三方登录身份或企业统一身份系统。

**用户**则是系统中的业务主体。

平台关心的是这个人能够进入哪些家庭或组织、可以看到哪些设备、拥有什么权限。

很多简单系统里，一个账号对应一个用户，看起来没有区别。

但进入企业系统以后，一个人可能拥有多种登录方式；一个账号体系也可能同时服务多个业务。

因此，后文会把“账号”更多用于登录和身份认证，把“用户”用于实际参与业务关系的人。

## 家庭、空间和组织描述的是不同关系

设备通常不会孤立存在。

家庭里的灯属于某个家庭，又安装在客厅或卧室；

公司的传感器属于某个企业，并安装在某栋楼、某个楼层或某间机房。

这些关系可以粗略分成两类。

**家庭和组织回答“谁在共同管理这些设备”。**

家庭可以包含成员、访客和一组设备；

组织可以是企业、酒店、学校或其他业务主体，也可能进一步包含部门和项目。

**空间回答“设备在哪里”。**

家庭里的客厅、卧室，办公楼里的楼层、会议室，工厂里的车间和区域，都属于空间关系。

所以，一盏灯可以同时具有这样的关系：

属于“张先生的家庭”，安装在“客厅”。

前者是管理和成员关系，后者是空间关系。

这两个概念可以组合使用，但不应该因为“家庭里包含房间”，就把家庭和房间当成同一种对象。

## 租户是平台资源隔离的一种边界

到了面向多家企业提供服务的平台，还会经常出现“租户”这个词。

租户通常表示一组需要彼此隔离的平台资源和数据。

例如，同一个 SaaS IoT 平台同时服务晴川和另一家照明企业，那么两家公司可能分别属于两个租户。

它们可以使用同一套平台软件，但原则上不能看到彼此的设备、用户和业务数据。

因此，**租户首先是平台层面的隔离和管理边界，不等于现实中的企业组织结构。**

有时一个企业对应一个租户；

有时一家大型企业拥有多个租户；

有些只服务单一品牌的平台甚至不需要显式暴露租户概念。

是否需要租户，要看平台服务谁，而不是因为“IoT 平台都应该有租户”。

## 产品和设备回答的是“一类”和“一个”

这个区别会贯穿后面的平台设计。

假设晴川生产了十万盏同型号智能灯。

它们共享相同的硬件和能力定义，比如都支持开关和 0—100 的亮度调节。

平台可以用一份共同的**产品定义**来描述这类设备。

但用户客厅里的那一盏灯，则需要有自己的身份、状态、安装位置和运行记录。

这就是一个具体的**设备**或设备实例。

所以可以简单理解为：

**产品定义描述“一类设备是什么”，设备描述“现实中具体是哪一台”。**

改变某一盏灯的亮度，只影响这个设备；

修改产品定义，则是在改变平台怎样理解这一类设备。

这里的“产品定义”也不要和品牌销售给消费者的商业产品混为一谈。前者是平台里的设备分类和能力约定，后者是客户实际购买到的一整套商品和服务。

## 在线、可用和可控也不是同一件事

这是 IoT 系统中非常容易混淆的一组概念。

平台显示一台设备**在线**，通常只能说明：

最近还能通过某种连接与它交换信息。

但在线不一定意味着设备真的**可用**。

例如，一台摄像头仍然保持网络连接，但镜头模块已经故障，它可能在线，却无法正常提供视频。

可用也不一定意味着当前用户**可控**。

设备可能运行正常，但用户没有权限；

也可能正在升级、处于保护状态，暂时拒绝某些操作。

因此可以粗略理解为：

**在线**关注通信关系是否存在；

**可用**关注设备或功能是否处于能够工作的状态；

**可控**关注当前主体是否能够对它执行某种操作。

三者之间有关联，却不能用一个布尔值全部代替。

一台设备完全可能出现：

在线，但不可用；

可用，但当前用户不可控；

暂时离线，但本地自动化仍然正常工作。

后面设计设备状态时，我们还会进一步处理这些区别。

## 数据采集和设备控制是两个方向

IoT 系统还有两个最基本的方向。

设备把温度、位置、开关状态等信息发送给系统，这是**数据采集或状态上报**。

用户、规则或业务系统要求设备开灯、调温或执行其他动作，则属于**设备控制**。

表面上，它们都只是网络里的消息，但业务含义不同。

数据采集关注：

**设备观察到了什么。**

设备控制关注：

**系统希望设备做什么。**

而控制请求发出去以后，又会产生新的问题：

设备有没有收到？

有没有接受？

有没有完成？

完成以后现实状态有没有变化？

这些问题会在后面的消息、状态和控制章节继续展开。

## 把这些概念放在一起

到这里，可以先建立一组后文会反复使用的基本词汇。

| 概念 | 主要回答的问题 |
| --- | --- |
| 账号 | 怎样登录并证明身份 |
| 用户 | 谁在使用系统并参与业务关系 |
| 家庭 / 组织 | 哪些人和设备属于同一个管理范围 |
| 空间 | 设备安装或作用在哪里 |
| 租户 | 哪些平台资源和数据需要彼此隔离 |
| 产品定义 | 一类设备共有怎样的能力和约定 |
| 设备 | 现实中具体是哪一个可管理实例 |
| 在线 | 当前是否还能进行通信 |
| 可用 | 当前功能是否能够正常工作 |
| 可控 | 当前主体是否有条件执行某种操作 |
| 数据采集 | 设备观察到了什么 |
| 设备控制 | 系统希望设备做什么 |

这张表并不是完整的 IoT 词典。

真正进入具体平台以后，还会遇到设备模型、属性、事件、命令、规则、权限、凭证、固件等更多概念。

但现在最重要的，是先建立一种习惯：

**不要因为两个词经常一起出现，就把它们当成同一件事。**

IoT 平台面对的复杂性，很大一部分就来自这些对象和关系同时存在，而且还会不断变化。

设备会换主人；

用户会退出家庭；

设备会被移动到另一个房间；

产品会增加新的能力；

企业会增加新的组织；

一台原本在线的设备也可能在下一分钟失去连接。

平台要做的，就是在这些变化发生以后，仍然让身份、关系、状态、权限和操作保持一致。

这也是接下来平台设计真正要开始处理的问题。

第一章到这里，完成的是外部世界的地图：

我们知道有哪些设备、连接、产品、企业和参与者，也知道它们为什么最终会产生一批反复出现的共同问题。

从下一章开始，我们把视线转到平台内部，看看这些对象和关系应该怎样被表示，又需要哪些基础能力才能长期管理起来。
