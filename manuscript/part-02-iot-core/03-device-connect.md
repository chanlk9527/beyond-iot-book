# 第 3 章：设备身份、注册与接入

## 引言

第二章已经给出了星云 IoT Core 的整体蓝图。我们知道，平台一端连接真实设备，另一端服务 App、行业应用和其他系统；设备上报、远程控制、状态管理、权限和生命周期等能力，也都建立在这套共同底座之上。

从这一章开始，我们不再停留在总体架构，而是沿着设备进入平台的路径，逐步展开其中的细节。

设备接入通常很容易让人首先想到 MQTT、HTTP、长连接、心跳和 Topic。它们当然都很重要，但在真正建立通信之前，还有一个更基础的问题：

**平台怎么知道连接过来的到底是谁？**

一台设备能够访问服务器，并不意味着它已经成为平台中的合法设备。知道一个设备编号，也不意味着平台能够相信连接者确实拥有这个身份。设备第一次进入系统时，还需要完成注册、激活、凭证建立和身份认证；以后重新连接时，平台也需要再次确认它是谁，并把这次连接重新关联到那台长期存在的设备。

因此，“设备接入”并不只是建立一条网络连接。

它至少包含几层不同的问题：平台怎样标识一台设备，设备怎样被纳入平台管理，它使用什么凭证证明自己的身份，以及认证成功以后怎样真正建立通信关系。

这些问题如果混在一起，系统早期可能仍然能够运行，但随着设备量增加，很快就会出现麻烦。设备更换网络以后是不是应该重新创建？证书泄露以后能不能只更换凭证？设备恢复出厂以后原来的身份还在不在？一台网关重新代理某个子设备以后，平台是不是还认为它是原来的那台设备？

这些问题表面上属于不同场景，背后其实都依赖一个共同前提：

**设备身份必须比一次连接更加稳定。**

本章就从这里开始。

我们会先建立设备标识、设备身份、凭证、注册、激活、认证和连接之间的基本关系，再看看一台设备从生产出来，到第一次进入星云、获得身份、证明自己，最终建立连接的完整过程。

在这个过程中，我们也会逐渐看到，消费设备、企业批量设备、网关和子设备虽然接入方式不同，但平台需要解决的核心问题其实非常相似。

本章暂时不会深入讨论 MQTT Broker 应该选择哪一种，也不会展开高并发连接集群怎样实现。这些更偏工程实现的问题，会在后面的设备接入基础设施章节中专门讨论。

这一章首先要建立的是更稳定的一层：

**无论设备最终通过什么协议、网络和基础设施接入，星云都必须能够回答“你是谁、你凭什么证明自己，以及我现在怎样和你保持联系”。**

把这三个问题分清楚，后面的连接、消息、状态和控制设计才有可靠的起点。
