# 第 5 章：消息、状态与控制——设备和平台如何形成闭环

## 引言

用户在 App 中点击“关闭客厅灯”，接口很快返回“请求已受理”，灯却仍然亮着。平台已经记录了这次请求，消息可能正在等待发送，也可能已经到达设备，只是执行反馈还没有回来。对用户而言，他关心的事情很直接：灯什么时候会关，是否还需要再点一次？平台要回答这些问题，就得知道这次操作究竟进行到了哪里。

平时使用智能设备，我们很少留意中间的通信过程。点击开关，灯随即熄灭，整个过程看起来和按下墙壁开关没有多大区别。可一旦等了几秒还没有动静，我们就会发现，页面上的响应和设备上的变化之间，还有一段需要被解释的过程。尤其当人不在设备旁边时，应用显示的信息几乎就是判断现场情况的全部依据。

第四章建立了理解这件事所需的概念。模型说明灯支持开关能力，期望状态记录用户希望关灯，报告状态保存设备最近一次上报的开关值，控制记录描述某次请求的处理过程。区分这些信息以后，我们还需要把它们联系起来：用户的要求怎样到达设备，设备的反馈又怎样回到平台，让应用知道发生了什么。

设备也会在没有 App 请求的情况下发生变化。家人通过墙壁开关关了灯，设备随后报告新的开关值；传感器定时采样，把新的温度读数送到平台。这些上报不断更新着平台对现场的了解。因此，除了跟踪一次操作的结果，平台还要持续接收设备的变化，并处理用户期望与设备报告暂时不一致的情况。

**本章讨论设备上报和应用控制如何把消息、状态与操作结果联系起来。** 网络顺畅时，一次交互可能很快完成；设备暂时离线或反馈迟迟未到时，平台仍然需要知道哪些事情已经确认，哪些还需要等待。这也是章标题中“闭环”的含义：把请求、处理进展和反馈关联起来，依据操作约定判断结果，或明确记录尚未确认的部分。

下面从消息模型开始，看看每次交互需要携带哪些信息，再沿一次控制请求，逐步理解设备与平台怎样完成这段往返。
