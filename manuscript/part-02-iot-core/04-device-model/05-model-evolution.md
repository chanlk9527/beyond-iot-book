# 4.5 模型演进：设备变化以后怎么办

晴川智能灯 S1 刚交付时，平台用一份包含开关和亮度属性的模型描述它。后来，一部分设备升级了固件，开始支持场景模式，另一部分仍然运行旧固件。如果平台直接给所有 S1 设备增加场景控制入口，尚未升级的设备就会收到无法处理的请求；如果始终沿用原来的能力定义，新功能又无法被应用使用。

上一节讨论了如何保存设备运行事实，而这些记录能够被正确解释，有一个前提：平台知道记录产生时适用的能力定义。设备能力和平台定义都可能随时间变化，因此，模型需要同时支持当前设备的使用与过去数据的解释。模型演进要处理的，就是变化发生以后，设备、模型、应用和运行记录之间的对应关系如何继续成立。

<a id="_4-5-1-产品-设备和模型关注不同层面的变化"></a>

## 4.5.1 产品、固件与模型的变化边界

讨论升级之前，需要先区分变化发生在哪一层。产品定义组织一类设备的交付与管理，设备实例对应某一台持续运行的实体，固件决定设备内部运行的软件，模型则描述平台可以使用哪些能力。这些信息彼此关联，但分别承担不同职责，不适合共用一个版本号来表示所有变化。

<a id="_4-5-2-重大产品变化通常会形成新的产品定义"></a>

例如，晴川在 S1 之后推出智能灯 Pro，增加彩光灯珠、更强的处理器和新的通信模组，同时采用不同的销售与售后方案。在这样的交付安排下，可以为 Pro 建立独立的产品定义，分别管理两类设备。即使它们都具有开关和亮度能力，也没有必要仅因功能相似而合并产品；反过来，同属 S1 的两台设备，也可能因为固件升级进度不同而暂时具备不同能力。

<a id="产品版本"></a>
<a id="固件版本"></a>
<a id="模型版本"></a>

| 管理对象 | 主要描述什么 | 示例中的变化 |
| --- | --- | --- |
| 产品定义 | 产品的交付与管理边界 | S1 与 Pro 分别管理 |
| 设备实例 | 某台设备的身份及当前关联信息 | 同一台 S1 持续运行，固件发生升级 |
| 固件版本 | 设备内部运行的软件实现 | 修复重连问题，或增加场景控制 |
| 模型版本 | 能力的名称、语义与使用约定 | 增加操作定义，或调整属性约束 |

**产品归属、固件版本和模型版本需要分别记录，再通过明确的适用关系连接起来。** S1 与 Pro 是两个产品定义，不能简单当作同一模型的两个版本；固件从 1.0 升级到 1.1，也不意味着模型必须同步增加一个版本。判断是否需要调整模型，要继续看设备对外提供的能力与约定是否改变。

<a id="_4-5-3-固件升级是模型变化最常见的来源"></a>

## 4.5.2 从固件变化判断模型是否需要演进

假设 S1 的初始固件支持开关和调光，模型 V1 用 `power` 与 `brightness` 两个属性描述这些能力。固件 2.0 新增了预设场景控制，平台可以在模型 V2 中增加 `set_scene` 操作，使应用能够通过统一接口调用它。升级后的设备关联 V2，尚未升级的设备继续使用 V1，两种设备仍属于同一个产品。

这里，能力变化需要有设备侧的实现基础。利用已有调光硬件实现渐亮场景，可以主要通过固件完成；如果新增的是色温调节，就还需要设备具备相应的光源和驱动电路。模型能够描述设备已经实现的能力，不能通过增加一个字段让缺少必要硬件的设备获得新功能。

<a id="_4-5-4-固件升级不一定导致模型变化"></a>

如果固件 1.1 只修复 Wi-Fi 重连或降低待机功耗，属性、事件、操作及其对外约定均未改变，平台仍然可以使用模型 V1。多个固件版本因此可以对应同一个模型版本。**固件变化是否引起模型变化，取决于它是否改变平台需要理解和使用的能力约定。** 版本号本身不能代替这项判断。

模型也可能在设备固件不变时演进。例如，原先温度属性没有明确记录单位，后来依据已有协议确认它始终表示摄氏温度，并在模型中补充说明。这是平台描述方式的完善。不过，只有旧数据的单位已有可靠依据时，才能用这一说明解释历史记录；如果过去混用了不同单位，就需要先识别来源并处理差异，不能通过修改模型把不确定的历史数据统一认定为摄氏温度。

由此，模型演进既包括设备能力的增加、修改或移除，也包括平台对这些能力描述方式的调整。每次变化都应说明影响了哪些设备、哪些数据和哪些调用方，再决定如何发布新的定义。

<a id="_4-5-6-模型演进需要考虑数据和历史兼容"></a>

## 4.5.3 兼容性取决于原有含义是否保持

在模型 V1 的基础上增加 `set_scene`，通常比改变 `brightness` 的含义更容易兼容。前提是已有属性和操作保持原来的约定，旧应用能够容忍不认识的新能力，新应用也会在调用前判断设备是否支持。新增能力并不意味着所有设备都必须立即提供它，更不应因为某次上报缺少新字段，就把字段值补为零或据此断定设备故障。

改变已有能力时，需要沿着数据和控制两条路径检查影响。假设 V1 把亮度表示为 0～100 的百分比刻度，V2 改为 0～1000 的千分比刻度。在这两种明确定义下，同一个 `brightness = 50` 分别表示 50% 和 5%。旧应用若仍按百分比展示或发送控制参数，得到的结果就会偏离原先的含义。问题涉及数值如何解释，单纯扩大字段的允许范围不能解决它。

如果变化仅来自设备协议的表示精度，平台可以在接入转换中把新旧协议都换算成稳定的模型单位，避免把差异传递给每个应用。如果平台模型确实需要改变刻度或语义，就应发布能够明确区分的新定义，并提供转换或迁移规则。移除能力、改变枚举含义、收紧参数范围，以及修改操作完成条件，也都需要检查已有应用是否仍能按原来的约定工作。

对历史数据而言，兼容意味着过去的记录仍能按当时的定义解释。**设备当前使用的模型版本，不能自动成为它全部历史数据的解释依据。** 星云可以在记录中保留适用的模型版本，或维护能够可靠追溯的关联关系，同时保留对应的模型定义。收到升级前采集、升级后才补传的数据时，也需要依据消息携带的版本信息或可核查的采集上下文选择规则，不能只按接收时的设备版本处理。

当前状态同样可能保留升级前的值。切换模型关联时，旧值需要按明确规则转换，或者标记为等待重新上报，不能直接套用新单位继续展示。这样，兼容处理才同时覆盖了未来的调用、已有状态和历史记录。

<a id="_4-5-5-应用必须根据能力理解设备-而不是根据名称猜测"></a>

## 4.5.4 新旧设备共存时的能力识别

明确模型差异以后，还需要把正确的定义关联到每台设备。在开篇的升级过程中，平台发布了模型 V2，并不意味着所有 S1 都已具备新能力；发出了固件升级任务，也不等于设备完成了升级。平台应在获得可信的升级结果、版本上报或能力信息后，再按适用规则更新实例关联。确认机制还应考虑硬件修订、固件分支等条件，避免仅凭一个缺少上下文的版本字符串推断能力。

**应用应依据设备实例当前确认的能力及其约束组织功能。** 对支持 `set_scene` 的设备，可以展示场景选择；对仍使用 V1 的设备，则继续提供开关与调光。判断还需要覆盖参数类型、取值范围和访问方式，而不只是检查能力名称是否存在。例如，同样支持亮度属性的设备，应用仍应按照适用模型生成和校验控制参数。

模型定义、实际支持能力与最近属性值是不同的信息。某台设备尚未上报新属性，不一定表示它不支持；一个历史值仍然存在，也不能证明当前固件继续支持这项能力。因此，能力查询应来自已经确认的实例与模型关系，状态查询则提供运行观测，应用不能用其中一项代替另一项。

固件回滚也会改变这项关系。如果一台已支持场景控制的灯退回旧固件，平台就需要重新确认适用模型，应用也应停止向它发起新场景请求。由于页面展示到实际发送之间仍可能发生变化，控制入口还应依据设备当时确认的能力再次校验。对于升级期间尚未确认的能力，可以暂缓开放相关功能，并向应用提供明确状态，而不必假定设备已经成功切换。

<a id="_4-5-7-星云中的版本关系"></a>

## 4.5.5 星云中的模型发布与长期维护

结合前面的约束，星云可以把模型演进组织为定义发布、实例确认和数据兼容三个相互衔接的过程。发布新定义时，先确定能力变化、适用的产品与硬件条件、关联的固件范围，以及对已有数据和应用的影响。对于正在被设备使用、或仍被历史记录引用的定义，应保留可追溯的版本，避免原地修改后使同一版本标识出现两种含义。

回到 S1 的场景功能升级，平台可以先发布 V2 及其适用规则，使接入和应用准备好处理新能力，再逐步升级设备。每台设备确认升级完成后，更新它的模型关联；尚未升级或升级失败的设备继续使用 V1。这个过程需要同时验证 V1 的原有控制、V2 的新增操作，以及升级和回滚时的状态处理，不能只验证新固件能否完成一次场景调用。

<a id="_4-5-8-平台真正管理的是长期变化关系"></a>

新版本稳定运行以后，旧版本的处理仍取决于使用情况。停止让新设备关联 V1，并不等于可以删除 V1：可能还有未升级设备依赖它，历史记录也可能需要它来解释。**模型的维护期限由设备使用和数据解释的需要共同决定。** 若最终停止支持某项旧能力，也应明确应用和存量设备如何迁移，而不是仅从定义中移除一个字段。

至此，第四章建立了设备、能力和运行数据之间的关系。模型给出共同定义，协议映射把设备表达对应到这些定义，运行记录保存具体设备的观测与控制过程，模型演进则让这些关系在设备变化后仍然可用。平台因此能够判断某台设备当前支持什么，以及过去的一条记录应当怎样解释。

有了这些依据，一次开关请求或一条状态上报便具备了明确含义。不过，消息仍可能延迟、重复或丢失，请求也可能停留在不同的执行阶段。下一章将进入设备与平台的交互过程，讨论消息如何传递、结果如何关联，以及一次控制如何形成可确认的闭环。
