# 4.3 从设备数据到平台模型：设备如何被“翻译”

上一节介绍了属性、事件和操作，它们为平台描述设备能力提供了统一的方式。不过，模型中定义了车速属性，并不意味着设备上报的数据就能直接作为这个属性使用。设备可能只发送一段二进制报文，平台还需要知道其中哪些字节表示车速、数值采用什么单位，以及这条消息表达的是一次测量还是一次告警。

从设备报文到模型数据，需要建立一套明确的对应关系。协议解析负责读出字段，数据转换负责处理数值表示，模型映射则把转换后的数据归入相应的设备能力。这些工作共同连接了设备侧的通信约定与平台侧的能力模型，也是应用能够统一使用不同设备的前提。

<a id="_4-3-1-设备语言和平台语言解决不同的问题"></a>

## 4.3.1 设备协议与平台模型的分工

设备侧的数据表达受通信带宽、功耗和硬件资源约束，往往采用适合自身运行条件的格式。例如，一台内置 4G 通信模块的车载定位终端，通过移动网络向车辆管理平台上报位置、车速等数据。为了减少上报数据量，它可能采用厂商自定义的二进制报文。假设其中的车速数据片段如下：

```text
01 00 FD
```

在这个示例协议中，`01` 表示车速数据类型，后两个字节按高字节在前的顺序表示无符号整数。`00 FD` 对应十进制数 253，协议约定以 0.1 km/h 为单位，因此这段数据表示车速为 25.3 km/h。设备固件按照这套约定生成报文，平台也必须依据同一套约定读取它。

连接认证可以帮助平台确认设备身份，却不能代替报文解释。接入层还需要根据设备所属产品及其协议版本，选择相应的解析规则。脱离这些约定，`01` 只是一个字节，253 也只是一个整数；平台无法仅凭它们确定能力名称、单位和业务含义。

应用需要使用的则是模型中定义的 `speed` 属性：它的类型是浮点数，单位是 km/h，这台设备本次上报的值为 25.3。**设备协议规定设备如何交换和表达数据，平台模型规定这些数据在平台中对应什么能力。** 协议本身也可以包含明确的业务含义，映射工作的任务，就是把这些含义与平台模型中的定义对应起来。

<a id="_4-3-2-数据进入平台前-需要经过解析和映射"></a>

## 4.3.2 从报文字段到属性值

沿着车速报文继续向下看，可以把数据处理过程分成三个层次。它们在实现中可以由同一个适配器完成，但各自依据的规则和处理的问题不同，区分这些职责有助于判断错误究竟发生在哪里。

<a id="协议解析"></a>

协议解析依据报文结构读取字段。在本例中，解析器识别出类型字段为 `01`，随后读取两个字节，按照约定的字节顺序得到整数 253。对于完整报文，解析器还需要按协议检查长度、校验信息等内容；如果报文不完整，就不能把缺失的字节当作有效数据继续处理。这一层得到的是协议字段及其原始值。

<a id="数据转换"></a>

数据转换依据字段定义，把原始表示转换成模型使用的值。车速的换算规则是 `253 ÷ 10 = 25.3`，其结果以 km/h 表示。其他字段可能需要处理单位换算、枚举值对应或数值精度。转换规则必须来自设备协议和产品定义，例如某个特殊数值如果被约定为“测量无效”，就应先识别这一含义，不能直接参与普通数值换算。

<a id="模型映射"></a>

模型映射进一步确定转换结果属于哪项能力。对于这台定位终端，类型 `01` 对应模型中的 `speed` 属性，因此处理结果是一条属于该设备的车速属性上报。平台还应依据模型检查结果是否符合属性的数据类型和取值约定，避免把无法解释或不符合定义的值写入正常状态。

整个过程可以简要表示为：

```text
01 00 FD → 类型 01、原始值 253 → 25.3 km/h → speed 属性上报
             协议解析             数据转换        模型映射
```

**解析成功只说明报文能够被读取，完成映射后，数据才具有平台约定的能力含义。** 如果车速被错误地换算为 253 km/h，问题出在转换规则；如果 25.3 被写入温度属性，问题则出在模型映射。把这几个层次分清，既有利于组织接入代码，也能让后续排查有明确依据。

<a id="_4-3-3-真正困难的是语义-而不是格式"></a>

## 4.3.3 映射规则中的业务语义

数值换算解决了表示方式的差异，但字段的业务含义仍然需要单独确定。一个状态码 `1`，在智能灯协议中可能表示开启，在门磁协议中可能表示门已打开，在工业设备协议中又可能表示运行正常。平台必须结合产品定义解释这个值，不能给所有设备建立一条通用的“1 表示开启”规则。

即使属于同一种设备，相似的数据也可能承担不同职责。门磁上报“门当前处于打开状态”，对应的是状态属性；上报“刚刚发生了一次开门”，对应的则是事件。前者用于回答最近观察到的状态，后者用于保留一次发生过的事实。如果把周期性的打开状态上报都转换成开门事件，门持续打开期间就会产生多次虚假的开门记录。因此，映射规则除了字段名称和枚举值，还必须说明消息是在报告状态，还是在报告某次事件。

操作结果也需要按照其实际含义处理。设备回复“已接收开灯请求”，只能说明请求已经到达设备；除非协议明确保证这条回复代表执行完成，否则平台不能据此认定灯已经开启。是否更新开关属性，应取决于回复所作的保证或后续状态上报。**模型映射必须保留设备消息原有的语义边界，不能把有限的确认扩展成尚未得到证实的运行事实。**

由此可见，一份可用的映射定义需要共同确定来源字段、转换规则、目标能力和消息含义。这些约定使不同设备的数据能够进入同一个模型，也约束了应用可以从数据中得出什么结论。字段名称相同只是统一表达的一部分，含义一致才是应用复用这些数据的基础。

<a id="_4-3-4-开放生态需要适配不同设备"></a>

## 4.3.4 第三方设备的协议适配

当平台接入第三方设备时，前面的解析、转换和映射通常由协议适配层承担。已有设备的报文格式和固件行为往往已经确定，平台需要依据厂商提供的协议与产品资料建立适配规则，把设备特有的表达转换成平台能够处理的数据。

例如，假设某工业设备通过 Modbus 提供温度读数，厂商文档把温度寄存器标为 `40001`，并约定其数值为摄氏温度的十倍。读取结果为 253 时，适配器依据这份定义换算出 25.3℃，再将它映射到设备模型的 `temperature` 属性。这里，温度含义和缩放比例来自该产品的寄存器定义；仅仅知道设备使用 Modbus，还不足以完成映射。

经过适配，应用可以围绕温度属性读取数据、设置展示方式或编写告警条件，寄存器位置和厂商报文细节则由接入部分处理。**适配层把协议差异集中在设备接入的边界，使上层服务能够围绕模型能力工作。** 如果每个应用都自行解释寄存器，同一套换算和映射规则就会散落在多个系统中，协议变化时也必须分别修改。

这种方式适合平台无法统一设备固件的场景，代价是每种协议及其版本都需要相应的适配、验证和维护。适配器也只能转换设备实际提供的信息：如果设备只报告当前状态，没有提供事件记录，平台就不能仅靠映射恢复完整的事件历史。接入范围扩大，并不意味着所有设备都具备同样的能力或数据质量。

<a id="_4-3-5-自有产品体系更适合建立标准接入协议"></a>

## 4.3.5 自有产品的标准接入协议

如果企业能够协调设备固件和平台共同开发，就可以在产品设计阶段统一接入约定。例如，让智能灯、门锁和传感器采用一致的消息结构上报属性、发送事件、接收操作并返回结果，再由各自的产品模型定义具体能力。这样，新产品仍然需要确定自身的业务含义，但可以复用已有的通信和消息处理机制。

这套约定可以通过接入协议文档、设备 SDK、固件组件或模组方案交付。设备团队把采样值和固件状态对应到产品模型，公共组件负责约定中的消息封装、连接和认证等工作；平台则使用统一的消息处理入口。标准接入协议由此把一部分原本由平台适配器完成的工作，前移到设备开发阶段。

<a id="_4-3-6-标准协议是一种长期工程效率优化"></a>

对于持续推出新产品的企业，这种投入能够减少重复的协议设计和接入开发。设备团队可以复用通信组件，平台团队也可以复用解析逻辑与通用测试，不过产品特有的能力映射和行为仍然需要验证。**标准协议的收益在于复用共同机制，而它的成本是持续维护这套共同约定。** SDK 升级、协议兼容和新旧固件共存，都需要设备与平台团队共同承担。

因此，是否统一接入协议，取决于企业对设备开发的控制程度和长期复用的需求。对能够共同规划的新产品，标准协议有利于减少重复工作；对难以修改的存量设备，保留适配器往往更符合实际。统一协议也不要求所有设备使用同一种网络，只要数据到达约定的接入边界后，能够按一致的消息和模型规则被处理即可。

<a id="_4-3-7-标准协议和开放适配并不冲突"></a>
<a id="_4-3-8-星云的数据接入方式"></a>

## 4.3.6 星云中的两条接入路径

据此，星云可以同时提供标准接入和协议适配两条路径。自有或深度合作的设备按照平台协议表达能力与数据，第三方设备通过适配器完成解析、转换和映射。两条路径最终汇入同一套模型约定，使状态服务、数据服务和业务应用能够使用一致的能力标识与数据含义。

```text
自有设备   → 标准接入协议 → 消息解析与模型校验 ─┐
                                              ├→ 标准设备数据 → 平台服务与应用
第三方设备 → 厂商设备协议 → 协议解析、转换与映射 ─┘
```

标准接入路径仍然需要校验消息类型、能力标识和数据值，只是可以复用更多规则；适配路径则需要补齐设备协议到平台模型之间的对应关系。无论经过哪条路径，交给后续服务的数据都应能够明确归属到具体设备和具体能力，并保留其作为属性上报、事件或操作结果的含义。对于无法确定含义的数据，接入部分应记录异常，而不能猜测后写入正常业务记录。

至此，设备模型与设备数据建立了联系：模型定义平台可以理解哪些能力，接入过程把设备实际报告的信息对应到这些能力。应用因而可以基于模型使用设备，而由接入部分承担协议差异带来的处理工作。

不过，一条数据被正确解释，并不意味着它始终代表设备此刻的状态。车速从采集到到达平台需要时间，后续上报还可能延迟、重复或乱序。接下来的问题便是：平台应如何在模型定义的基础上，分别管理最近观察到的状态、持续产生的历史数据，以及已经发生的事件。
