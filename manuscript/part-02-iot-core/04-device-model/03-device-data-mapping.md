# 4.3 从设备数据到平台模型：设备如何被“翻译”

上一节我们讨论了能力模型。

能力模型解决的是：

> 平台如何描述设备具有什么能力。

例如，一盏智能灯支持：

- 开关；
- 调光；
- 色温控制；
- 过温告警。

但是，设备真正运行时，并不会直接产生“属性”“事件”“操作”这样的概念。

设备首先产生的是自己的通信数据。

这些数据可能来自：

- 传感器采样；
- 固件状态；
- 控制结果；
- 协议消息。

平台需要将这些设备侧表达转换成统一模型，才能让上层应用理解。

因此，IoT 平台中通常存在一个重要过程：

**设备协议数据 → 平台模型数据。**

这个过程可以称为协议解析、数据映射或模型转换。

---

## 4.3.1 设备语言和平台语言解决不同的问题

设备和平台关注的问题并不相同。

设备侧首先关心：

- 如何可靠通信；
- 如何减少数据量；
- 如何降低功耗；
- 如何适配硬件资源。

例如，一个资源有限的温度传感器，可能通过蓝牙广播发送一个简单的数据帧：

```
01 0A FD
```

其中：

- `01` 表示数据类型；
- `0A FD` 表示温度编码。

设备固件知道：

这几个字节代表什么。

但平台收到后，并不知道：

- 这是什么设备；
- 01 对应什么能力；
- 数值如何转换；
- 它表示状态还是事件。

平台需要的是：

```text
设备：
temperature

类型：
float

单位：
℃

当前值：
25.3
```

因此：

**设备协议描述信息如何传输，平台模型描述信息代表什么。**

两者承担不同职责。

---

## 4.3.2 数据进入平台前，需要经过解析和映射

设备产生的数据，通常需要经过几个步骤。

例如，一个温度设备上报：

```
设备数据：

0x01 0x00 FD
```

平台接入层首先需要根据设备协议解析：

```
字段：

类型 = 01

数据 = 253
```

然后根据产品定义转换：

```
253 ÷ 10 = 25.3℃
```

最后映射到平台模型：

```
属性：

temperature

值：

25.3℃
```

这个过程包含几个不同层次：

### 协议解析

解决：

> 这一段数据怎样读取。

例如：

- 哪几个字节代表温度；
- 字节顺序是什么；
- 是否需要校验。

---

### 数据转换

解决：

> 原始数值怎样变成业务数据。

例如：

- 放大倍数；
- 单位转换；
- 枚举转换。

---

### 模型映射

解决：

> 这条数据属于设备的什么能力。

例如：

```
字段 01

↓

temperature 属性

↓

设备当前温度
```

只有完成这些步骤，平台和应用才能使用设备数据。

---

## 4.3.3 真正困难的是语义，而不是格式

格式转换通常比较明确。

例如：

```
253

↓

25.3℃
```

但是 IoT 中更困难的问题是：

> 这个数据到底代表什么。

例如设备发送：

```
状态码：

1
```

它可能表示：

对于智能灯：

```
power = on
```

对于门磁：

```
door = open
```

对于工业设备：

```
running = normal
```

同一个数字，在不同设备中可能完全不同。

因此，平台不能只保存：

```
字段 = 数值
```

而必须结合设备模型理解：

```
这个字段属于什么能力。

这个值代表什么含义。

这个数据如何被应用使用。
```

这也是为什么设备模型是 IoT 平台的重要基础。

---

## 4.3.4 开放生态需要适配不同设备

如果一个 IoT 平台希望连接大量第三方设备，就必须面对设备世界的差异。

例如：

家庭设备可能使用：

- Wi-Fi；
- BLE；
- Zigbee。

工业设备可能使用：

- Modbus；
- OPC UA；
- CAN。

不同厂商还可能有自己的私有协议。

这些设备已经存在，并不会因为某个平台出现，就全部重新开发。

因此，开放型 IoT 平台通常需要建设：

**协议适配层。**

典型流程：

```
第三方设备协议

        ↓

协议解析

        ↓

数据转换

        ↓

模型映射

        ↓

平台标准数据

        ↓

应用使用
```

例如：

一个工业设备通过 Modbus 提供：

```
寄存器 40001 = 253
```

平台通过设备协议定义知道：

```
40001 = 温度 ×10
```

转换后：

```
temperature = 25.3℃
```

应用不需要理解：

- 寄存器地址；
- 通信帧格式；
- 厂商协议。

它只需要理解：

设备具有一个温度属性。

---

## 4.3.5 自有产品体系更适合建立标准接入协议

但是，开放生态只是 IoT 平台的一种情况。

对于拥有大量自有产品的企业，例如：

- 智能灯；
- 空调；
- 门锁；
- 传感器；

长期依靠协议适配并不是最优选择。

因为每增加一种设备，都可能增加：

- 协议解析代码；
- 数据映射规则；
- 测试工作；
- 维护成本。

因此，很多大型 IoT 平台会建立自己的设备接入规范。

也就是说：

不是平台不断学习设备语言，

而是设备按照平台约定表达。

---

例如，平台可以提供：

- Device SDK；
- 固件 SDK；
- 模组方案；
- 接入协议规范。

统一约定：

设备如何：

- 注册身份；
- 建立连接；
- 上报属性；
- 发送事件；
- 接收操作；
- 返回执行结果。

设备开发团队只需要实现：

```
初始化设备

↓

连接平台

↓

上报能力和数据

↓

接收控制

↓

反馈结果
```

而不需要每个产品重新设计完整通信逻辑。

---

## 4.3.6 标准协议是一种长期工程效率优化

建立统一协议，看起来增加了设备开发约束。

但对于大规模产品体系来说，它减少的是长期复杂度。

对于设备团队：

可以复用：

- SDK；
- 通信机制；
- 认证流程；
- OTA 能力。

产品团队可以更多关注：

- 硬件功能；
- 用户体验；
- 产品差异化。

对于平台团队：

可以减少：

- 重复协议解析；
- 数据适配；
- 接入测试。

因此，很多成熟 IoT 企业会同时建设：

- 云平台；
- 设备 SDK；
- 模组方案；
- 开发工具链。

这些并不是独立产品，而是一套设备生态能力。

---

## 4.3.7 标准协议和开放适配并不冲突

一个成熟 IoT 平台通常同时存在两条路径。

第一类：

**自有或深度合作设备。**

例如品牌自己的产品。

流程：

```
设备 SDK

↓

标准协议

↓

平台模型
```

设备直接按照平台规范提供数据。

转换工作较少。

---

第二类：

**开放生态设备。**

例如合作伙伴已有产品。

流程：

```
第三方协议

↓

适配层

↓

平台模型
```

平台负责吸收差异。

---

因此，现代 IoT 平台并不是选择：

“全部统一”

或者：

“全部开放”。

而是：

- 对内部生态建立标准；
- 对外部生态提供适配。

这样既能提高自身产品效率，也能扩大生态范围。

---

## 4.3.8 星云的数据接入方式

结合前面的设计，星云可以将设备数据进入平台的过程抽象为：

```
设备

↓

设备协议 / SDK

↓

接入层

↓

协议解析

↓

数据转换

↓

能力模型映射

↓

标准设备数据

↓

状态服务、数据服务、业务应用
```

其中：

设备协议解决：

> 数据怎样传输。

接入层解决：

> 不同设备怎样进入平台。

模型映射解决：

> 数据代表什么能力。

平台服务解决：

> 这些能力怎样被应用使用。

---

最终，设备模型的价值不是消灭设备差异。

现实世界中的设备一定不同。

真正成熟的平台做的是：

**在设备侧允许多样性，在平台侧建立统一理解。**

开放生态依靠适配能力连接更多设备；

自有生态依靠标准协议降低长期成本。

两者共同决定了一个 IoT 平台能够支持多少设备、多少产品，以及未来能否持续演进。
