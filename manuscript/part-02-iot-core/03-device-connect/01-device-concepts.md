## 3.1 设备进入平台之前：先分清几个概念

假设一台新的温湿度传感器第一次启动，并准备连接星云。

我们很容易说一句：

> 设备登录平台了。

但如果把这句话拆开，会发现里面其实混合了很多不同的事情。

平台首先要知道这是哪一台设备；设备需要证明自己确实拥有这个身份；如果它之前从未出现过，平台还要决定是否允许它加入系统；如果验证通过，双方才能进一步建立连接；连接建立以后，平台才能认为这台设备当前可以通信。

这些步骤在一个简单 Demo 中可能只需要几十行代码，看起来没有必要严格区分。但平台真正运行起来以后，设备会断线，会更换网络，会恢复出厂，会更换证书，也会被转卖、返修甚至重新分配给其他客户。此时，如果设备标识、身份、凭证、注册、认证和连接全部混成一个概念，很多问题就会变得非常难处理。

所以，在设计接入流程之前，我们先把几个最基本的概念分开。

### 3.1.1 标识回答“怎么找到你”，身份回答“你是谁”

一台真实设备通常拥有很多可以用来区分它的编号。

例如序列号、MAC 地址、IMEI、芯片唯一 ID，甚至包装盒上的二维码，都可能在某个环节中用来识别设备。

这些都可以称为某种**设备标识**。

标识首先解决的是区分问题：有了它，我们能够把一台设备和另一台设备区分开。

但平台中的**设备身份**还要更进一步。

设备身份表示星云长期认为“这就是哪一台设备”。它通常对应平台中的一个稳定设备实例，并与这台设备的产品、生命周期、权限、状态和历史数据关联。

这两者经常可以对应，但不应该天然认为它们就是同一个东西。

例如，一台设备可能有这样的信息：

```text
设备序列号：SN202609290001
MAC 地址：A4:7B:...
芯片 UID：8F2A...
星云 Device ID：dev_01K...
```

前三个都来自硬件或生产环节，最后一个则是平台建立的设备身份。

为什么还要多一个平台 Device ID？

因为硬件标识有自己的生命周期和局限。

MAC 地址可能因为通信模块更换而变化；某些芯片 ID 只在特定硬件平台上存在；OEM 产品可能需要重新组织设备编号；生产序列号的格式也可能随着供应商变化。

如果平台把自己的核心身份完全绑定在某一种硬件标识上，那么底层硬件一变，平台中的设备关系也会跟着受到影响。

因此，更稳妥的思路通常是：

**外部标识用于帮助平台找到或确认设备，平台身份则用于长期管理这台设备。**

当然，这并不意味着每一种设备都必须拥有很多编号。对于非常简单的产品，某个硬件唯一标识完全可以参与设备身份生成。重要的不是形式，而是理解两者承担的责任不同。

### 3.1.2 知道设备是谁，不代表它已经证明了自己

假设一台设备连接平台时声称：

> 我的 Device ID 是 `dev_123`。

平台能不能因此相信它就是 `dev_123`？

当然不能。

因为任何知道这个编号的程序都可以发送同样的内容。

这就需要另一个概念：**凭证**。

凭证是设备用来证明自己身份的材料。它可以是一段设备密钥，也可以是证书和对应私钥，还可能是其他受保护的认证材料。

因此，可以简单理解：

**设备身份回答“你是谁”，凭证回答“你拿什么证明”。**

这两个概念必须分开，一个很重要的原因是凭证需要能够变化。

设备可能运行很多年。在这段时间里，凭证可能因为安全策略需要定期轮换，也可能因为泄露被吊销，再重新签发新的凭证。

如果“设备身份”和“凭证”是同一个东西，那么每次更换凭证都意味着重新创建一台设备，这显然不合理。

这和人的身份很相似。

一个人更换密码，并不会因此变成另一个人；补办身份证件，也不代表原来的个人关系全部失效。

IoT 设备也一样。

平台长期管理的是设备身份，而凭证只是它在某个阶段证明身份的一种手段。

### 3.1.3 注册解决“平台知不知道你”，认证解决“这次来的真的是不是你”

设备身份和凭证建立以后，还会遇到两个非常容易混淆的动作：**注册**和**认证**。

注册解决的是：

> **这台设备是否已经被纳入平台管理？**

认证解决的是：

> **这一次访问平台的人，是否真的拥有这个设备身份？**

例如，晴川工厂生产了一批新的温湿度传感器，可以在生产系统中提前把设备序列号导入星云，为每台设备创建对应记录。这一步完成以后，平台已经“知道”这些设备存在。

但这些设备此时可能还没有开机，更没有建立任何网络连接。

几周以后，其中一台设备被用户购买并启动。它第一次连接平台时，需要提交自己的凭证。星云检查凭证以后，确认：

> 这次连接者确实是之前登记的那台设备。

这是认证。

因此：

**注册是建立平台关系，认证是验证一次访问。**

一台设备通常只需要在某个阶段完成一次正式注册，但只要它不断断线重连，认证就可能发生很多次。

当然，真实产品中注册过程并不一定发生在工厂。

有些设备会在用户首次配网时才向平台申请注册；有些 B 端设备通过批量导入进入平台；还有些设备在第一次安全启动时根据预置材料自动完成注册。

这些差别属于后面的注册方案设计。

当前最重要的是先区分两种语义：**平台是否已经接受这台设备存在，以及当前连接者是否可信。**

### 3.1.4 激活通常表示“这台设备开始真正投入使用”

在设备注册流程中，还经常会出现另一个词：**激活**。

这个词在不同厂商的平台里含义并不完全一致，因此不能把它当成一个绝对统一的技术标准。

在星云中，我们可以先把激活理解为：

**一台已经具备设备身份的设备，第一次满足必要条件并正式进入可用生命周期。**

例如，一批设备在工厂生产时就已经完成预注册，但此时它们还只是库存。

当用户购买设备、完成首次配网，并成功与平台建立可信关系以后，平台可以把它们从“已注册”推进到“已激活”。

于是：

> 注册更偏向“平台已经认识这台设备”，  
> 激活更偏向“这台设备已经开始真正使用”。

为什么要区分这两个状态？

因为很多业务确实需要知道设备是否真正进入使用阶段。

生产了十万台设备，不代表已经有十万台活跃设备；

设备进入仓库，也不代表已经属于最终用户；

售后保修、订阅服务、运营统计甚至许可证计费，都可能关心首次激活时间。

不过，不同产品并不一定都需要显式的“激活”对象。

如果某类设备只有第一次连接平台时才会创建设备记录，那么注册和激活甚至可以发生在同一流程中。

因此，激活更像是一种生命周期概念，而不是每套 IoT 平台都必须拥有的固定 API。

### 3.1.5 认证成功以后，才谈得上连接

认证通过以后，平台和设备之间才可能建立持续通信关系。

这就是**连接**。

例如，一台设备通过 MQTT 与平台建立长连接。在连接存在期间，平台可以接收它的上报，也可以沿着这条连接下发控制。

但连接和设备身份的生命周期差异很大。

一台设备可以在星云中存在五年，而一次 MQTT 连接可能只持续几个小时。

Wi-Fi 信号不好，连接会断开；路由器重启，连接会断开；设备进入省电模式，也可能主动关闭连接。稍后重新联网时，它再次完成认证，然后建立一条新的连接。

因此：

**设备可以存在，但当前没有连接。**

这就是通常所说的“离线设备”。

反过来，平台中出现一条网络连接，也不应该在没有身份认证的情况下自动认为它已经对应某台合法设备。

这就是为什么身份与连接必须分离。

对于网关场景，这种区别更加明显。

一台 Zigbee 传感器可能从来没有直接连接过云端，但星云仍然拥有它的独立设备身份。真正与云端建立网络连接的是网关，传感器的消息通过网关代理进入平台。

所以，“平台中有这台设备”和“这台设备拥有一条直接云连接”，本来就是两件不同的事情。

### 3.1.6 在线也不是设备身份的一部分

连接概念再向前一步，就会遇到“在线”。

很多产品页面都会显示：

> 在线 / 离线

看起来非常简单。

但在线并不是一种永久的设备属性，而是平台根据当前通信情况推断出来的一种运行状态。

例如，对于长连接设备，可以把连接仍然有效作为在线的重要依据；对于周期性上报的低功耗设备，则可能需要根据“最近一次通信时间”判断。

一台每小时上报一次数据的传感器，在两次上报之间到底应该算在线还是离线，未必能使用和 MQTT 长连接设备完全相同的标准。

所以，“在线”真正表达的是：

> **平台认为自己当前是否仍然能够与这台设备保持有效通信关系。**

它与“设备存在”“设备已经激活”“设备正在真实世界中工作”都不是同一回事。

一台设备可以离线，但仍然在本地正常运行。

例如，智能灯断开互联网以后，墙壁开关仍然可以打开它；网关与云端断开以后，本地自动化仍然可能继续执行。

因此，后面设计在线状态时，我们必须避免把“云端看不到”直接理解成“设备已经停止工作”。

### 3.1.7 把这些概念放到同一条路径上

现在，可以把前面的几个概念串起来。

一台设备从“刚生产出来”到“能够和星云稳定通信”，大致可能经历：

```text
硬件产生或写入标识
        ↓
平台建立设备身份
        ↓
设备注册
        ↓
准备或获取设备凭证
        ↓
设备激活
        ↓
发起访问
        ↓
身份认证
        ↓
建立连接
        ↓
设备在线
        ↓
上报数据 / 接收控制
```

这不是所有产品都必须严格遵守的固定流程。

有些步骤可以在工厂完成，有些可以在第一次联网时合并，有些产品也可能根本没有显式“激活”状态。

这张图真正想表达的是它们之间的责任差异。

可以用下面这张表简单总结。

| 概念 | 主要回答的问题 |
| --- | --- |
| 设备标识 | 怎样区分或找到这台设备 |
| 设备身份 | 平台长期认为它是哪台设备 |
| 凭证 | 它怎样证明这个身份 |
| 注册 | 平台是否已经把它纳入管理 |
| 激活 | 它是否已经进入实际使用阶段 |
| 认证 | 这一次访问者是否真的拥有该身份 |
| 连接 | 平台当前通过什么通信关系与它交换信息 |
| 在线 | 平台当前是否认为这种通信关系仍然有效 |

这些概念不一定对应八张数据库表，也不一定对应八个 API。

它们首先是一组不同的语义。

设计时可以合并实现，但如果在概念上先把它们混成一件事，后面面对恢复出厂、换证书、返修、设备转移和网关代理时，就很容易陷入混乱。

接下来，我们可以从其中最基础的一个问题开始继续深入：

**一台真实设备究竟应该怎样获得自己的平台身份？**
