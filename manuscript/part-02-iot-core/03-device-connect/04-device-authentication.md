## 3.4 设备认证：设备如何证明自己是谁

前面几节，我们一直围绕一个问题展开：

> 平台如何认识一台设备？

3.2 讨论了设备身份的来源。

我们知道，星云中的设备身份并不一定来自某一个固定字段。它可能来自生产阶段预注册，也可能在首次接入时动态建立。无论采用哪种方式，平台最终都会形成一个稳定的设备对象，用来代表现实中的某一台设备。

但这里还有另一个问题：

**平台知道存在一个设备身份，不代表连接过来的设备就一定是真的。**

例如，平台中已经存在：

```
device_001
```

如果某个客户端连接平台，并发送：

> “我是 device_001。”

平台是否应该相信？

当然不能。

因为设备 ID 本身通常不是秘密。任何知道这个编号的人，都可能尝试伪造一个连接。

因此，设备接入还需要第二个过程：

**认证。**

认证解决的是：

> 当前连接者是否拥有某个设备身份对应的证明能力。

简单来说：

- 身份回答：**你是谁？**
- 认证回答：**你凭什么证明你是它？**

这也是为什么设备身份和认证材料必须分开设计。

---

## 3.4.1 身份是长期对象，凭证是证明方式

回顾 3.2 的设计。

星云中的设备可能具有：

- 平台设备 ID；
- 工厂序列号；
- 模组信息；
- 芯片编号。

这些信息共同帮助平台认识设备。

但认证并不是依靠这些信息本身完成。

认证通常依赖某种凭证。

例如：

- 对称密钥；
- 数字证书；
- 非对称密钥对；
- 短期访问令牌。

这些凭证的共同特点是：

它们能够证明连接方确实拥有某种授权材料。

例如：

设备身份：

```
device_001
```

对应一个认证凭证：

```
credential_xxx
```

设备连接平台时，需要使用这个凭证完成认证。

认证成功以后，平台才建立：

```
连接 → device_001
```

这样的可信关系。

因此：

设备 ID 可以公开；

认证凭证必须受到保护。

---

## 3.4.2 为什么不能只使用设备 ID

很多初学者第一次设计 IoT 接入时，会想到：

> 每台设备有一个唯一 ID，连接时上传 ID 就可以了。

这种方案的问题在于：

ID 只是标识，不是证明。

例如，一个智能门锁：

设备编号：

```
lock_123456
```

如果攻击者知道这个编号，并伪造连接：

```
device_id=lock_123456
```

平台无法判断：

这是真门锁，

还是一个冒充者。

因此，设备认证必须依赖比 ID 更强的机制。

这和日常生活类似。

身份证号码用于标识一个人，但不能单独作为所有场景中的身份验证。

登录银行账户时，需要密码、验证码或者其他证明。

IoT 设备也是如此。

设备 ID 负责让系统知道“讨论的是哪台设备”，认证材料负责证明“当前连接者确实拥有这台设备”。

---

## 3.4.3 常见设备认证方式

不同规模和场景的 IoT 系统，会采用不同认证方式。

### 对称密钥认证

这是较简单也是非常常见的一种方式。

设备和平台共享一个秘密：

```
设备：
secret_key

平台：
secret_key
```

连接时，双方通过算法验证设备是否拥有正确密钥。

这种方式实现简单，计算成本低，适合大量资源有限的设备。

但它也带来一个问题：

如果大量设备共享同一个密钥，一台设备泄露可能影响整个设备群。

因此，大规模设备通常会为每台设备分配独立密钥。

例如：

```
device_001 → key_A
device_002 → key_B
device_003 → key_C
```

这样单台设备的问题不会扩散到全部设备。

---

### 证书认证

在企业级和安全要求较高的场景中，经常使用数字证书。

设备拥有：

- 设备证书；
- 私钥。

平台保存可信的证书链。

连接时，设备证明：

> 我拥有与这个证书对应的私钥。

平台验证：

- 证书是否合法；
- 是否由可信机构签发；
- 是否已经过期或撤销。

这种方式类似互联网 HTTPS 中使用的身份体系。

它的优势是：

- 身份关系更加清晰；
- 支持规模化管理；
- 方便吊销和更新。

但实现复杂度更高，需要管理证书生命周期。

---

### Token 或临时凭证

一些场景中，设备不会长期直接使用固定凭证，而是通过已有身份获取短期访问令牌。

例如：

设备首先完成一次安全注册；

平台返回一个短期 Token；

设备使用 Token 建立后续访问。

这种方式更灵活，适合复杂系统。

但需要注意：

Token 通常不是设备最终身份，而是一种临时访问授权。

它解决的是：

> 当前这次访问是否允许。

而不是：

> 这台设备长期是谁。

---

## 3.4.4 设备认证和用户认证有什么不同

IoT 平台同时存在设备和人的身份体系。

用户登录 App 时，也需要认证。

例如：

用户输入账号密码；

平台验证用户身份；

返回访问权限。

设备认证看起来类似，但目标不同。

用户认证关注：

- 谁在操作；
- 是否允许访问某些资源。

设备认证关注：

- 哪台设备正在连接；
- 它是否是真实设备；
- 是否允许它进入系统。

例如：

用户张三打开 App 控制智能灯。

这里同时发生两种认证：

第一步：

张三登录 App。

平台确认：

> 这是张三。

第二步：

App 请求控制某台灯。

平台确认：

> 这盏灯确实是 device_001。

然后平台还需要判断：

> 张三是否有权限控制 device_001。

因此，一个完整 IoT 操作通常同时涉及：

- 用户身份；
- 设备身份；
- 权限关系。

这也是为什么设备认证不能替代权限系统。

---

## 3.4.5 设备认证失败时怎么办

真实系统中，认证失败是必然会发生的。

例如：

- 设备凭证错误；
- 凭证过期；
- 设备已经被撤销；
- 设备被迁移到其他租户；
- 设备时间错误导致证书校验失败。

平台需要明确处理策略。

例如：

认证失败：

是否允许重试？

是否记录异常？

是否暂时锁定设备？

是否通知运营人员？

是否进入待重新注册状态？

这些策略需要结合设备类型设计。

对于家庭智能灯，用户可能希望重新配网即可恢复。

对于工业控制设备，异常认证可能需要更严格的安全处理。

---

## 3.4.6 凭证生命周期比认证本身更重要

很多系统关注：

> 设备能不能登录。

但长期运行中，更重要的问题是：

> 凭证如何管理。

设备可能运行十年。

期间可能发生：

- 密钥泄露；
- 证书过期；
- 安全策略升级；
- 供应商更换。

因此平台需要支持：

凭证生成；

安全下发；

轮换；

撤销；

恢复。

这里再次体现身份和凭证分离的重要性。

设备身份可以长期保持：

```
device_001
```

但对应凭证可以变化：

```
credential_v1
        ↓
credential_v2
        ↓
credential_v3
```

平台仍然知道：

这是同一台设备。

---

## 3.4.7 星云中的认证关系

综合前面的设计，星云中的关系可以理解为：

```
设备身份
    |
    | 绑定
    |
认证凭证
    |
    | 验证
    |
设备连接
```

其中：

设备身份负责长期管理；

认证凭证负责证明身份；

连接负责传输信息。

三者生命周期不同：

设备身份：

可能存在多年。

认证凭证：

可能定期变化。

连接：

可能几分钟后重新建立。

如果把这三个概念混成一个对象，系统很难支持：

设备换证书；

设备转移；

设备维修；

多环境部署；

安全升级。

---

设备认证的目标，并不是让平台“记住一个密码”。

更准确地说：

**设备认证是在不可信网络环境中，让平台能够确认当前连接者确实代表某个合法设备身份。**
