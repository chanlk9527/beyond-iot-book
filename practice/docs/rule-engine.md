# IoT 自动化与数据集成产品规划

## 1. 文档目的

本文定义平台面向 C 端用户、B 端运营人员和 B 端开发者提供的自动化与数据集成产品。它回答四个问题：

- 不同用户来平台完成什么任务；
- 实时数据、场景自动化、数据集成和通知分别解决什么问题；
- Web、App 和开发者入口如何分工；
- 哪些能力先做，什么结果才算交付。

本文是产品规划和验收依据。技术边界遵循[平台架构与开发约定](architecture.md#规则与集成边界)，EventBus 的实现事实遵循 [EventBus 说明](../backend/EVENTBUS.md)，前端原型操作见[规则与集成交互预览](../console/AUTOMATION-PREVIEW.md)。

当前状态：管理端交互原型已实现；规则管理 API、持久化运行服务、EventBus 规则消费、真实外部投递、真实通知发送和 C 端场景后端尚未交付。

## 2. 产品定位

平台不是给所有用户展示一个“万能规则引擎”。平台提供三类可理解的产品能力：

```text
我想知道设备现在怎么样       → 实时数据
我想让平台自动做某件事       → 场景自动化
我想让我的系统拿到平台数据   → 数据集成
```

通知是被自动化和其他业务复用的独立能力，不与规则计算或外部数据集成混为一个对象。

这四类能力可以共用事件接入、条件计算、权限、版本和运行追踪，但面向用户的入口、配置方式和成功标准不同。

## 3. 用户与待完成任务

### 3.1 C 端终端用户

C 端用户拥有或使用少量设备，目标是获得设备体验，不需要理解租户、消息主题、EventBus 或 SQL。

| 用户任务 | 产品能力 | 用户看到的结果 |
| --- | --- | --- |
| 查看设备现在的状态 | 设备详情实时数据 | 打开页面即可看到最新状态和在线状态 |
| 操作设备 | 属性写入、功能调用 | 能看到受理、设备反馈和失败原因 |
| 配置简单联动 | 场景自动化 | 用“当……就……”完成家庭或个人场景 |
| 知道重要变化 | 通知与消息中心 | 收到提醒，能查看已读和处理状态 |

C 端的规则配置应以模板、物模型和有限选项为主。首版不要求用户编写 SQL，也不让用户配置外部 Kafka 或复杂数据转换。

### 3.2 B 端运营和实施人员

B 端运营人员管理一个组织、项目、门店、园区或客户的设备，目标是减少人工监控和重复交付。

| 用户任务 | 产品能力 | 用户看到的结果 |
| --- | --- | --- |
| 监控大量设备 | Web 实时监控 | 设备列表、状态变化和异常趋势可持续查看 |
| 配置设备联动 | 企业场景自动化 | 一个条件可以作用于设备组、产品或项目 |
| 处理异常 | 通知、运行记录 | 知道是否触发、通知是否成功、设备是否执行 |
| 复用项目方案 | 复制、模板、版本 | 同一套场景可以调整后交付给不同项目 |

B 端配置比 C 端允许更多范围、时间窗口、持续条件、冷却时间、顺序动作和权限控制，但仍然优先使用可视化配置。

### 3.3 B 端开发者和系统集成人员

开发者已有业务 Server 或数据平台，希望平台持续提供设备数据，而不是把业务逻辑全部放在 IoT 平台内。

| 用户任务 | 产品能力 | 用户看到的结果 |
| --- | --- | --- |
| 选取数据范围 | 产品、设备、事件和属性选择 | 只接收自己授权范围内的数据 |
| 筛选和转换 | 条件、字段映射、格式转换、可选 SQL | 外部系统收到可直接消费的数据 |
| 对接系统 | HTTPS、Webhook、Kafka、RocketMQ 等连接 | 一个流转规则可以投递到一个或多个目标 |
| 排查问题 | 测试、运行记录、失败重试 | 能定位未命中、处理失败和目标不可用 |

数据集成优先满足开发者的可控性和可靠性，不强迫平台替开发者实现完整业务流程。

## 4. 产品分层和入口

### 4.1 App 入口

```text
首页 / 设备 / 场景 / 消息 / 我的
```

- **设备**：设备状态、实时数据、操作和历史摘要。
- **场景**：创建、启停和手动执行个人场景。
- **消息**：查看通知、处理状态和历史消息。

App 中的实时订阅是设备页面的内部能力，不单独设计成面向普通用户的“订阅管理”菜单。

### 4.2 Web 管理端入口

```text
设备监控
自动化
  ├── 场景自动化
  └── 数据流转
连接管理
通知管理
运行记录
```

- **设备监控**：服务实时查看和运营观察。
- **场景自动化**：配置“发生什么，就做什么”。
- **数据流转**：配置“哪些数据，处理后交给哪个系统”。
- **连接管理**：维护可复用的外部目标和凭证。
- **通知管理**：维护短信、邮件、App 推送等渠道和模板。
- **运行记录**：查看规则计算、动作执行和外部投递结果。

### 4.3 开发者入口

开发者中心提供 API、SDK、WebSocket/MQTT 实时数据订阅和数据流转配置说明。这里的实时订阅是对外接口能力，不等同于 Web/App 页面订阅，也不替代持久化数据流转。

## 5. 四类能力的产品边界

### 5.1 实时数据

实时数据解决“用户当前想看到什么”。页面或客户端建立连接后，平台按当前身份、租户和资源权限推送状态变化，并在重连后返回最新快照。

产品特征：

- 生命周期通常跟随页面或客户端会话；
- 重点是低延迟和状态收敛；
- 用户离线时通常不要求补发全部历史事件；
- 页面收到数据不代表业务处理成功；
- App 或 Web 断开不能停止后台自动化和数据集成。

### 5.2 场景自动化

场景自动化解决“平台在条件满足时要做什么”。它可以服务 C 端个人场景，也可以服务 B 端项目自动化。

一条场景由以下对象组成：

```text
触发条件 → 可选状态条件 → 动作列表 → 执行记录
```

典型动作包括：

- 控制设备或设备组；
- 调用通知模块；
- 调用外部连接；
- 延时后继续执行；
- 手动一键执行。

场景负责判断和编排动作，不负责实现短信客户端、HTTP 客户端或设备协议。动作由通知、连接和设备领域分别执行并返回结果。

### 5.3 数据集成

数据集成解决“平台持续把数据交给外部系统”。它是一条长期运行的任务，不依赖任何用户是否打开页面。

一条数据流转由以下对象组成：

```text
数据范围 → 条件筛选 → 字段处理 → 一个或多个投递目标 → 投递结果
```

数据范围至少包括租户、产品、设备、消息类型和时间生效范围。范围应参与内部路由，不能让每条规则默认读取全部消息后再过滤。

原样转发是数据流转关闭处理步骤的特例：

```text
选择数据 → 关闭筛选和映射 → 原样发送到目标
```

因此不另外建设一个“消息订阅转发”业务入口。用户配置的是持续投递任务，内部是否使用 EventBus 订阅是平台实现细节。

### 5.4 通知

通知解决“人需要被告知并处理什么”。它独立管理：

- 渠道：短信、邮件、App 推送、企业微信等；
- 模板：标题、正文、变量和多语言内容；
- 接收对象：用户、角色、组织或指定地址；
- 发送任务：受理、发送、送达和失败结果。

场景自动化、设备管理、生产交付和其他业务都可以调用通知模块。Kafka、RocketMQ 和外部 Webhook 属于数据集成目标，不因为发送了一条消息就变成通知。

告警实例管理是可选的独立业务：只有平台需要持续管理“发生、确认、恢复、关闭和处理责任”时才建设告警域。规则首版负责条件、冷却和恢复判断，不把这些判断转移给告警模块。

## 6. 订阅与数据流转的本质区别

两者都可能消费同一条设备消息，但产品契约不同：

| 维度 | 实时订阅 | 数据流转 |
| --- | --- | --- |
| 用户问题 | 我现在想看到什么 | 平台以后要持续处理什么 |
| 使用者 | App/Web 用户或 API 消费者 | 租户管理员、开发者、外部系统 |
| 生命周期 | 会话级或接口连接级 | 长期配置、独立运行 |
| 离线语义 | 重连取快照，未必补齐全部事件 | 继续处理、重试、记录结果 |
| 目标 | 页面、客户端或开发者连接 | HTTPS、Webhook、Kafka、RocketMQ 等系统 |
| 成功标准 | 数据及时到达并可展示 | 规则命中、处理、投递和失败恢复可追踪 |

因此不能按“C 端就是订阅、B 端就是数据流转”划分。C 端也可以配置个人自动化，B 端也可以使用实时监控；订阅和数据流转是数据消费方式，C/B 是用户角色维度。

## 7. 核心产品流程

### 7.1 C 端场景流程

```text
选择设备或设备组
  → 选择触发条件
  → 选择动作
  → 预览并保存
  → 启用场景
  → 查看执行结果和通知
```

### 7.2 B 端场景流程

```text
选择项目／产品／设备范围
  → 配置条件、时间窗口和冷却
  → 编排设备、通知或连接动作
  → 模拟输入
  → 发布版本
  → 启用并查看执行记录
```

### 7.3 数据流转流程

```text
选择产品／设备／消息类型
  → 配置条件和字段映射
  → 选择连接和目标
  → 使用样例测试
  → 发布版本
  → 启用流转
  → 查看每个目标的投递记录和失败重试
```

### 7.4 通知流程

```text
创建渠道
  → 创建模板
  → 配置接收对象
  → 测试预览
  → 被场景或其他业务调用
  → 查看发送和送达结果
```

## 8. 规则表达方式

规则表达按用户能力分层：

### 8.1 普通用户和运营人员：可视化配置

优先支持：

- 事件、属性和设备状态条件；
- 比较、范围、枚举和组合条件；
- 时间段、持续时间和冷却；
- 字段映射、单位换算和固定值；
- 设备控制、通知和连接动作。

### 8.2 开发者：受限高级表达

SQL 或表达式只作为数据集成的高级能力，不是规则引擎的定义，也不是所有用户的必填项。首版只考虑只读、单消息范围内的筛选和输出计算：

- 不允许写入平台数据库；
- 不允许执行任意函数、网络访问或跨租户查询；
- 数据范围必须由平台表单和权限确定；
- 无法安全解析范围时拒绝发布或明确要求扩大范围；
- 表达式错误必须在保存和样例测试阶段给出可定位信息。

是否支持完整 SQL 方言、窗口聚合、跨事件状态和历史查询，待性能、执行器和资源隔离方案确定后再单独立项。

## 9. 运行和结果模型

每条规则都需要经过：

```text
草稿 → 测试 → 发布 → 启用 → 停用／归档
```

产品必须区分：

- 保存成功：配置已经保存；
- 发布成功：版本通过校验；
- 生效成功：运行订阅和配置已准备完成；
- 执行成功：条件命中且动作受理；
- 投递成功：目标系统确认接收；
- 业务成功：设备或外部系统完成实际业务。

每次运行关联确定的规则版本，并能从输入追踪到：

```text
输入消息 → 条件结果 → 输出数据 → 动作 → 投递／设备命令 → 最终结果
```

多目标流转分别记录任务、尝试历史和最终结果。一个目标失败不能导致其他已成功目标被无意重发。

## 10. 与 EventBus 的关系

EventBus 是平台内部事件接入和路由基础，不是让用户配置的外部产品。

目标链路为：

```text
可信设备事件
  → EventBus 按租户／产品／设备／主题范围路由
  → 规则接收与计算
  → 持久化动作待办
  → 设备下行／通知／外部投递
  → 各领域结果记录
```

产品上需要保证：

- 数据流转的产品和设备范围参与内部路由，避免无界全量消费；
- 页面实时订阅和后台长期流转使用不同的生命周期和结果语义；
- 规则停用不能误停其他规则或实时页面订阅；
- 外部系统变慢不能阻塞设备接入和规则接收；
- 规则版本切换、首次启用、积压和重试边界可解释。

Dubbo 发布侧范围匹配、Kafka 消费侧过滤、共享订阅数量和回放语义等实现差异，按[架构约定](architecture.md#规则与集成边界)和 [EventBus 说明](../backend/EVENTBUS.md)执行，不能在产品页面中承诺尚未实现的流量裁剪或历史回放。

## 11. 当前原型与目标产品

| 产品能力 | 当前原型 | 目标交付 |
| --- | --- | --- |
| 实时数据 | 现有设备和 App/Web 实时订阅链路 | 完整权限、快照、重连和订阅协议 |
| 场景自动化 | 条件、时间段、冷却、动作和本地模拟 | 物模型条件、设备动作、持久调度和真实执行 |
| 数据流转 | 产品／设备／消息类型、条件、映射、多目标和本地 JSON 测试 | EventBus 输入、规则版本、持久运行、真实投递和重试 |
| 连接管理 | HTTPS、Kafka、RocketMQ 示例配置 | 凭证托管、连通性测试、配额和连接版本 |
| 通知管理 | 邮件、短信、App 推送模板预览 | 真实渠道、发送任务、送达结果和偏好管理 |
| 运行记录 | 本地样例运行、输出和错误展示 | 规则、动作、投递和设备反馈的统一追踪 |

## 12. 分阶段建设路线

### 阶段 A：统一产品模型和权限

- 明确租户、项目、用户、角色和设备范围；
- 固化规则、版本、连接、通知模板和运行记录对象；
- 将前端原型中的内存状态替换为管理 API；
- 完成草稿、发布、启停和资源引用校验。

验收：不同角色只能看到和操作被授权的资源；刷新页面后配置和版本仍然存在。

### 阶段 B：真实数据流转

- EventBus 按授权范围接入规则；
- 支持原样转发、基础条件和字段映射；
- 交付一个 HTTPS 连接器；
- 保存任务、尝试、失败和重试记录；
- 支持多目标独立结果。

验收：指定产品或设备的真实消息能到达测试 Server；未命中和越权消息不投递；目标故障可恢复并可定位。

### 阶段 C：真实场景自动化和通知

- 支持物模型条件、时间窗口、持续条件和冷却；
- 支持设备控制、通知和一键执行；
- 交付一个真实通知渠道；
- 记录设备受理、反馈和失败。

验收：设备 A 的有效输入能触发设备 B 或通知；重复触发、设备离线、权限撤销和进程重启都有明确结果。

### 阶段 D：开发者数据能力

- Kafka、RocketMQ、Webhook 等连接器；
- 受限 SQL 或表达式；
- 字段映射、格式转换、签名和批量投递；
- API/SDK/WebSocket/MQTT 实时订阅说明和配额。

验收：开发者能在不改动平台代码的情况下配置数据范围、处理方式和目标，并能通过运行记录定位问题。

### 阶段 E：规模化和高级编排

- 共享订阅和规则负载隔离；
- 历史回放、窗口聚合和跨事件状态；
- 规则模板、复制、导入导出和灰度发布；
- 告警实例、确认恢复和升级流程；
- 更丰富的可视化编排。

这些能力在前四阶段的用户任务和可靠性得到验证后再建设，避免先做通用编排器而没有明确业务场景。

## 13. 首版明确不做

- 不把 Web/App 实时订阅做成与数据流转相同的业务对象；
- 不把通知渠道、外部连接和规则计算实现为一个模块；
- 不要求所有用户写 SQL；
- 不承诺完整 SQL、跨事件窗口和任意拖拽编排；
- 不在首版建设完整告警中心、工单和值班升级；
- 不把前端原型的本地模拟当作真实规则执行或可靠投递。

## 14. 产品决策待确认

正式开发前需要在对应需求中补齐：

- C 端用户、家庭和设备授权是否独立于现有租户账号；
- 场景动作失败后是停止、继续还是按动作配置分支；
- 延时动作和规则停用后的待执行任务如何处理；
- 连接配置变更后，已创建任务使用旧版本还是新版本；
- 数据流转是否默认至少一次投递，外部幂等键如何提供；
- 实时订阅是否提供历史补发、事件游标和离线缓存；
- 告警实例何时从规则动作中独立出来。

这些决策会影响产品交互和验收，不能只在实现阶段由中间件默认决定。
