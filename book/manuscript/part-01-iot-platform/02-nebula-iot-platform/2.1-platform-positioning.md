## 2.1 我们要建设什么样的平台

如果一家企业只有一款智能灯，那么很多问题都可以围绕这款产品直接解决。设备怎样接入，状态保存在哪里，用户怎样绑定设备，App 怎样发送控制，都可以写进这款产品自己的后台。

但当产品逐渐增加，情况就会发生变化。

假设企业陆续推出照明、空调、门锁、传感器、摄像头、能源设备和网关，每个产品团队都分别建设设备身份、连接、状态、控制、OTA、权限和运营系统，相似的能力就会被不断重复实现。与此同时，不同产品之间还会逐渐需要协作。用户希望在同一个 App 中管理多个设备，希望传感器能够触发灯光，希望门锁、空调和窗帘共同参与一个自动化场景。

到了这个阶段，问题已经不再只是“怎样给某一款设备做后台”，而是：

**哪些能力应该被抽出来，成为所有产品都可以共同使用的基础？**

星云 IoT Core 就从这里开始。

它不属于某一款具体产品，而是负责解决不同 IoT 产品反复遇到的共同问题，例如设备和产品怎样被识别，设备能力怎样描述，设备怎样接入和认证，状态和事件怎样进入系统，控制怎样下发，权限怎样管理，以及设备怎样被长期运营和维护。

这样，新产品接入时就不需要重新建设一整套后台，而可以在共同的平台能力之上，重点完成自己的硬件功能和产品体验。

### 2.1.1 IoT Core 只是星云产品体系的一部分

现实中的大型 IoT 平台通常并不只提供一套云端后台。

为了让设备厂商更容易接入，它可能提供 Device SDK、Gateway SDK、调试工具和生产工具；为了让应用开发者更方便地使用平台，可能提供 App SDK、Web SDK、开发者控制台甚至快速生成 App 的工具；为了支持实际业务，还可能提供运营后台和面向学校、医院、办公等场景的行业解决方案。

因此，“IoT 平台”这个词有时指底层的核心平台，有时又被用来指围绕它形成的整套产品和服务。

在本书中，我们把两者区分开。

**星云 IoT Core** 是其中最基础、最稳定的一层。它负责跨产品、跨场景复用的 IoT 能力。

围绕 Core，还可以形成设备开发工具、应用开发产品、运营工具和行业解决方案。这些都可以属于星云产品体系，但并不意味着它们都应该进入 Core。

可以把它们之间的关系简单理解为：

```text
设备与边缘开发工具
        ↓
   星云 IoT Core
        ↑
应用开发与运营产品
        ↑
   行业解决方案
```

这个图只是表达责任关系，并不是说所有产品都只能位于某一侧。真正重要的是：Core 提供稳定的共同能力，外围产品负责让不同角色更容易使用这些能力。

因此，本书不会尝试完整设计星云体系中的每一种产品。

后面的主线始终是 **星云 IoT Core**。Device SDK、App SDK、运营后台和行业解决方案会在需要时出现，用来帮助我们判断 Core 应该提供什么能力、接口是否合理，以及平台是否能够支撑真实业务，但不会逐一深入实现。

可以把本书的范围概括成一句话：

**深入设计 Core，理解外围产品，验证行业方案。**

### 2.1.2 星云要支撑的不只是自己的设备

星云首先服务企业自己的产品线。

照明、空调、门锁、摄像头和传感器可以共享同一套设备身份、连接、模型、状态、权限和运维能力。平台越成熟，新产品越不应该从头建设后台。

但如果星云只能接入企业自己的设备，它仍然只是一个内部平台。

我们希望它还能够向外开放。

第三方设备厂商可以按照平台约定接入设备，开发者可以通过 API 和 SDK 使用经过授权的设备能力，合作伙伴和行业应用也可以建立在同一套 Core 之上。

这意味着平台不能只按照某一款内部产品的实现方式设计。

一旦能力开始被外部使用，产品模型、接口、权限和生命周期就需要更加稳定。内部团队的一次代码调整，不能轻易破坏外部设备和应用。

从这个意义上说，开放平台真正增加的并不只是几个 API，而是长期维持一套协作规则的责任。

### 2.1.3 同一套 Core 还要能够支撑不同业务场景

星云也不会只面向消费产品。

同样的设备能力还可能进入智慧办公、智慧学校、智慧医院、园区和楼宇等 B 端场景。

这些场景会使用大量相同的 IoT 能力，但业务本身并不相同。

家庭关心成员和房间，学校关心校区、教学楼和教室，医院关心院区、病区和病房。平台需要能够表达设备属于谁、安装在哪里、谁可以访问，却不应该因为进入某个行业，就把该行业所有业务概念都写进核心。

例如，Core 可以提供组织、空间、用户、资源和权限等通用能力。至于某个空间究竟代表卧室、教室还是病房，则由上层应用决定。

因此，星云需要坚持一个基本原则：

**平台沉淀跨产品、跨场景可以复用的能力，具体业务留给上层产品和行业应用。**

只有这样，同一套 Core 才可能同时支撑消费产品和企业项目，而不必为每个行业重新建设一套底层平台。

### 2.1.4 星云还必须能够适应不同的设备和部署环境

IoT 世界里的设备并不都是“直接连接云端的智能终端”。

有些设备通过 Wi-Fi 或蜂窝网络直接接入平台，有些设备需要经过蓝牙、Zigbee 或其他协议连接到网关，还有一些现场会部署边缘节点，在本地完成设备接入和部分自动化。

同样，平台本身也不一定永远运行在同一种环境中。

面向消费产品时，企业可能统一运营一套云平台；进入 B 端项目后，有些客户会继续使用 SaaS，有些可能要求独立实例、私有化部署或者本地边缘能力。

因此，星云从一开始就不能把自己限定为“某一种设备 + 某一种网络 + 某一种云部署方式”。

它需要面对一个更加多样的设备世界，也需要允许同一套核心能力在不同规模和环境中运行。

具体怎样处理网关、边缘、SaaS 和私有化，我们会在后面的章节继续展开。此时只需要先确定一个方向：

**Core 的逻辑能力应该尽可能稳定，而设备形态、连接方式和部署方式可以变化。**

### 2.1.5 本书要设计的星云 IoT Core

综合前面的要求，星云 IoT Core 并不是某一款设备的后台，也不是单纯的消息接入服务。

我们希望它是一套能够长期支撑多产品、多组织、多场景和开放生态的 IoT 基础平台。

它需要统一管理设备以及设备与产品、用户、组织、空间、应用和其他系统之间的关系，并把这些能力稳定地提供给上层产品和外围工具。

因此，本书后面对星云的设计，可以先用一句话概括：

**星云 IoT Core 是一套面向多产品、多组织、多场景和长期运行的通用 IoT 基础平台，它统一表示、连接、管理和运营设备及其核心关系，并向设备端、应用端和生态伙伴提供稳定的基础能力。**

这一定义先回答了“我们要建设什么”。

下一步，读者不需要继续听更多抽象定义。

我们可以直接把星云 IoT Core 摊开来看一看：它整体上由哪些部分组成，这些部分之间怎样协作。
