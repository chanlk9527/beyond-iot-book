## 2.2 星云 IoT Core 的整体架构

上一节确定了星云 IoT Core 的定位。接下来先不急着讨论 MQTT、数据库、消息队列或者微服务，而是把整个平台摊开来看。

从最粗的层次上说，一个 IoT 平台连接的是两个世界。

一边是真实世界中的设备。灯、空调、门锁、传感器、摄像头和各种控制器持续产生状态和事件，也等待来自系统的控制、配置和升级。

另一边是使用这些设备能力的软件。消费者 App、运营后台、行业应用和第三方系统，并不希望分别理解每一种设备的通信协议，而是希望通过相对统一的方式知道：这是什么设备，它现在怎样，它能够做什么，以及自己是否有权操作它。

星云 IoT Core 位于两者之间。

它向下面对复杂多样的设备和网络，向上提供相对稳定的平台能力。在中间，它需要理解设备是谁、能够做什么、怎样连接、当前处于什么状态，以及设备与用户、组织和应用之间存在什么关系。

可以先用一张简化的图理解整个 Core 的位置。

```text
┌──────────────────────────────────────────────┐
│                 上层产品与系统                │
│                                              │
│  消费者 App   运营后台   行业应用   第三方系统 │
└──────────────────────┬───────────────────────┘
                       │
                  API / Event
                       │
                       ▼
┌──────────────────────────────────────────────┐
│                星云 IoT Core                  │
│                                              │
│  产品与设备         用户、组织与权限          │
│  设备模型           状态与设备数据            │
│  接入与连接         自动化与规则              │
│  消息与控制         OTA 与生命周期            │
│  网关与拓扑         运维、诊断与开放能力      │
└──────────────────────┬───────────────────────┘
                       │
                       ▼
┌──────────────────────────────────────────────┐
│                 设备与边缘世界                │
│                                              │
│  直连设备    网关    子设备    边缘节点        │
└──────────────────────────────────────────────┘
```

这张图首先是一张**逻辑架构图**。它描述的是平台需要承担哪些责任，而不是规定以后一定要部署多少个服务。

例如，“设备管理”和“OTA”可以是两类不同的逻辑能力，但在一个小型私有化版本中，它们完全可能运行在同一个应用进程里；在大规模 SaaS 环境中，又可能被拆成多个独立服务和集群。

因此，现在先不要把图中的每个方框直接理解成一个微服务。

第二章的目标是先把地图画清楚，至于地图中的每一块最终怎样实现，后面再逐步展开。

### 2.2.1 从设备世界进入平台

星云首先面对的是各种真实设备。

最简单的情况是一台设备直接通过 Wi-Fi、以太网或者蜂窝网络连接云端。例如，一只智能插座完成认证以后，可以持续向平台报告开关状态，并接收用户的远程控制。

但现实中的 IoT 设备远比这复杂。

一只 Zigbee 传感器可能无法直接访问互联网，需要通过网关连接平台；一栋楼里的现场设备可能先连接边缘服务器，再由边缘节点与中心平台交换信息；有些设备还需要在本地完成控制和自动化，即使互联网暂时中断也不能停止工作。

因此，星云面对的不能只是一种“云端直连设备”。

它需要同时理解直连设备、网关、网关之后的子设备以及边缘节点，并逐渐把不同连接方式转换成平台能够理解的统一设备语义。

例如，对上层 App 来说，一只温度传感器究竟是通过 Wi-Fi 直连，还是通过 Zigbee 网关接入，通常不应该改变读取温度的基本方式。

底层连接可以不同，但平台最终都希望表达成类似这样的事实：

> 某台设备当前报告温度为 26.3℃。

这就是 Core 在设备侧承担的第一项重要责任：**吸收底层连接差异，向上提供稳定的设备身份和能力表达。**

设备真正进入平台时，首先经过的是接入和连接能力。平台需要识别连接来自哪台设备，验证它提供的凭证，并建立相应的通信关系。

连接建立以后，设备会不断发送消息。消息可能表示温度、电量和开关状态，也可能表示告警、日志、命令回复或者升级进度。

接入层解决的是“怎样把信息送进来”，但收到信息以后，平台还需要继续回答“这条信息是什么意思”。

这就进入了 Core 的下一层。

### 2.2.2 平台需要从“收到消息”走向“理解设备”

如果一个系统只能收发 MQTT 消息，它还不能算完整的 IoT 平台。

假设平台收到这样一段数据：

```text
{"dp": 3, "value": 263}
```

仅仅收到它，并不能知道 `3` 是什么意思，也不知道 `263` 应该解释成 263、26.3℃，还是另一个完全不同的值。

平台必须知道这条消息来自什么产品，这类设备具有什么能力，以及消息字段遵循什么约定。

因此，星云需要产品、设备和设备模型。

这里先建立几个最基本的概念。

**产品定义**描述一类设备共享的能力和约定。例如，“晴川调光灯 V2”支持开关、亮度和色温调节。

**设备**则表示现实中的某一个具体实例。例如，用户客厅里安装的那一盏灯。

同一个产品定义下面可以有成千上万台设备。它们拥有相同的能力定义，却拥有各自独立的状态、版本、位置和生命周期。

**设备模型**进一步描述这些能力如何被平台理解，例如设备能够报告哪些状态，会产生哪些事件，可以接受哪些操作。

有了这些信息以后，平台看到的就不再只是主题、字段和 JSON，而可以进一步理解成：

> 设备 A 报告当前温度为 26.3℃。

或者：

> 设备 B 支持亮度调节，合法范围是 1～100。

设备模型因此处在整个 Core 非常关键的位置。

上层 App 需要它来知道设备能做什么，控制服务需要它来校验参数，自动化规则也需要它来理解某个状态和事件代表什么。

从这个角度看，IoT Core 并不是简单地“转发设备消息”，而是在逐步建立一套能够理解设备世界的共同语言。

### 2.2.3 状态和控制构成平台最基本的双向链路

设备进入平台以后，最常见的行为大致可以分成两个方向。

一个方向从设备流向平台。

设备把现实世界发生的事情告诉系统，例如当前温度、开关状态、电池电量、门锁是否打开。星云接收这些信息以后，可以更新设备当前状态，也可以把其中一部分保存为历史数据或者事件，再提供给 App 和业务系统使用。

另一个方向则从应用流向设备。

用户在 App 中点击“开灯”，行业系统修改空调目标温度，或者自动化规则触发某项动作，都会产生一个控制请求。

平台需要判断这个请求来自谁、是否拥有权限、目标设备当前怎样连接，再把命令送到正确的位置，并继续处理设备返回的执行结果。

因此，可以用一句很简单的话理解 IoT Core 最基本的双向关系：

**设备告诉平台发生了什么，平台又通过设备影响现实世界。**

围绕这两个方向，平台还会逐渐形成状态管理、设备数据、控制、事件和自动化等能力。

例如，人体传感器报告“检测到运动”以后，一条自动化规则可以产生“打开灯”的控制请求；温度超过某个阈值时，可以触发告警或者调用另一个业务系统。

这些能力看起来不同，但都建立在相同的基础上：平台已经知道设备是谁、它的消息是什么意思，以及如何对它执行操作。

### 2.2.4 平台不仅要理解设备，还要理解设备与谁有关

IoT 设备不会孤立运行。

一盏灯可能属于某个家庭，安装在客厅；一只传感器可能属于某所学校，安装在三楼教室；一台工业设备可能由某个项目团队负责维护，同时还允许另一个业务系统读取运行数据。

所以，星云不能只管理设备本身，还需要理解设备与用户、组织、空间和应用之间的关系。

这里也只需要先建立一组基本语言，不必在第二章把所有模型设计展开。

可以暂时这样理解：

| 对象 | 在当前阶段可以怎样理解 |
| --- | --- |
| 产品定义 | 一类设备共享的能力和约定 |
| 设备 | 现实中某一个具体的设备实例 |
| 用户 | 平台中的人 |
| 应用 | 使用平台能力的软件或外部系统 |
| 租户 | 一组资源和数据的隔离边界 |
| 组织 | 谁在管理相关资源 |
| 空间 | 设备安装或作用在哪里 |
| 连接 | 设备当前通过什么路径与平台通信 |

这些概念以后都会继续展开。

例如，“用户”和“账号”是不是一回事，“租户”和企业组织是什么关系，“设备”和连接为什么要分开，“空间”和组织为什么不能合并，这些问题都值得深入讨论，但不是这一节的任务。

现在只需要知道：平台管理的不是一张孤立的设备清单，而是设备与这些对象形成的关系。

这些关系也会进入权限判断。

消费者可能只能访问自己家庭中的设备，学校教师可以查看教室环境，却没有权修改设备固件；某个第三方应用则可能只被允许读取一类传感器数据。

所以，用户、组织、空间和权限虽然在架构图中看起来只是其中一块，实际上会横向影响设备查询、控制、配置、数据访问和开放 API。

### 2.2.5 IoT Core 还要面对设备的长期运行

如果只看到“设备连接—状态上报—远程控制”，很容易把 IoT 平台理解成一个实时消息系统。

但真正交付到用户手里的设备往往会运行很多年。

固件会升级，配置会改变，网络会发生变化，设备会转移，也可能损坏、维修或者最终退役。设备规模扩大以后，运营人员还需要知道哪些设备长期离线、某个固件版本有多少设备、一次升级成功了多少，以及某个型号最近是否突然出现大量故障。

因此，星云 IoT Core 还需要承担设备长期运营的能力。

OTA、配置、批量任务、日志、指标、告警、诊断和生命周期管理，都属于这一部分。

这也是“设备能够连接平台”和“设备能够被长期运营”之间的区别。

前者关心连接是否建立、消息是否能够传递；后者还需要知道设备运行得怎么样，出了问题能否定位，软件能否安全升级，以及设备最终退出系统以后应该怎样处理。

对于真实 IoT 产品而言，后者往往比第一次成功连接设备更加困难。

### 2.2.6 Core 向上提供稳定能力，而不是直接承担所有业务

星云 IoT Core 的另一端，是各种上层产品。

普通消费者使用的是品牌 App，运营人员使用的是设备管理后台，企业客户面对的可能是智慧学校或智慧楼宇系统，第三方开发者则可能直接使用 API。

它们对平台的需求并不相同。

消费者 App 关心用户自己的设备和空间；运营后台更关心设备查询、OTA 和故障诊断；行业应用会在设备能力之上继续组织自己的业务；第三方系统则需要稳定的开放接口和事件订阅。

Core 的任务不是替这些应用完成所有业务，而是为它们提供共同基础。

例如，星云可以告诉智慧学校系统：

> 301 教室中的人体传感器刚刚报告“无人”。

至于学校系统是否应该立即关闭灯光，是否要考虑课程表、考试安排或者值班规则，则属于行业业务。

同样，摄像头可以作为设备由星云管理身份、状态、权限和 OTA，但实时视频传输、录像、转码和回放可以由专业媒体系统承担；企业员工可以通过星云权限访问设备，但员工身份本身可以来自企业已有的 SSO；设备数据也可以从星云继续流向数据仓库和分析系统。

所以，Core 位于整个体系的中央，却不意味着所有能力都必须被它吸收。

Device SDK、App SDK、运营后台和行业解决方案可以属于完整的星云产品体系；IAM、视频、数据平台和 ITSM 等专业系统也可以与星云紧密协作。

Core 真正需要长期保持稳定的是那一组跨产品、跨应用反复出现的 IoT 基础责任。

### 2.2.7 这张图还不是最终部署方式

现在看到的星云仍然是一张逻辑架构图。

它告诉我们平台需要处理设备接入、模型、状态、权限、生命周期和开放能力，却没有规定这些能力具体运行在哪些服务器中。

这一区分非常重要。

“设备接入”是一项逻辑能力，不意味着它必须对应一个独立微服务；“状态管理”也不代表一定要有一个名为 `device-state-service` 的进程。

在一个小型私有化项目中，多项能力可以合并部署，以降低资源和运维成本。在大规模 SaaS 环境中，同样的能力又可能按照负载特点拆成多个服务和集群。

类似地，MQTT Broker、数据库、缓存和消息队列以后都会出现在部署架构中，但它们首先是实现平台能力所使用的技术组件，并不是平台逻辑架构本身。

因此，现阶段更重要的是先把责任关系建立起来。

我们需要先知道谁负责理解设备，谁负责连接，谁负责状态和控制，谁负责权限和生命周期，再去讨论这些责任应该由哪些服务、数据库和中间件来承担。

先有逻辑架构，再做物理架构，能够避免过早让技术选型反过来定义平台。

### 2.2.8 先有一张地图，再看它怎样运行

到这里，星云 IoT Core 已经有了一张足够使用的总体地图。

向下，它连接直连设备、网关、子设备和边缘节点；向上，它服务 App、运营后台、行业应用和第三方系统；在内部，则围绕产品、设备、模型、连接、状态、控制、权限、自动化、生命周期和运维组织共同能力。

后面的章节会不断放大这张图中的不同区域。

我们会讨论设备怎样获得身份，怎样证明自己，模型怎样描述设备能力，连接怎样建立和恢复，状态怎样保存，控制怎样确认，OTA 怎样执行，以及用户、组织和设备之间怎样建立权限关系。

但在第二章，现在还不需要把这些问题全部展开。

与其继续增加概念，不如先让这张架构真正运行起来。

下一节，我们只选择两条最常见的路径：**设备上报**和**远程控制**。通过一条数据怎样从设备走到应用，以及一次点击怎样从 App 最终到达真实设备，可以更直观地看清刚刚这些能力之间究竟怎样协作。
