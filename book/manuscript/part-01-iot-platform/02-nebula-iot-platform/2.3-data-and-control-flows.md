## 2.3 两条链路看懂平台怎样工作

上一节我们已经看到了星云 IoT Core 的整体架构，但那张图仍然是静态的。

真正理解一个平台，不能只看它由哪些部分组成，还要看一条真实请求经过平台时，这些能力怎样一起工作。

对于 IoT 平台来说，最典型的两个方向分别是：**设备把现实世界的状态告诉平台，以及平台把应用的意图传递给设备。**

前者可以叫作设备上报，后者可以叫作远程控制。

这两条链路方向相反，却几乎会经过整个 IoT Core。把它们走一遍，前面看到的设备、模型、连接、状态、权限和应用就不再只是架构图上的几个方框，而会开始真正联系起来。

### 2.3.1 一条温度数据怎样从设备走到 App

假设教室里安装了一只温度传感器。

某一时刻，它测得当前温度为 26.3℃，并把这个结果发送给星云。

表面上看，这件事似乎非常简单：

> 设备上报温度，App 显示温度。

但中间实际上需要完成一连串工作。

首先，设备必须能够到达平台。

如果这是一只 Wi-Fi 传感器，它可能直接通过互联网连接星云；如果使用 Zigbee，它可能先把数据发送给网关，再由网关转发到平台。

无论底层采用哪种方式，平台首先要解决的都不是“温度是多少”，而是：

**这条消息是谁发来的？**

连接建立时，星云需要确认设备身份，并验证它使用的凭证是否合法。否则，任何能够连接服务器的客户端都可能冒充真实设备发送数据。

确认身份以后，平台收到的仍然可能只是一段协议数据。

例如底层消息可能类似：

```text id="lw8yyw"
{"dp":3,"value":263}
```

对网络层来说，这条消息已经成功送达。

但对业务来说，它几乎还没有意义。

平台还需要知道：`dp=3` 表示温度，`263` 应该按照十分之一摄氏度解释，因此真正的含义是：

> 设备 A 当前温度为 26.3℃。

这一步依赖设备所属的产品以及相应的设备模型。

于是，一条原本只具有协议意义的数据，开始变成平台能够理解的设备语义。

接下来，星云可能会更新设备的当前状态。

如果 App 此时打开设备页面，它需要知道“现在温度是多少”，通常不应该重新等待设备发送一次，而是可以直接读取平台已经保存的最新状态。

与此同时，这条温度数据还可能被保存为历史记录，用于绘制过去一天的温度曲线。

如果平台存在自动化规则，它还可能继续参与判断。例如：

> 当温度超过 30℃时产生高温告警。

或者：

> 当室内温度过高时自动开启空调。

上层行业系统也可能订阅这个变化。智慧学校系统收到温度更新以后，可以刷新教室环境页面，或者把数据进一步送往自己的分析系统。

于是，一次看似简单的温度上报，实际上经过了这样一条路径：

```text id="cytmdc"
温度传感器
    ↓
设备连接 / 网关
    ↓
身份识别与认证
    ↓
消息接收
    ↓
产品与设备模型解释
    ↓
设备当前状态
    ↓
历史数据 / 事件 / 自动化
    ↓
App 或其他业务系统
```

这条链路说明了一个非常重要的区别：

**平台“收到了一条消息”，和平台“知道设备发生了什么”，不是一回事。**

前者属于通信，后者才真正进入设备管理和业务语义。

一个 MQTT Broker 可以帮助我们把消息送进服务器，但如果没有设备身份、产品模型、状态和数据能力，上层应用看到的仍然只是一堆难以直接使用的原始消息。

这也是 IoT Core 存在的一个重要原因：它把底层设备通信逐渐转换成上层应用能够稳定使用的设备能力。

### 2.3.2 一次“开灯”怎样从 App 到达设备

再看相反方向。

用户打开 App，看到了客厅中的一盏智能灯，然后点击“打开”。

从用户角度看，只发生了一次点击。

但站在平台内部，这实际上是一次从数字世界影响现实世界的过程。

首先，App 向星云发送一个控制请求。

这个请求至少需要说明：

> 谁正在操作；

> 想操作哪台设备；

> 希望设备做什么。

平台第一步并不是立即向设备发消息，而是先确认请求是否合法。

星云需要知道当前用户是谁，也需要判断这个用户是否有权控制这盏灯。

如果这是用户自己家庭中的设备，权限可能来自家庭成员关系；如果设备位于企业中，则可能来自组织、角色和空间权限；如果请求由第三方应用发起，则还要检查这个应用是否获得了相应授权。

只有通过权限判断以后，这个控制请求才有资格继续向设备侧流动。

接下来，平台还需要确认：

**这台设备是否支持“打开”这个操作？**

对于灯来说答案显然通常是肯定的，但平台不能靠猜。

设备模型中应该已经定义了这类设备支持哪些状态和操作，因此 Core 可以检查请求是否符合设备能力，参数是否合法。

然后，平台需要找到设备。

如果设备直接连接星云，控制消息可以沿着它当前的连接发送；如果设备位于网关之后，平台可能需要先找到网关，再由网关把消息转发给子设备。

这一步说明，设备身份和设备连接并不是同一个概念。

应用只需要指定：

> 控制设备 A。

至于设备 A 此刻通过哪条连接、哪个网关、哪台边缘节点可以到达，应该由平台负责解决。

最终，命令到达真实设备。

设备执行开灯动作以后，事情却还没有完全结束。

它可能返回一条执行结果，也可能随后重新上报自己的状态：

> `power = on`

星云收到这些信息以后，可以更新设备状态，再把新的状态传递给 App。

于是，用户看到灯已经打开。

整条路径大致如下：

```text id="gd2c0r"
用户点击“开灯”
        ↓
       App
        ↓
     星云 API
        ↓
用户身份与权限判断
        ↓
设备与模型校验
        ↓
查找设备当前连接路径
        ↓
控制消息下发
        ↓
设备 / 网关
        ↓
真实设备执行
        ↓
执行结果 / 状态上报
        ↓
状态更新
        ↓
       App
```

这条链路比“向 MQTT Topic 发一条消息”复杂得多。

平台至少需要依次回答几个问题：

> 你是谁？

> 你有没有权操作这台设备？

> 这台设备是否支持这个操作？

> 设备现在从哪里可以到达？

> 控制请求有没有送出去？

> 设备是否真的执行了？

> 最终状态是什么？

这些问题以后会分别进入身份、权限、模型、连接、消息、状态和控制等章节。

此时还不需要解决它们，只需要先看到这些问题确实存在。

### 2.3.3 “发送成功”和“设备执行成功”并不是一回事

远程控制还暴露了 IoT 系统中一个很容易被忽略的问题。

假设 App 请求开灯，平台成功把消息交给 MQTT Broker。

这能不能说明灯已经打开？

不能。

它只能说明控制链路向前推进了一步。

即使 Broker 成功把消息发送给设备连接，也只能说明消息可能已经到达设备，仍然不能直接证明真实硬件完成了动作。

设备可能收到命令以后执行失败，也可能已经执行成功，但返回结果在网络中丢失。

因此，在一个完整控制过程中可能存在多个不同阶段：

> 平台接受了请求；

> 消息成功进入下发通道；

> 设备收到命令；

> 设备完成执行；

> 平台收到执行结果；

> 平台观察到最终状态。

这些阶段不能简单地用一个“成功”全部代替。

同样的问题也存在于设备上报中。

平台收到一条温度消息以后，可以确认“收到了一次上报”，但不能仅凭这一点保证设备之后仍然在线，也不能保证这条数据一定代表此刻最新的物理状态。

这些看起来像细节，其实是 IoT 和普通 Web 请求非常不同的地方。

网络可能不稳定，设备可能离线，消息存在延迟，现实世界中的动作也需要时间。

因此，平台不能假设一次 API 调用等同于现实世界中的动作已经同步完成。

后面讨论控制和状态时，我们会专门处理这些问题。

### 2.3.4 设备离线以后会发生什么

再考虑一个很常见的情况。

用户点击“开灯”时，设备正好离线。

这时候平台应该怎么办？

最简单的做法是立即返回失败。

但有些场景可能希望等待设备重新上线以后再执行；另一些控制具有明显时效性，例如“现在打开门锁”，如果设备十分钟后才上线，这个请求显然不应该继续执行。

类似地，一台设备离线并不意味着它在现实世界中停止工作。

灯可能仍然亮着，空调仍然在运行，网关中的本地自动化也可能继续执行。

只是云端暂时无法观察到它的最新状态。

于是又出现几个问题：

> 平台显示的状态究竟有多新？

> 设备离线时是否还能接受控制意图？

> 控制请求需要保存多久？

> 设备重新上线以后如何恢复状态？

> 本地状态和云端状态发生冲突时以谁为准？

这些问题都非常重要，但现在还不是展开它们的时候。

在第二章，我们只需要从两条链路中看到：**IoT 平台处理的不是理想网络中的同步函数调用，而是一个包含设备、网络和现实世界的不确定系统。**

后面的很多架构设计，正是为了管理这种不确定性。

### 2.3.5 两条链路背后，其实是同一组平台能力

现在把设备上报和远程控制放在一起看，会发现它们虽然方向相反，却依赖同一组基础能力。

设备上报需要知道设备身份，需要通过连接接收消息，需要使用设备模型解释数据，再把结果写入状态或交给其他系统。

远程控制同样需要设备身份和模型，只不过还要从用户或应用开始经过权限判断，再找到设备当前的连接路径，把请求送回真实设备。

可以把两条链路放在一起：

```text id="ndfbcc"
现实世界
   │
   │  状态 / 事件
   ▼
 设备
   │
   ▼
连接与消息
   │
   ▼
身份与模型
   │
   ▼
状态 / 数据 / 自动化
   │
   ▼
应用与用户
   │
   │  控制意图
   ▼
权限与模型
   │
   ▼
连接与消息
   │
   ▼
 设备
   │
   ▼
现实世界
```

这也是理解整个星云 IoT Core 最简单的方式之一。

它一直在处理两个方向：

**把现实世界发生的事情可靠地带到数字世界；**

以及

**把数字世界中的意图安全地作用回现实世界。**

在这两个方向之间，设备身份、模型、连接、状态、权限和生命周期共同提供基础支撑。

前面的整体架构因此不再只是静态模块，而开始形成一个完整系统。

接下来，我们还需要面对另一个现实问题。

同样一套逻辑能力，可能运行在平台方统一运营的大规模 SaaS 中，也可能被部署到某家医院自己的数据中心，甚至还可能有一部分运行在现场边缘节点。

那么，同一个星云 IoT Core，应该怎样适应这些不同环境？

下一节，我们就从逻辑架构转向部署架构。
