## 2.4 同一套平台怎样运行在不同环境

前面两节讨论的星云 IoT Core，主要是一套逻辑架构。

无论设备通过什么网络接入，无论用户从 App 还是行业系统发起控制，平台都需要处理设备身份、模型、连接、状态、权限和生命周期。这些责任不会因为服务器部署在哪里而消失。

但真正落地以后，星云并不会永远运行在同一种环境中。

面向消费产品时，最自然的方式通常是由平台运营方统一建设一套云平台。所有用户和设备连接同一套服务，产品团队只需要使用平台提供的能力。

进入企业市场以后，情况就会复杂得多。

有些客户可以继续使用 SaaS；有些客户希望获得独立运行环境；还有一些客户要求平台部署到自己的云账号、数据中心甚至完全隔离的网络中。与此同时，部分设备能力还可能需要运行在现场边缘节点上。

因此，我们需要区分两个经常被混在一起的问题：

**平台在逻辑上由哪些能力组成，以及这些能力在物理上运行在哪里。**

前者是逻辑架构，后者是部署架构。

### 2.4.1 最常见的形态：统一运营的 SaaS

对于面向大量消费者或中小企业的产品，SaaS 往往是最直接的方式。

星云由平台方统一建设和运营，不同客户共同使用一套基础设施。平台负责服务器、数据库、消息系统、版本升级、监控和故障处理，客户则直接使用设备接入、管理和开放接口。

这种方式最大的特点是**集中运营**。

平台发布一个新版本，可以统一升级；安全漏洞可以由平台方集中修复；基础设施扩容也可以根据整体设备规模进行规划。

但多个客户共享平台以后，星云必须能够清楚地区分彼此的数据和资源。

例如，企业 A 和企业 B 可以使用同一套设备管理服务和数据库集群，却不能看到对方的设备，也不能使用对方的应用凭证。

这正是租户概念的重要来源之一。

在 SaaS 中，租户不仅是业务上的一个名称，还承担着资源和数据隔离的责任。很多查询、权限判断和开放接口最终都需要回答：

> 当前操作属于哪个租户？

随着规模扩大，还可能进一步出现容量隔离、流量限制和资源配额等问题。

因此，多租户并不是简单给数据库表增加一个 `tenantId` 就结束了。它会逐渐影响平台中大量能力。

但这些细节不需要在这里展开。当前只需要知道：**SaaS 的核心特征，是很多客户共享同一套由平台方统一运营的 Core。**

### 2.4.2 有些客户希望拥有自己的平台实例

共享 SaaS 并不适合所有客户。

一家大型企业可能希望自己的平台资源与其他客户完全分开，也可能对数据库、网络和安全策略有特殊要求。

这时候，可以为客户提供独立实例。

从使用方式看，它仍然可能由星云团队运营，但运行环境已经不再与普通 SaaS 租户完全共享。

再进一步，客户可能要求平台部署在自己的公有云账号中。

此时计算资源、数据库和网络都属于客户，但运行的软件仍然是星云 IoT Core。

还有一些场景会进一步要求**私有化部署**。

例如，客户希望设备数据不离开自己的数据中心，或者现场网络本身无法自由访问互联网。星云就需要被安装到客户自己的服务器、虚拟机或者内部云环境中。

从平台逻辑上看，这几种方式并没有改变核心问题。

设备仍然需要注册和认证，状态仍然需要管理，控制仍然需要经过权限判断，OTA 和运维也仍然存在。

变化的是这些能力实际运行在哪里，以及由谁负责维护。

因此，我们不希望出现这样的情况：

> SaaS 是一套平台，私有化又重新开发另一套平台。

如果两边的核心模型、API 和行为长期分裂，研发成本会迅速增加。一个功能需要分别开发两次，一个安全问题需要分别修复，客户之间也很难共享生态和工具。

更理想的目标是：

**SaaS、专属实例和私有化部署共享同一套核心模型和主要能力，只在基础设施、规模和运维方式上有所不同。**

### 2.4.3 不同规模，不应该使用完全相同的部署方式

共享同一套 Core，并不意味着所有环境都必须按照同一种方式部署。

这是一个很容易犯的错误。

假设星云的公有 SaaS 已经管理数千万台设备。为了支撑这样的规模，接入服务、消息处理、数据库和规则引擎可能都需要集群化，并根据负载独立扩容。

如果把这一整套架构原封不动地交付给一所只有两千台设备的学校，不仅浪费资源，还会给客户带来很高的安装和运维成本。

反过来，也不能因为小型私有化版本只需要几个进程，就认为大型 SaaS 也可以永远使用同样的单体部署。

因此，星云需要允许：

**逻辑上相同的能力，在不同规模下采用不同的物理组合。**

例如，在大型 SaaS 中可能是：

```text id="x9wr0h"
设备接入集群
    ↓
消息处理集群
    ↓
设备与状态服务
    ↓
数据库 / 缓存 / 消息系统
```

而一个小型私有化版本完全可能是：

```text id="akp8gs"
星云 Core
├── 设备接入
├── 设备管理
├── 状态与控制
├── 权限
└── OTA

+ 数据库
+ MQTT Broker
```

前者可能部署几十甚至几百个实例，后者也许几台服务器就能够运行。

它们在物理形态上差别很大，但从上层应用看来，创建产品、注册设备、查询状态和执行控制的基本模型不应该因此完全改变。

这就是为什么第二章一直强调：

**不要过早把逻辑模块等同于微服务。**

模块首先表示责任边界，是否独立部署则要根据规模和运行环境决定。

### 2.4.4 有些能力还需要运行在边缘

云端部署并不是 IoT 的全部。

想象一栋智能办公楼。

楼里的灯、空调和传感器都接入星云。如果每一次人体感应开灯都必须先把消息发送到几百公里外的数据中心，再等待云端规则计算后返回控制，虽然技术上可以实现，却未必是最合理的方案。

一旦外网中断，这些自动化甚至可能全部失效。

因此，一部分能力需要离设备更近。

现场可以部署星云的边缘节点，承担设备接入、协议转换、本地状态和部分自动化。即使与中心云之间暂时失去连接，必要的本地功能仍然可以继续运行；网络恢复以后，再与云端同步状态和数据。

这时候，星云的整体形态就不再只是：

```text id="hr7b9c"
设备 → 云
```

而可能变成：

```text id="4qdvmd"
设备
  ↓
网关 / 边缘节点
  ↓
星云云端 Core
  ↓
应用与业务系统
```

更重要的是，边缘节点不应该变成另一套完全独立的 IoT 平台。

如果云端和边缘各自拥有不同的设备身份、模型和规则体系，系统会很快陷入同步困难。

更合理的方向是让两者共享一套核心语义。

例如，同一台设备在云端和边缘仍然使用同一个平台身份；同一个产品模型可以被下发到边缘，用于解释设备数据；某些自动化规则也可以根据需要从云端部署到现场执行。

因此，云边协同真正困难的地方并不是“再安装一个服务器”，而是：

**哪些能力应该留在中心，哪些能力可以下沉，以及两边怎样保持一致。**

这部分后面还会专门展开。

### 2.4.5 私有化真正困难的是长期交付，而不是把软件装进去

当平台开始支持私有化以后，还有一个容易被低估的问题。

很多人会把私有化理解成：

> 把 Docker 镜像交给客户，然后安装起来。

真正运行几年以后，会发现困难远不止如此。

客户的操作系统版本可能不同，网络环境不同，数据库版本不同，也可能无法访问公共互联网。平台发布新版本以后，几十个甚至几百个私有化客户不可能像 SaaS 一样在同一天自动完成升级。

于是会出现版本并存。

客户 A 可能仍然使用 3.2，客户 B 已经升级到 3.5，另一个客户由于项目原因长期停留在更早版本。

平台团队需要考虑：

旧版本还能支持多久；

数据库怎样迁移；

设备模型和 API 是否兼容；

客户自定义配置升级以后会不会丢失；

出现问题以后怎样诊断客户现场；

升级失败能不能回滚。

因此，**可部署性本身就是平台能力的一部分。**

一个平台即使在开发环境中功能很好，如果无法稳定安装、升级、迁移和维护，也很难真正成为可交付的平台软件。

这也是为什么星云从设计早期就需要避免对某一种内部环境形成过深依赖。

### 2.4.6 社区版和商业版是产品形态，不应该变成两套 Core

如果星云未来不仅作为企业内部平台，也向外提供社区版和商业版本，同样需要遵守这一原则。

社区用户可能在一台服务器上部署星云，用来学习、测试或者管理较小规模的设备；企业客户则可能要求高可用集群、企业身份集成、更完整的审计、安全治理和长期技术支持。

两者需要的产品能力确实不同。

但最基础的产品、设备、模型、连接和 API 最好仍然来自同一个 Core。

否则，一旦社区版和商业版变成两套完全不同的代码体系，时间久了就很难保持兼容，社区生态和商业产品也很难真正相互促进。

因此，本书不会提前决定哪些功能免费、哪些功能收费，也不会把某一种开源许可证作为架构前提。

我们只确定一个更基础的要求：

**Core 应该能够被独立部署，并允许在同一套核心模型之上形成不同规模和不同产品形态。**

具体怎样划分社区版和企业版，是产品策略；能不能支持这种划分，则首先是架构问题。

### 2.4.7 部署方式可以不同，平台语义应该尽量一致

现在把这些形态放到一起，可以得到这样一张图。

```text id="96hxol"
                    星云 IoT Core
                         │
        ┌────────────────┼────────────────┐
        │                │                │
        ▼                ▼                ▼
   多租户 SaaS        专属实例         私有化部署
        │                                 │
        │                                 ▼
        │                             客户数据中心
        │
        └──────────────┬──────────────────┘
                       │
                       ▼
                 边缘节点 / 网关
                       │
                       ▼
                     设备
```

这张图看起来存在很多种“星云”，但我们希望它们拥有同一套核心语言。

无论运行在哪里，“产品”仍然表示一类设备的共同定义，“设备”仍然表示具体实例，“状态”和“控制”的基本含义仍然一致，应用使用的主要 API 也应该尽量保持一致。

真正发生变化的是规模、基础设施和运行位置。

因此，可以把星云的部署思想总结成一句话：

**逻辑上保持统一，物理上允许变化。**

这个原则让平台既能够支撑大规模公共云，也能够进入客户自己的环境；既能够集中运行，也能够把部分能力下沉到边缘。

当然，部署形态越多，平台需要面对的问题也越多。安全、可靠性、可观测性、版本兼容、资源成本和长期维护都会成为设计约束。

这些问题没有必要在第二章一次解决。

在进入后面的具体模块之前，我们只需要再做最后一件事：把前面已经隐含出现的设计选择整理成一组基本原则。

它们会成为后续章节判断方案优劣时反复使用的尺子。
