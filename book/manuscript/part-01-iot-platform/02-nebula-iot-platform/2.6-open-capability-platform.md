# 2.6 IoT 能力开放平台：让外部系统安全使用设备能力

## 2.6.1 背景

星云 IoT 平台已经提供设备接入、状态、控制和音视频等能力。随着智能家居 App、行业系统和合作伙伴接入，直接为每个系统单独提供接口会带来几个问题：

- 每个系统都要重复处理设备、绑定和权限。
- 接口、身份和错误处理不一致，后续难以维护。
- 外部系统可能直接接触设备凭证或内部协议。
- 设备权限分散在不同业务系统中，平台无法统一审计和撤销。

因此，星云需要建立一套受控的 OpenAPI 能力出口。它不是简单地把内部接口公开，而是定义一套稳定的合作方式：外部系统用自己的账号和业务，IoT 平台负责设备和设备能力，双方通过身份映射、授权、令牌和事件协作。

## 2.6.2 目标与收益

这套机制主要解决四件事：

1. **统一开放**：不同 App 使用同一套设备和能力接口。
2. **统一安全**：每个应用、用户和能力都可以单独授权、限流和撤销。
3. **清晰分工**：外部系统负责账号和业务，IoT 负责设备和最终权限判断。
4. **长期演进**：内部协议和服务可以变化，外部接口保持稳定。

这样做以后，新接入一个 App 不需要重新建设一套设备后台；平台也可以知道谁在什么时间访问了哪台设备，出现问题时能够追踪和处理。

## 2.6.3 职责边界

| 内容 | 外部系统 | IoT 平台 |
| --- | --- | --- |
| 用户注册、登录、会员、订单 | 负责 | 不负责 |
| App 中的家庭、房间和展示名称 | 负责 | 不负责 |
| 设备身份、在线状态、能力模型 | 使用 | 负责 |
| 设备归属和共享关系 | 参与业务流程 | 负责最终记录 |
| 谁能访问设备能力 | 提出业务条件 | 负责最终判断 |
| 设备控制、音视频会话 | 发起请求 | 执行和管理 |
| 审计、令牌、撤权 | 配合 | 负责平台侧记录 |

外部系统可以保存“这个用户在 App 中关联了哪些设备”。IoT 平台保存“哪个主体拥有或被授权使用哪些设备能力”。两者保存的是不同事实，不共享数据库。

## 2.6.4 核心对象

第一版只需要明确以下对象：

```text
App             外部接入系统
ExternalUser    外部系统中的用户
IoTPrincipal    IoT 侧可被授权的主体
Home            IoT 侧的家庭或资源空间
Device          设备
Capability      设备能力
Grant           对能力的授权
Session         控制或音视频会话
```

外部用户通过身份映射对应到 IoT 主体。IoT 主体再通过家庭、设备和授权关系访问具体能力。

## 2.6.5 交互方式

外部系统与 IoT 平台通过三种方式交互：

- **OpenAPI**：查询设备、绑定设备、授予权限、控制设备和创建会话。
- **令牌**：把外部用户转换成 IoT 可以识别的调用身份。令牌应有有效期和能力范围。
- **事件**：通知设备上线、绑定完成、权限撤销、录像完成等变化。

以用户观看摄像头为例：

```text
用户登录外部 App
  → App 请求 IoT 创建观看会话
  → IoT 校验用户映射、设备状态和观看权限
  → IoT 返回短时媒体令牌
  → App 使用令牌连接媒体服务
  → IoT 记录会话和审计信息
```

外部 App 不直接拿设备密码、内部流地址或 MQTT 指令。IoT 只给出完成当前操作所需的短时、最小权限凭证。

## 2.6.6 绑定关系怎样处理

“绑定”需要拆成几个动作：

1. 设备注册到 IoT 平台。
2. 设备归属某个 IoT 家庭或主体。
3. 外部 App 保存自己的用户、家庭和展示关系。
4. IoT 为用户或主体授予所需的设备能力。

绑定时，外部 App 发起请求，IoT 校验设备和绑定条件并建立设备侧关系；App 再保存自己的业务关联。解绑时，IoT 先撤销能力，再解除关系，并通过事件通知外部 App。

## 2.6.7 OpenAPI 的第一批范围

第一版围绕“设备、能力、授权、会话”提供接口：

```text
应用接入与凭证
用户身份映射
设备查询
设备绑定与解绑
能力查询
权限授予与撤销
音视频会话创建与关闭
事件订阅
```

接口统一使用版本、请求 ID、错误码、幂等键和审计信息。API Gateway 负责应用认证、租户隔离、限流、版本和基础审计；业务服务负责身份、绑定、授权、设备和会话逻辑。

## 2.6.8 分阶段落地计划

### 阶段一：确定边界和模型

- 完成“对象—负责人—写入方—最终判断方”清单。
- 确定外部用户到 IoT 主体的身份映射方式。
- 确定家庭、设备归属、共享和能力授权的关系。
- 明确音视频能力的安全等级和审计要求。

产出是领域模型和责任约定，不写具体代码。

### 阶段二：建设 OpenAPI 基础层

- 应用注册、应用凭证和环境隔离。
- Token 签发、刷新、过期和撤销。
- 统一认证、错误码、请求追踪和审计。
- 限流、配额、API 版本和基础文档。

### 阶段三：以音视频完成一个闭环

完成以下流程并验证异常情况：

```text
用户映射 → 设备绑定 → 能力授权 → 创建视频会话
→ 使用短时令牌 → 结束会话 → 撤权或解绑 → 审计和通知
```

重点验证重复请求、令牌过期、设备离线、权限撤销和外部系统暂时不可用时的行为。

### 阶段四：扩展其他 IoT 能力

在音视频闭环稳定后，再开放设备控制、告警、自动化、历史数据和 OTA 等能力。每种能力都要单独定义权限、可靠性和审计要求，不能只复用“已绑定设备”这一条件。

## 2.6.9 第一版的边界

第一版只支持一个外部 App 和一条完整的音视频业务链路。暂不把 C 端账号、会员和订单搬进 IoT，也不直接开放 MQTT、RTSP、厂商协议或内部数据库结构。

第一版完成的判断标准是：

- 外部 App 可以用自己的账号接入。
- IoT 可以识别调用主体并判断设备能力权限。
- 视频访问使用短时令牌，不暴露长期设备凭证。
- 绑定、解绑、授权和撤权有明确结果。
- 关键调用可以审计，状态变化可以通过事件同步。

## 2.6.10 总结

星云 OpenAPI 的定位可以概括为：

> 外部系统负责用户和业务，IoT 平台负责设备和设备能力；外部系统通过授权使用 IoT 能力，IoT 平台保留最终的设备安全控制权。

这套边界既能支持当前的音视频接入，也能为后续设备控制、家庭共享、行业应用和第三方生态提供统一基础。
