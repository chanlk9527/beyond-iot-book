# 1.1 IoT 的边界：我们究竟在讨论什么

用户在手机上点击“开灯”，几秒后，客厅亮了起来。

这个功能看上去只是把墙壁上的开关搬到了手机里，背后却增加了一整套关系：手机要找到正确的灯，系统要判断用户能否控制它，控制要求要传到设备，设备还要提供足够的信息，让软件判断发生了什么。

理解物联网，可以从这些关系开始。灯怎样接入网络只是其中一步；当软件开始参与现实对象的观察、管理和控制时，我们才看到了一个需要共同设计的系统。

## 1.1.1 一盏灯怎样进入 IoT 系统

普通的灯由墙壁开关控制。用户按下开关，电路接通，灯亮起来。用户就在现场，可以直接观察结果，整个过程不需要后台记录这盏灯属于谁，也不需要向手机解释灯的状态。

现在给灯增加网络通信和控制能力。用户离家以后，可以通过 App 发出开灯要求；灯接收要求、执行动作，并按照设备支持的方式反馈结果。

原来由用户在现场完成的判断，有一部分交给了设备和软件：控制的是哪一盏灯，指令是否到达，设备执行到了哪一步，都需要通过信息交换来表达。

**本书将物联网（Internet of Things，IoT）理解为：通过设备、连接和软件，让现实对象能够被数字系统识别，并参与信息采集、状态管理或控制协作的系统。**

这里的协作可以很具体：灯接受 App 的控制，传感器把读数交给监测软件，家庭网关根据传感器信息控制灯光。

一盏依靠内置人体传感器自动亮灭的灯，可以独立完成本地功能。当它把感应结果提供给其他设备，或接受外部软件的控制时，就参与了更大范围的协作。

因此，智能硬件和 IoT 设备并不是互斥的概念。同一件产品可以既是智能硬件，也是 IoT 系统的一部分，区别在于我们讨论的是产品自身的能力，还是它与其他对象和软件之间的关系。

## 1.1.2 现实对象怎样进入软件世界

对用户来说，“客厅灯”是一个熟悉的对象。对软件来说，这个名称还不够：不同家庭都可能有客厅灯，同一家庭也可能给两盏灯起相同的名字。

系统需要能够区分具体设备，再记录它所在的家庭、房间，以及哪些用户可以使用它。

软件还需要理解设备提供的信息。灯上报一个表示开关状态的值，双方必须对这个值的含义有共同约定；如果设备可以调节亮度，软件还要知道亮度的取值范围。

收到一串数据，只完成了通信的一部分工作。数据对应哪个设备、表示什么、在什么时候产生，决定了应用能怎样使用它。

设备身份、能力说明、状态记录，以及设备与现实对象之间的对应关系，共同构成软件理解现实世界的依据。我们可以把它们看作现实对象在软件中的数字表示。

信息和控制通常沿两个方向流动：

- 观察：设备 → 连接 → 软件 → 人或业务。 例如，温度传感器采集冷库温度，通过网络上报给软件，供工作人员查看。
- 控制：人或业务 → 软件 → 连接 → 设备。 例如，用户在 App 中要求开灯，软件将控制要求传给灯，设备执行动作并反馈结果。

这两个方向可以形成完整的控制闭环，也可以只实现其中一个。例如，冷库只采集温度并产生告警，也是一种有价值的 IoT 应用。

假设 App 保存的最新信息是“灯在五分钟前报告开启”，随后灯断电了，而新的信息尚未到达。软件仍然保留那条记录，但它已经不能据此确认此刻的灯还亮着。

控制过程也存在同样的限制。接口返回请求已受理、设备收到命令、控制部件执行开灯，以及灯实际发光，分别需要相应的证据。设备若只能反馈开关输出状态，软件就不能把这份反馈扩大解释为对实际照明效果的检测。

**软件保存的是依据设备信息建立的记录，对现实的判断受设备能力和信息时效限制。**

设备怎样被识别、数据怎样被解释、控制结果怎样被确认，正是后续平台设计需要解决的问题。

## 1.1.3 IoT 的边界：联网、智能与持续在线

理解了信息与动作的关系，还需要明确 IoT 不要求设备具备哪些条件，避免把某一种常见产品形态当成所有 IoT 系统的前提。

### 联网，不等于 IoT

互联网为信息交换提供基础。联网设备说明它能够通过网络交换数据，但这还没有说明数据对应什么现实对象、由谁管理，以及这些数据会被用于什么。

例如，一台设备能够通过网络上传一组数据，只说明通信能力已经具备。系统还需要知道这些数据来自哪个设备、表示什么，以及谁会使用它们。

### 智能，不等于 IoT

智能硬件通常具有计算、感知或自动控制能力，可以独立完成一些本地任务。

例如，一盏仅依靠内置传感器自动亮灭的灯，具备智能功能，但未必需要其他软件或设备参与。

相反，一个功能简单的温度传感器，只负责定时采集和上报数据，也可以成为 IoT 系统的重要组成部分。

几个概念的关注点可以简单区分：

| 概念 | 主要关注什么 |
| --- | --- |
| 互联网 | 信息怎样通过网络交换 |
| 联网设备 | 设备是否能够通过网络交换数据 |
| 智能硬件 | 产品自身具有怎样的计算、感知或自动控制能力 |
| IoT | 现实对象、设备和软件怎样建立关系并参与信息交换、管理或协作 |

同一件产品可以同时符合多个概念。分析时，与其判断一件设备够不够智能，不如明确它观察什么、和谁交换信息、能够执行什么动作。

### IoT 不要求完整的感知与控制闭环

冷库可以只安装温度传感器。软件记录温度变化，在超限时通知工作人员，由工作人员到现场检查和处理。

这里已经形成了一项清楚的服务：把现场变化交给软件持续观察，帮助人作出判断。是否增加远程控制，应由业务需求、设备能力和操作后果决定。

同样，一个主要接受控制的设备，也不必具备丰富的环境感知能力。它需要提供什么反馈，应与产品承诺一起确定。

### IoT 不要求设备直接连接云端，也不要求始终在线

家庭传感器可以把信息发送给本地网关，由网关执行规则并控制灯光。如果所需规则、数据和通信路径都在本地，这条自动化就可以在家庭内部完成。

为了节省电量，温度传感器也可以按计划唤醒、采样和上报，其余时间休眠。

因此，云服务是一种部署选择，持续管理也不意味着设备必须持续联网。

这里所说的持续，强调的是系统在使用过程中长期维护对象、记录和管理关系。这些关系需要能够适应设备休眠、断网、重新接入和设备转移等变化。

## 1.1.4 设备、连接、平台和应用的分工

前面描述了现实对象的信息怎样进入软件，以及软件怎样推动实际动作。进一步设计系统时，还需要把这条路径上的责任分清楚。

**设备：观察和作用于现实世界。**

传感器把温度、亮度、位置等变化转换为数据；执行器把控制要求转换为开关、移动或调节等动作。设备的测量范围、精度和反馈能力，限制了软件能够知道和做到什么。

**连接：让信息能够到达另一个地方。**

Wi-Fi、蓝牙、蜂窝网络或以太网等技术提供通信路径，使设备能够与其他参与方交换数据。消息送达并不自动解释业务含义，数据对应哪个设备、表示什么，还需要软件作出约定。

**平台：组织设备及其共同能力。**

不同产品会反复需要设备身份、接入、状态、控制、升级和权限等能力。平台把适合共享的部分组织起来，让产品团队复用，同时维护设备与用户、产品之间的管理关系。

**应用：把能力变成具体用途。**

应用面向具体的人和业务目标，可以是家庭控制 App，也可以是楼宇管理或工厂维护系统。同一条温度数据，在不同应用中可能用于实时显示、能耗分析或维修判断。

这四类责任并不意味着必须建设四个独立的系统。家庭网关可以同时转发消息和执行规则，一个后台也可以同时包含平台能力与应用业务。具体怎样划分，需要结合产品差异、共享需求和维护成本决定。

遇到问题时，可以先判断缺失的是设备能力、通信条件、平台管理还是应用规则，再决定应该调整哪个部分。

## 1.1.5 本书重点讨论什么

从一盏灯出发，我们已经看到一个 IoT 系统需要共同维护的内容：现实对象与设备的对应关系，设备与软件之间的信息交换，以及软件对数据、权限和控制结果的解释。

产品运行得越久，这些关系越需要经受变化：设备可能断网、升级、更换或转移给其他用户，原有记录和权限也需要随之处理。

本书重点讨论其中的平台设计问题：怎样组织不同设备，让应用能够理解并使用它们的能力；怎样维护设备身份、状态和交互记录；怎样在设备与业务不断变化时，保持管理关系清楚、控制依据可靠。

星云 IoT 平台将作为贯穿案例，承载这些设计推演。

硬件电路、无线通信细节和具体行业算法，只在影响平台判断时展开。设备和现场条件会始终参与论证，因为平台提供的能力必须建立在这些条件之上。

理清了 IoT 系统内部的组成与责任，接下来还需要了解谁来承担这些工作。一件 IoT 产品可能由不同企业设计设备、提供平台、开发应用和完成现场交付。它们怎样合作，设备交付后又由谁持续提供服务，将构成下一节的 IoT 产业地图。
