# 4.2 能力模型：平台如何描述设备能够做什么

上一节我们讨论了为什么需要设备模型。

设备模型解决的是：

> 一类设备具有什么共同能力。

但一个新的问题随之出现：

**这些能力应该怎样描述？**

例如，一盏智能灯支持调光。

平台需要知道：

- 它有亮度这个能力；
- 亮度是什么类型的数据；
- 取值范围是多少；
- 是否允许修改；
- 修改之后如何确认结果。

如果没有统一描述方式，应用只能针对每一种设备单独开发。

设备越多，接入成本越高。

因此，IoT 平台通常需要一种能力模型，把设备能够提供的信息和操作转换成软件可以理解的形式。

---

## 4.2.1 不同平台有不同的能力描述方式

IoT 行业并不存在唯一的设备模型标准。

不同平台会根据自己的业务目标，采用不同的抽象方式。

一种常见方式是**数据点模型（Data Point，DP）**。

例如，某些消费 IoT 平台会把设备能力表示成一组数据点：

智能灯：

| 数据点 | 含义 |
| --- | --- |
| DP1 | 开关 |
| DP2 | 模式 |
| DP3 | 亮度 |
| DP4 | 色温 |

设备上报：

```
DP3 = 50
```

平台根据产品定义知道：

这表示亮度变化。

这种方式的特点是：

设备和平台之间围绕统一的数据结构通信。

它非常适合大量消费设备快速接入：

- 能力定义简单；
- 设备侧实现成本低；
- 平台容易自动生成控制界面。

例如，一些面向消费硬件生态的平台就采用类似的数据点方式描述设备能力。

---

另一种方式，是进一步强调数据背后的业务含义。

例如，将设备能力拆分为：

- 属性（Property）；
- 事件（Event）；
- 操作（Action）。

这种方式关注的不只是：

> 传递了什么数据。

还关注：

> 这条数据代表什么，以及系统应该如何理解它。

例如：

一个温度值：

```
temperature = 25℃
```

可能表示设备当前测量到的温度。

一次过温告警：

```
overheat_alarm
```

表示某件事情曾经发生。

一次重启请求：

```
restart()
```

表示要求设备执行某个动作。

它们在数据层面都可以表现为消息，但业务含义完全不同。

---

因此，DP 模型和属性、事件、操作模型并不是互相冲突的关系。

可以简单理解为：

**DP 更像一种数据组织方式。**

**属性、事件、操作更像一种语义分类方式。**

一个数据点可以承载不同语义。

例如：

```
DP3 = 50
```

如果表示当前亮度，它是一个属性。

如果表示要求设备调整到 50%，它又接近一次控制操作。

真正重要的是：

平台是否明确知道这条数据代表什么。

---

## 4.2.2 星云采用属性、事件和操作描述设备能力

为了让平台不仅能够接入设备，还能够支撑自动化、跨产品协作和长期演进，星云采用更强调语义的能力模型。

设备能力主要分为三类：

- 属性；
- 事件；
- 操作。

它们分别回答三个不同的问题：

**设备现在是什么状态？**

**设备发生过什么事情？**

**设备能够执行什么动作？**

---

## 4.2.3 属性：描述设备可以被观察的状态

属性描述设备当前具有的某种状态。

例如智能灯：

- 开关状态；
- 当前亮度；
- 当前色温；
- 设备温度。

一个属性通常包含：

- 名称；
- 数据类型；
- 单位；
- 取值范围；
- 访问方式。

例如：

```
brightness

类型：
integer

范围：
0～100

访问：
读写
```

表示：

设备提供一个亮度能力。

应用可以读取当前亮度，也可以请求修改亮度。

但这里需要注意：

属性定义和属性值不是一回事。

模型中：

```
brightness:
0～100
```

表示：

这类设备支持亮度能力。

实例运行中：

```
device_001 brightness = 40
```

表示：

这一台设备当前报告亮度为 40。

前者描述能力。

后者描述现实状态。

---

## 4.2.4 事件：描述设备发生过的事实

属性适合描述：

> 现在是什么状态。

但很多 IoT 场景还需要知道：

> 曾经发生过什么。

例如：

智能灯检测到内部温度过高。

设备产生：

```
over_temperature_alarm
```

这是一条事件。

事件通常包含：

- 事件类型；
- 发生时间；
- 相关数据；
- 附加信息。

例如：

```
事件：
过温告警

时间：
2026-09-30 10:20

温度：
75℃
```

这里的 75℃ 和普通温度属性不同。

普通属性表示：

当前温度。

事件中的温度表示：

发生这次异常时记录的数据。

---

属性和事件经常同时存在。

例如门锁：

属性：

```
door_status = open
```

表示：

当前门是什么状态。

事件：

```
door_opened
```

表示：

某一次开门行为发生。

如果门随后关闭：

当前状态变成：

```
door_status = closed
```

但之前发生过的开门事件仍然存在。

因此：

状态和历史事实需要分别表达。

---

## 4.2.5 操作：描述设备能够执行的动作

除了提供状态和事件，设备还需要接受外部控制。

例如：

智能灯：

- 开灯；
- 关闭；
- 调节亮度；
- 重启设备。

这些属于设备提供的操作能力。

一个操作通常描述：

- 操作名称；
- 输入参数；
- 执行结果。

例如：

```
操作：
定位闪灯

参数：
次数

结果：
执行成功/失败
```

应用调用：

```
让客厅灯闪烁三次
```

就是一次具体操作请求。

---

## 4.2.6 为什么操作不能全部等同于属性修改

很多简单设备控制，看起来都可以通过修改属性完成。

例如：

```
brightness = 70
```

表示：

把亮度调整到 70。

这种方式没有问题。

但是，并不是所有动作都适合作为属性。

例如：

让灯闪三次。

它不是一个持续状态。

执行结束以后：

设备不会保持：

```
flash_count = 3
```

它只是完成了一次行为。

因此：

属性更适合表达：

> 设备处于什么状态。

操作更适合表达：

> 设备执行什么动作。

两者可能影响同一个现实对象，但语义不同。

---

## 4.2.7 三类能力如何共同工作

实际 IoT 系统中，属性、事件和操作通常会组合起来。

例如：

用户打开空调。

流程可能是：

1. 应用调用：

```
turn_on()
```

这是一次操作。

2. 空调执行动作。

3. 设备更新属性：

```
power = true
```

4. 平台产生事件：

```
air_conditioner_started
```

整个过程包含：

- 控制请求；
- 执行动作；
- 状态变化；
- 事件记录。

因此，能力模型不是简单的数据字典。

它描述的是：

设备如何被理解，以及不同能力之间如何产生关系。

---

## 4.2.8 星云能力模型示例

一个智能灯模型可以表示为：

```
智能灯模型

属性：

- 开关状态
- 当前亮度
- 当前色温


事件：

- 过温告警
- 设备故障


操作：

- 设置亮度
- 重启设备
- 恢复出厂
```

其中：

模型描述：

> 这种设备能够提供什么。

设备实例记录：

> 某一台设备现在是什么状态。

运行数据保存：

> 设备过去发生过什么。

控制记录保存：

> 系统曾经要求设备做什么。

这些信息共同组成平台对设备的理解。

---

能力模型的价值，并不是为了生成几个控制页面。

更重要的是，它建立了一套设备、平台和应用之间共同理解的语言。

当设备数量增加，产品类型增加，甚至不同厂商开始协作时，平台不需要让每个应用重新理解每一种硬件，而可以基于统一模型：

- 识别设备能力；
- 理解设备数据；
- 调用设备功能；
- 组织自动化逻辑。

## 4.2.9 产品自定义能力与平台标准管理信息

固件版本适合作为一个属性吗？从语义上看，它确实是设备可以报告的只读信息。不过，假设晴川智能灯用 `firmwareVersion` 表示当前固件版本，另一款门锁使用 `fw_ver`，平台的远程固件升级（OTA）服务若直接读取这些自定义属性，就必须逐个产品判断应该取哪个字段。产品越多，升级服务需要了解的产品细节就越多。

这里有两个不同的分类维度：属性、事件和操作区分信息的用途，产品自定义与平台标准则区分谁负责定义其含义。**某项信息可以具有属性语义，但只要平台公共管理功能依赖它，就需要稳定的标准定义，不能让业务逻辑直接依赖任意的产品字段。**

因此，星云把用于 OTA 的固件版本归入标准设备管理信息，统一规定组件标识、版本字段及上报含义。一台设备可能同时具有主控和通信模组固件，所以版本应归属于具体设备的具体组件。标准协议设备按这一约定上报；已有设备中的 `fw_ver` 等字段，则由接入适配层转换为同一份标准信息。OTA 服务读取标准记录，字段差异由接入部分处理。映射需要确认该字段表示当前运行版本，而非待安装的目标版本，不能只做名称替换。

这种边界也适用于其他管理场景：

| 场景 | 平台需要统一的约定 | 与产品能力的边界 |
| --- | --- | --- |
| 固件适配 | 硬件型号、硬件版本、组件及当前固件版本 | 产品业务属性不能任意改变这些信息的管理含义 |
| 在线判断 | 连接、心跳、超时及最后活动时间的定义 | 由平台按接入方式判定，不能直接用业务属性中的“运行正常”代替 |
| 配置同步 | 目标配置版本、设备报告的已生效版本与应用结果 | 配置项可以因产品而异，生效反馈需要统一解释 |
| 命令与升级反馈 | 请求或任务标识、处理阶段、结果及错误信息 | 具体操作可以由产品定义，某次执行进展归入相应流程记录 |

这些信息可以在设备详情中一起展示，也可以把固件版本呈现为预置的只读系统属性，但其标识和语义由平台维护，产品不能覆盖。展示应复用标准管理记录，避免另存一份可独立修改的普通属性值。升级任务的目标版本与设备当前报告的版本仍需分开：下发升级请求，只说明平台提出了目标，不能据此改写当前版本。

统一的范围也不宜无限扩大。电量、位置等信息可以先作为产品属性；当平台需要跨产品提供低电量管理或设备地图时，再定义相应的标准能力，并由产品声明属性映射。例如，`battery_pct` 与 `power_level` 都可以映射为电池电量，但必须同时约定百分比范围、无效值和必要的换算规则。仅仅统一 key，无法保证两个值能够被同一条规则使用。标准能力还需要声明设备是否支持，缺失的上报不能自动补成零。

由此，产品模型保留描述业务能力的自由，平台公共功能则依赖明确的管理协议或标准能力。建立这些约定需要维护映射与兼容关系，但可以避免每个公共服务都重复适配产品差异。下一节将进一步讨论，设备报文中的字段、单位和消息含义如何被转换为平台能够统一理解的数据。
