# 4.4 状态、数据与模型：平台如何保存设备运行事实

一盏智能灯在 10:00 上报自己处于开启状态，亮度为 40%。平台完成协议解析和模型映射后，已经能够理解这两个属性。到了 10:05，设备断开网络；10:10，用户又通过本地开关把灯关闭。此时打开 App，平台仍然只能提供断网前收到的信息。数据的含义没有歧义，但它已经不足以说明灯此刻的情况。

上一节解决了设备数据如何被平台理解的问题，本节进一步讨论这些数据进入平台后应当如何保存和使用。同一条上报既可能更新平台掌握的状态，也可能成为历史记录或业务判断的依据。要正确使用它，平台需要同时保留数据的归属、来源和时间，并区分设备已经报告的事实与系统希望达到的结果。

<a id="_4-4-1-模型描述能力-状态描述当前情况"></a>

## 4.4.1 模型定义与设备实例状态

晴川智能灯模型定义了一个名为 `brightness` 的整数属性，取值范围为 0～100。这个定义说明采用该模型的设备如何表达亮度，也为数据校验和应用展示提供了依据。当 `device_001` 上报 `brightness = 40` 时，变化的是这一台设备的属性值，模型对亮度的定义仍然保持不变。

**模型描述一类设备具有什么能力，实例状态记录平台掌握的某台设备的具体情况。** 在星云中，产品关联适用的模型，设备实例关联自身的运行数据。客厅灯和卧室灯可以使用同一个模型，同时具有不同的开关状态与亮度；修改客厅灯的亮度，不会改变卧室灯的状态，也不会修改模型的取值范围。

这一区分也决定了数据如何组织。模型保存属性名称、类型、单位和访问约定，状态记录则需要归属到具体的设备与属性，并保存相应的值。后续即使多个应用同时读取设备，也应当依据同一份模型解释这些值，避免各自赋予不同含义。

<a id="_4-4-2-平台为什么需要保存设备状态"></a>

## 4.4.2 平台状态是最近一次有效观测

设备是运行数据的来源，但应用并不总能在需要时直接查询设备。即使只有一台电池供电的传感器，它也可能正在休眠；设备数量增加后，逐台查询还会引入网络等待和额外通信开销。因此，星云需要保存已接收的状态，让应用能够及时读取平台目前掌握的信息。主动查询可以用于刷新这些信息，却不能保证设备始终可达，也不能消除采集到展示之间的时间差。

<a id="_4-4-3-状态不是现实本身-而是平台掌握的信息"></a>

回到开篇的智能灯。10:00 的上报使平台保存了 `power = true` 和 `brightness = 40`；设备断网后，这条记录仍然是一次有效的历史观测。问题在于，如果 App 不显示更新时间，继续把它呈现为刚刚确认的状态，用户就可能误以为灯仍然亮着。**平台保存的状态应解释为最近一次有效观测，而不能无条件地视为设备此刻的现实状态。**

为了保留这一边界，状态记录需要携带数值之外的信息。例如，开关状态可以同时记录设备标识、属性标识、数据来源、设备产生时间和平台接收时间。来源用于区分设备直接上报、网关代报或平台推算，时间则帮助应用判断这次观测距今有多久。若两个属性分别上报，它们各自的更新时间也可能不同，不能因为刚收到温度值，就把设备全部属性都标记为刚刚更新。

状态是否仍可使用，还取决于具体业务。一个小时前的室温可以用于查看最近读数，却未必足以支持此刻的自动调节；离线设备的最后状态仍有查询价值，但界面应说明它的时效。连接状态与属性新鲜度也需要分别判断：设备在线，只能说明当前连接情况，不能证明每个属性都已有最新读数。

<a id="_4-4-4-设备时间和平台时间并不总是一致"></a>

## 4.4.3 数据时间与状态更新顺序

保存更新时间以后，平台还需要明确这个时间表示什么。假设仓库温度传感器在 12:00 采集到 20℃，由于网络中断，直到 12:30 才补传到平台。若系统仅把 12:30 作为这条数据的时间，历史曲线和业务规则就可能把半小时前的观测当作刚刚发生的测量。

<a id="设备产生时间"></a>
<a id="平台接收时间"></a>

这里需要区分设备产生时间与平台接收时间。设备产生时间表示设备记录的采样或事件发生时刻，平台接收时间表示服务器收到消息的时刻。前者帮助还原现场过程，后者说明平台何时获得这份信息。它们描述的是同一条数据经历的不同阶段，不能相互替代；设备没有提供可靠时间时，也应保留这一限制，而不能把接收时间标成确定的采样时间。

延迟还会改变消息的到达顺序。假设网络恢复后，一条新采样先到达，随后才补传旧记录，平台看到的顺序可能如下：

| 到达顺序 | 设备采样时间 | 平台接收时间 | 温度 |
| --- | --- | --- | --- |
| 第一条 | 12:29 | 12:29:02 | 24℃ |
| 第二条 | 12:00 | 12:30:00 | 20℃ |

如果每收到一条消息就覆盖当前值，状态会从 24℃退回到更早采集的 20℃。**最后到达的数据不一定是最新产生的数据，状态更新需要明确的新旧判定规则。** 在设备时钟可靠的前提下，可以依据采样时间比较；如果协议提供采样序号，也可以在约定的序列范围内判断先后。旧数据仍可补入历史记录，但不应因此覆盖已经确认的较新状态。

这些依据也有适用边界。设备时钟可能偏移或在重启后回退，序号也可能重新开始，因此不能不加区分地比较所有时间或序号。星云需要在接入约定中明确它们的含义及有效范围；缺少可靠顺序依据时，应记录不确定性，并按业务约定处理。平台接收时间可以保留到达顺序，却无法凭空恢复现场的真实先后关系。

<a id="_4-4-5-状态-历史数据和事件服务不同目标"></a>

## 4.4.4 状态、历史记录与事件的不同用途

一条温度上报进入平台后，可以服务于几个不同的问题。状态服务判断它是否足够新，以决定是否更新最近温度；历史数据服务保存这次采样，使应用能够查询一段时间内的变化；规则处理则结合已有记录，判断是否满足某个业务条件。它们使用同一份输入，但保留的信息和处理目标不同。

<a id="第一-更新当前状态"></a>
<a id="第二-保存历史数据"></a>
<a id="第三-生成业务事件"></a>

| 数据用途 | 主要回答的问题 | 需要保留的信息 |
| --- | --- | --- |
| 状态 | 平台最近知道设备怎样 | 最近有效值及其来源、时间 |
| 历史记录 | 各次观测如何随时间变化 | 按保存策略保留的采样值及时间依据 |
| 事件 | 发生了哪一次事实或规则判定 | 事件类型、发生时间、来源及关联数据 |

状态适合快速读取，但只保留最新值就会失去变化过程。历史记录能够支持曲线、报表和追溯，也需要相应的存储与保留策略。两者可以依据各自的规则处理同一条数据：例如，迟到的旧采样可以补入历史而不更新当前状态，重复上传的同一次采样则需要按既定标识去重，避免被误认为新的观测。

事件还需要区分来源。设备直接报告的过温告警，是设备对现场情况的判断；平台根据温度记录生成的告警，是规则对已获得数据的判断。**业务事件应保留判定依据，使应用能够分清现场上报的事实和平台推导的结果。** 这也延续了上一节的语义约束：一次状态上报不应自动等同于一次事件。

例如，“温度连续十分钟超过 35℃”不能仅凭十分钟前和现在的两个高温读数就认定成立。规则需要约定采用哪一种时间、要求怎样的采样覆盖，以及如何处理数据缺失和迟到。证据不足时，应按约定标记未知或产生相应的数据异常，而不能默认为这十分钟始终处于高温。只有明确这些条件，告警才能成为业务处置的可靠依据。

<a id="_4-4-6-控制过程中的期望状态和实际状态"></a>

## 4.4.5 期望状态、报告状态与控制结果

状态管理在设备控制中又增加了一层含义。用户要求关闭客厅灯时，平台首先获得的是一个控制意图。请求可能尚未发出，也可能在传输中，设备还可能拒绝执行；因此，平台接受了请求，并不足以把设备的报告状态直接改为关闭。

<a id="期望状态-desired-state"></a>
<a id="报告状态-reported-state"></a>

为了区分目标与观测，星云可以分别保存期望状态（Desired State）和报告状态（Reported State）。期望状态表达用户或系统希望设备达到的结果，报告状态保存设备最近报告的值。对关灯请求，使用模型中的开关属性更直接；只有模型明确约定亮度为零即表示关闭时，才能用亮度值代替开关状态。

```text
控制目标：power = false
最近报告：power = true
```

这两个值不同，说明目标尚未得到报告状态的确认，但仅凭差异还不能判断设备正在执行还是执行失败。平台还需要单独记录这次请求的发送、接收、执行反馈和超时等进展。**期望状态描述目标，报告状态描述观测，控制记录说明某次请求的处理过程。** 将三者分开，应用才能准确显示“等待设备响应”“执行失败”或“最近已报告关闭”等不同情况。

如果设备后续上报 `power = false`，并且能够确认这是比控制前更新的观测，平台就有依据说明最近报告与目标一致。不过，要进一步判断某次请求是否执行成功，还需要协议提供相应的执行结果或关联信息。设备也可能被本地开关关闭，状态相同并不能独自证明是哪次请求导致了变化；反过来，等待超时也只说明平台未在期限内获得确认，并不必然意味着设备没有执行。

期望状态适合表达希望持续达到的属性目标，例如开关、亮度或配置值。对于重启、闪灯三次这类一次性操作，应依据操作记录和执行反馈管理结果，不能把它们强行表示为一个长期等待匹配的属性值。两种控制方式都可以使用模型定义的能力，但需要保留各自的完成条件。

<a id="_4-4-7-状态管理是平台的重要能力"></a>

## 4.4.6 星云中的运行事实管理

结合前面的区分，星云可以围绕设备实例组织运行数据：模型提供能力定义与校验依据，接入部分把上报转换成带有设备身份、能力标识、来源和时间的信息，再交给状态、历史与事件处理部分。控制请求则另外保留目标和执行记录，并与设备反馈建立关联。这里划分的是处理职责，实现时可以根据系统规模组合部署。

<a id="_4-4-8-从-设备数据-到-业务价值"></a>

以冷库监测为例，值班人员首先需要知道最近温度和数据是否新鲜，因而读取状态；调查温度为何升高时，需要查询历史曲线；处理高温告警时，则需要查看触发条件、覆盖的时间范围和相关采样。如果系统只保存一个温度数字，这些问题都无法完整回答。业务能够采取什么行动，取决于平台保留了哪些事实，以及这些事实的有效范围是否清楚。

这些处理也可能在不同时间完成。当前状态已经更新时，历史记录或规则判定未必同时可见。因此，应用应依据各项记录的时间和处理进展理解结果，不能把一个环节的完成当作所有环节都已完成。**运行事实管理的基础，是让每一份记录都能说明它来自哪里、描述何时的情况，以及能够支持什么判断。**

到这里，模型与运行数据的职责已经清晰：模型规定如何理解设备能力，运行记录保存具体设备在不同时间的观测、事件和控制过程。不过，这些记录仍依赖模型定义才能被解释。如果固件升级后新增能力，或者同名属性的单位与范围发生变化，已有状态和历史数据又该按哪一份定义读取？下一节将沿着这个问题，讨论设备能力变化时的模型演进与兼容。
