# 4.1 从一台设备到一类设备：为什么需要模型

第三章中，我们为设备建立了平台身份。

星云现在可以知道：

> 这是一台设备。

例如：

> device_001 是一台已经注册并激活的智能灯。

但如果平台只保存设备身份，还无法真正理解它。

当应用请求控制这台设备时，平台还需要回答：

它是不是支持开关？

是否支持调光？

亮度应该使用什么单位？

它会产生哪些状态变化？

如果没有这些信息，平台只能把设备看作一个未知的数据来源。

因此，IoT 平台除了管理设备实例，还需要描述设备本身具有什么能力。

这就是设备模型存在的原因。

---

## 4.1.1 一台设备和一类设备不是同一个问题

假设晴川生产了一批智能灯。

其中：

第一盏灯安装在用户家的客厅；

第二盏灯安装在酒店走廊；

第三盏灯安装在办公楼会议室。

它们可能使用相同硬件，运行相同固件，也支持相同功能。

从生产角度看，它们属于同一种产品。

但从运行角度看，它们完全不同：

- 属于不同位置；
- 被不同用户管理；
- 拥有不同状态；
- 产生不同历史数据。

平台不能简单地把它们当成同一个对象。

因此，IoT 系统通常需要区分：

**设备模型（Model）**

和

**设备实例（Instance）。**

设备模型描述：

> 一类设备共同具有什么能力。

设备实例描述：

> 某一个具体设备当前是什么状态。

例如：

智能灯模型：

```
支持开关
支持亮度调节
支持过温告警
```

客厅里的灯实例：

```
device_001
位置：客厅
当前亮度：40%
最近上线：10:23
```

酒店走廊里的灯实例：

```
device_002
位置：三楼走廊
当前状态：关闭
最近上线：10:25
```

两个实例共享同一个模型，但运行状态完全不同。

这也是为什么平台不能把设备功能直接写死在设备记录里。

如果每增加一台灯，就复制一份完整能力定义，那么设备数量增加以后，模型管理会迅速失控。

---

## 4.1.2 产品、产品模型和设备实例

在实际 IoT 平台中，“产品”这个词经常产生混淆。

原因是它同时存在于两个不同语境中。

从商业角度看，产品是企业卖给用户的东西。

例如：

> 晴川智能氛围灯 Pro 套装。

它可能包含：

- 一盏灯；
- 一个网关；
- 一个 App；
- 云端服务；
- 售后支持。

这个产品关注的是：

用户购买了什么。

但在 IoT 平台中，产品通常还有另一层含义：

> 一类设备的技术定义。

例如：

“调光灯 V2”这个平台产品模型，可以描述：

- 支持开关；
- 支持亮度；
- 支持色温；
- 支持温度事件。

它关注的是：

软件如何理解这一类设备。

因此，同一个“产品”在两个语境下可能不是同一个范围。

例如：

一个家庭照明套装，从用户角度看是一个商品。

但在平台中，它可能由多个模型组成：

```
家庭照明套装

 ├── 智能灯模型
 ├── 网关模型
 └── 人体传感器模型
```

用户购买的是一个产品组合。

平台管理的是多个设备模型和实例。

---

## 4.1.3 模型描述共同约定，实例保存现实变化

设备模型和设备实例最核心的区别是：

**模型描述可能性，实例记录现实。**

例如，一个智能灯模型定义：

```
亮度：
范围 0～100

支持读取

支持设置
```

这表示：

所有属于该模型的设备，都应该理解亮度这个能力。

但某一台灯当前是多少亮度，并不属于模型。

例如：

```
device_001

当前亮度：
40
```

这是运行数据。

同样：

模型可以定义：

```
支持过温告警
```

但某一次具体事件：

```
2026-09-30 10:20
设备温度超过阈值
```

属于实例运行记录。

如果把两者混合，就会出现典型问题。

例如：

某个用户把客厅灯调成 40%。

平台修改了模型里的亮度字段。

那么所有同型号灯是不是都应该变成 40%？

显然不是。

因为：

模型变化影响“设备能够怎样被理解”。

实例变化影响“某一台设备现在怎样”。

这两个变化的生命周期完全不同。

---

## 4.1.4 为什么不能直接按照商品型号建立模型

一个自然想法是：

> 一个商品型号对应一个设备模型。

很多简单系统确实这样做。

但随着产品复杂化，这种关系会出现问题。

例如：

晴川销售三款灯：

- 智能阅读灯；
- 智能氛围灯；
- 智能吸顶灯。

它们可能在商业上是三个商品。

但底层能力可能高度重叠：

- 开关；
- 调光；
- 色温；
- OTA；
- 能耗统计。

如果平台完全按照商品划分模型，那么大量能力会重复定义。

另一方面，同一个硬件模型也可能服务不同商业产品。

例如：

同一款灯芯片和控制板，可以被：

- 家庭照明产品；
- 酒店照明方案；
- 办公楼能源管理方案；

分别采用。

硬件相同，不代表商业产品相同。

因此，平台模型设计需要保持一定抽象：

它既不能完全贴着销售商品变化，也不能脱离实际设备能力。

它描述的是：

> 软件需要理解的设备能力边界。

---

## 4.1.5 模型需要连接现实，而不能脱离设备

这里还有一个容易忽略的问题：

模型只是描述。

它不会自动创造能力。

假设平台模型中声明：

```
支持色温调节
```

但某批旧设备实际上没有对应硬件。

那么平台虽然知道这个能力，却无法真正执行。

因此：

**模型必须反映设备真实能力。**

模型和设备实现之间需要保持一致。

这也是为什么设备升级、固件升级和模型版本管理会成为 IoT 平台的重要问题。

例如：

第一代智能灯：

```
开关
亮度
```

第二代智能灯：

```
开关
亮度
色温
```

平台不能因为第二代产品出现，就认为所有设备都支持色温。

它必须能够表达：

不同实例对应不同能力版本。

---

## 4.1.6 星云中的基本关系

综合前面的讨论，星云中可以建立这样的关系：

```
产品模型
    ↓
设备实例
    ↓
运行数据和控制记录
```

其中：

产品模型描述：

- 设备类型；
- 支持能力；
- 数据结构；
- 交互方式。

设备实例描述：

- 某一台具体设备；
- 身份；
- 位置；
- 所属关系；
- 当前状态。

运行数据描述：

- 实际产生的数据；
- 状态变化；
- 事件记录；
- 控制结果。

三者相互关联，但不能互相替代。

---

设备模型的价值，并不是让平台多保存一张表。

它真正解决的是：

**如何让不同设备、不同应用和不同团队，对同一类设备形成共同理解。**

当设备数量只有几个时，应用直接理解每种设备也许还能接受。

但当平台面对：

- 数十种产品；
- 数百万设备；
- 多个品牌；
- 多种应用；

没有统一模型，设备之间就无法形成稳定协作。

下一节，我们继续深入设备模型本身，讨论：

**一个模型应该描述哪些能力，以及属性、事件和服务为什么成为 IoT 平台中最常见的表达方式。**
