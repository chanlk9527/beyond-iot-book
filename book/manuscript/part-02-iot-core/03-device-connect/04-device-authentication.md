## 3.4 设备认证：设备如何证明自己是谁

前面几节，我们一直围绕“平台如何认识一台设备”这个问题展开。3.2 讨论了设备身份的来源：星云中的设备身份并不一定来自某一个固定字段，它可能来自生产阶段预注册，也可能在首次接入时动态建立。无论采用哪种方式，平台最终都会形成一个稳定的设备对象，用来代表现实中的某一台设备。

但平台知道存在一个设备身份，并不代表连接过来的设备就一定是真的。例如，平台中已经存在一个名为 `device_001` 的设备对象。某个客户端连接平台时，发送了一句“我是 device_001”，平台并不能就此相信它。设备 ID 本身通常不是秘密，任何知道这个编号的人，都可能尝试伪造一个连接。

因此，设备接入还需要认证过程，用来判断当前连接者是否拥有某个设备身份对应的证明能力。简单来说，**身份回答“你是谁”，认证回答“你凭什么证明你是它”**。这也是为什么设备身份和认证材料必须分开设计。

## 3.4.1 身份是长期对象，凭证是证明方式

回顾 3.2 的设计，星云中的设备可能具有平台设备 ID、工厂序列号、模组信息和芯片编号。这些信息共同帮助平台认识设备，但认证并不是依靠这些信息本身完成的，而是通常依赖某种凭证，例如对称密钥、数字证书、非对称密钥对或短期访问令牌。连接方通过使用相应的认证材料，证明自己拥有该身份所要求的证明能力。

例如，设备身份 `device_001` 对应一个认证凭证 `credential_xxx`。设备连接平台时，需要使用这个凭证完成认证。认证成功以后，平台才会在当前连接与设备身份之间建立可信关系：

```text
连接 → device_001
```

在这个关系中，设备 ID 用于标识设备，凭证用于证明身份。**设备 ID 可以公开，用于认证的秘密材料必须受到保护。**

## 3.4.2 为什么不能只使用设备 ID

很多初学者第一次设计 IoT 接入时，会想到：每台设备有一个唯一 ID，连接时上传 ID 就可以了。这种方案的问题在于，**ID 只是标识，不是证明**。例如，一个智能门锁的设备编号是 `lock_123456`，如果攻击者知道这个编号，就可以在伪造的连接中提交同样的信息：

```text
device_id=lock_123456
```

仅凭这个编号，平台无法判断连接的是真门锁，还是一个冒充者。因此，设备认证必须依赖比 ID 更强的机制。

这和日常生活类似：身份证号码用于标识一个人，但不能单独作为所有场景中的身份验证。登录银行账户时，还需要密码、验证码或者其他证明。IoT 设备也是如此，设备 ID 负责让系统知道“讨论的是哪台设备”，认证材料则用于证明“当前连接者能够代表这台设备”。

## 3.4.3 常见设备认证方式

不同规模和场景的 IoT 系统，会采用不同的认证方式。

### 对称密钥认证

对称密钥认证是一种较简单、也很常见的方式。设备和平台共享一个秘密，连接时通过算法验证设备是否拥有正确的密钥：

```text
设备：
secret_key

平台：
secret_key
```

这种方式实现简单，计算成本低，适合大量资源有限的设备。但如果大量设备共享同一个密钥，一台设备的密钥泄露就可能影响整个设备群。因此，大规模设备接入时，通常会为每台设备分配独立密钥：

```text
device_001 → key_A
device_002 → key_B
device_003 → key_C
```

这样，单台设备的密钥泄露就不会因为共用密钥而扩散到全部设备。

### 证书认证

在企业级和安全要求较高的场景中，经常使用数字证书。设备拥有设备证书和私钥，平台保存可信的证书链。连接时，设备需要证明自己拥有与这个证书对应的私钥，平台则验证证书是否合法、是否由可信机构签发，以及是否已经过期或撤销。

这种方式类似互联网 HTTPS 中使用的身份体系。它的优势是身份关系更加清晰，支持规模化管理，也方便吊销和更新；相应的代价是实现复杂度更高，需要管理证书的整个生命周期。

### Token 或临时凭证

在一些场景中，设备不会长期直接使用固定凭证，而是通过已有身份获取短期访问令牌。例如，设备首先完成一次安全注册，平台返回一个短期 Token，设备再使用这个 Token 进行后续访问。这种方式更灵活，适合复杂系统。

这里需要区分设备身份与临时访问授权。**Token 通常不是设备的长期身份，而是一种临时访问授权**：它解决的是“当前这次访问是否允许”，而不是“这台设备长期是谁”。

## 3.4.4 设备认证和用户认证有什么不同

IoT 平台同时存在设备和人的身份体系。用户登录 App 时，也需要认证：用户输入账号密码，平台验证用户身份，再返回相应的访问权限。设备认证看起来与之类似，但两者关注的对象不同。用户一侧需要确认谁在操作，以及是否允许访问某些资源；设备一侧需要确认哪台设备正在连接、连接者能否证明其设备身份，以及是否允许它进入系统。

例如，用户张三打开 App 控制智能灯。张三登录 App 时，平台需要确认“这是张三”；对于接入平台的灯，平台也需要通过设备认证，确认它代表 `device_001`。当 App 请求控制这盏灯时，平台还需要进一步判断：张三是否有权限控制 `device_001`。

因此，一个完整的 IoT 操作通常同时涉及用户身份、设备身份和权限关系。**设备认证不能替代权限系统**，确认用户和设备各自是谁之后，仍然需要判断两者之间是否存在相应的控制权限。

## 3.4.5 设备认证失败时怎么办

真实系统中，认证失败是必然会发生的。设备凭证错误、凭证过期、设备已经被撤销、设备被迁移到其他租户，或者设备时间错误导致证书校验失败，都可能使设备无法通过认证。

平台需要为这些情况明确处理策略：认证失败后是否允许重试，是否记录异常，是否暂时锁定设备，是否通知运营人员，以及是否让设备进入待重新注册状态。这些策略需要结合设备类型设计，不能只停留在返回一次认证失败结果。

对于家庭智能灯，用户可能希望通过重新配网恢复使用；对于工业控制设备，异常认证则可能需要更严格的安全处理。同样是认证失败，不同设备所需要的后续处理并不相同。

## 3.4.6 凭证生命周期比认证本身更重要

很多系统关注设备能不能登录，但在长期运行中，更重要的问题是凭证如何管理。一台设备可能运行十年，期间可能发生密钥泄露、证书过期、安全策略升级或供应商更换。因此，平台需要支持凭证生成、安全下发、轮换、撤销和恢复，覆盖凭证从投入使用到失效及恢复使用的过程。

这里再次体现了身份和凭证分离的重要性。设备身份可以长期保持为 `device_001`，而它对应的凭证可以随着运行和维护不断变化：

```text
credential_v1
        ↓
credential_v2
        ↓
credential_v3
```

**凭证发生变化，设备身份仍然可以保持不变。**平台依然知道这是同一台设备，不需要因为更换了证明方式，就把它当成另一台设备。

## 3.4.7 星云中的认证关系

综合前面的设计，星云中的设备身份、认证凭证与设备连接之间，可以理解为下面的关系：

```text
设备身份
    |
    | 绑定
    |
认证凭证
    |
    | 验证
    |
设备连接
```

设备身份负责长期管理，认证凭证负责证明身份，连接负责传输信息。三者的生命周期不同：设备身份可能存在多年，认证凭证可能定期变化，而连接可能几分钟后就会重新建立。如果把这三个概念混成一个对象，系统就很难支持设备换证书、设备转移、设备维修、多环境部署和安全升级。

设备认证的目标，并不是让平台“记住一个密码”，而是在不可信网络环境中，让平台能够确认当前连接者确实代表某个合法设备身份。上一节解决了设备如何从注册进入生命周期，本节补上了连接者如何证明身份这一环节。下一节，我们继续讨论设备真正接入通信系统的问题：认证通过以后，设备如何建立连接，以及平台如何管理大量设备连接。
