# 5.4 异常处理：重试、重复与乱序

设备已经执行了“闪灯三次”，完成反馈却在断线时丢失。平台等待超时后再次发送请求，设备又闪了三次。消息终于得到了回复，但用户要求的一次操作已经发生了两遍。

前面几节已经区分消息编号、命令进展与状态版本。异常处理需要进一步规定：哪一方负责恢复，恢复时保留哪些标识，接收方怎样识别已经处理的工作，以及无法确认结果时如何停止自动操作。本节以这些约定为基础，讨论星云在离线、重复、乱序和进程重启中的处理规则。

## 5.4.1 确认边界与恢复责任

**一次确认只证明约定边界内的工作已经完成。** 接入通道确认接收，不能证明设备执行；设备反馈执行完成，也不能证明平台已经保存结果。沿链路恢复时，需要先找到最后一个有可靠记录的环节。

以设备上报告警为例，如果平台承诺“确认收到后，即使接入进程重启也会继续处理”，确认之前就必须把消息交给可恢复的存储或处理流程。只放进进程内存便确认，随后进程退出，会让设备认为交付结束，而平台再也找不到这条告警。这里的业务接收确认还应与通信库自动发出的协议确认区分，不能默认两者发生在同一持久化边界。

设备没有收到确认时，可以保留原消息编号再次上报。平台保存成功、确认尚未到达设备时断线，则会发生重复交付。由此可见，能够恢复丢失的机制，往往也要求接收方能够处理重复。

MQTT 5.0 将 QoS 1 定义为至少一次交付、QoS 2 定义为恰好一次交付，但其交付协议讨论的是单个发送方与接收方之间的消息传递。业务数据库更新、应用再次提交和设备物理动作仍需各自的处理约定，不能从 QoS 2 推导出整条控制链路只执行一次。具体边界见 [MQTT 5.0 标准第 4.3 节](https://docs.oasis-open.org/mqtt/mqtt/v5.0/os/mqtt-v5.0-os.html)。

星云可以让应用负责恢复请求提交，让命令服务负责投递与结果查询，让设备负责本地执行与结果保留。恢复责任应对应各自持久保存的记录；某个环节只有“发送过”的日志，就不能据此宣称后续工作已经完成。

## 5.4.2 离线等待与有限重试

离线首先影响的是请求何时有机会被处理。即时查看摄像头画面，可以在离线时直接告知不可用；允许延后的任务，可以在有效期内等待；持续配置则按 5.3 的约定保存最新目标。是否排队，应在受理时确定，避免接口承诺了延后执行，后台却没有相应记录。

对于已经进入链路的请求，应根据失败原因决定是否重试。临时断线或通道繁忙可能随时间恢复；参数不符合模型、设备不支持能力或权限被拒绝，需要修正请求或改变条件。设备反馈“忙”时，还需明确它是否已经受理，不能把“暂时没有完成”一律当作可以重新创建操作。

**重试既要有停止条件，也要有恢复条件。** 星云可为单次命令保存尝试次数、下次尝试时间、最后原因和截止时间。到达次数上限或有效期后停止自动投递，保留最后确认的进展；若请求曾可能到达设备，停止重试后的执行结果仍可能是未确认。

连续失败时，重试间隔可以逐步增加，并加入随机延迟。例如按 1、2、4、8 秒增加等待上限，再在各自上限内随机选择等待时间。这只是策略示例，实际间隔应结合设备唤醒周期、业务期限和平台容量确定。大量设备同时恢复连接时，随机延迟与并发限制可以分散请求，避免重连立即带来一轮集中投递。关于退避和随机延迟的依据，可参见 [AWS 对重试控制的说明](https://docs.aws.amazon.com/wellarchitected/2024-06-27/framework/rel_mitigate_interaction_failure_limit_retries.html)。

应用、命令服务和接入通道还需要协调预算。如果每层都独立把一次调用扩成三次尝试，三层组合就可能产生 27 次底层调用。星云应明确业务重试的负责方，并把通道自身的重传纳入期限和观测范围。

投递前还应重新检查有效期、目标版本和当前授权。设备已经退役，或影子目标已经被新版本替代时，恢复连接不构成继续执行旧工作的理由。持续目标可以在下一次唤醒或条件变化后启动新一轮协调，但每轮仍需有限尝试，不能让同一个拒绝结果触发无限循环。

## 5.4.3 去重与幂等的作用范围

去重是根据标识和处理记录识别重复工作；幂等是同一操作重复处理时，在约定的业务范围内不产生额外效果。去重可以用来实现幂等，但“消息有编号”与“重复处理无额外效果”之间，还隔着记录保存、并发控制和结果返回等规则。

把亮度设为 30，在没有其他更新插入时，重复执行可以保持同一亮度；“亮度增加 10”则会累加。即使固定赋值本身没有额外效果，执行时附带的计费、通知或动作次数统计仍可能重复。因此，**幂等必须说明保护哪个操作及其副作用，不能只看最后一个属性值。**

同一请求在不同环节可能使用不同标识。表 5-5 将每个环节的重复问题分开，避免把入口去重当作整条链路的保证。

表 5-5：各处理边界的重复识别与处理约定。

| 处理边界 | 重复识别依据 | 再次到达时的处理 |
| --- | --- | --- |
| 应用提交命令 | 租户、调用方与请求标识 | 校验参数一致，返回原命令编号 |
| 平台投递设备 | 设备身份与命令编号 | 查执行记录，返回已有进展或结果 |
| 设备上报进入平台 | 设备身份、消息编号及其唯一范围 | 复用接收记录，继续尚未完成的处理 |
| 事件触发业务处理 | 消费方、事件编号与处理用途 | 跳过已完成效果，恢复未完成工作 |

同一逻辑消息重传时保留 `message_id`，同一次控制始终保留 `command_id`；发送尝试可另记次数或尝试编号。设备重新生成一条进度反馈时可以使用新消息编号，但仍引用原命令。业务去重不能依赖“所有相关消息都有同一个消息编号”。

使用请求标识时，需要把目标设备、能力和参数与原记录核对。相同标识携带不同内容，应返回冲突；用户主动发起第二次“闪灯三次”，则需要新的请求标识。否则，平台可能把用户确实需要的第二次操作当作网络重传。

处理记录还必须约定保留期限。若命令允许一天内重试，设备却在一分钟后清除执行记录，迟到请求仍会被当作新工作。应让保留窗口覆盖允许的重试与延迟范围；窗口之外的旧请求可以借助有效期或持久保存的版本基线拒绝。没有可信的过期判断，也没有原处理记录时，就不能继续承诺识别任意迟到的重复。

## 5.4.4 中途故障与执行结果恢复

检查编号后再执行业务，并不自动解决并发和崩溃。两个处理线程可能同时发现“尚未处理”，随后各做一次。平台应利用唯一约束、条件写入或同等能力，使同一处理键只能建立一份有效的处理记录，而不能依靠先查后写的时间间隔。

对于同一数据库内的操作，可以在一个事务中写入去重记录和业务变更。例如保存事件与登记待处理工作同时提交，重启后便能继续扫描未完成项。若事件记录已经存在，但后续告警通知尚未完成，重复到达时应恢复未完成步骤，不能因为“见过这个编号”就把整条链路跳过。

跨边界的效果需要单独处理。平台保存“已通知”和外部通知服务实际接收，并不天然属于一个事务；设备保存“已执行”和电机真正转动，也不天然属于一个事务。

以一次投料操作为例，先记完成再驱动电机，断电可能留下“记录完成、实际未投料”；先投料再记完成，断电可能留下“实际投料、记录缺失”。**持久化去重记录能够保留证据，却不能自动把物理动作和记录写入变成原子操作。**

设备可以先持久保存受理记录，让重复请求查询已有进展，再执行并保存结果。但重启后发现“执行中”，仍需根据设备能力恢复：若执行控制器支持按操作编号查询结果，就据此补齐；若有可靠的累计量或传感反馈，可以按业务约定核对；若只有一份未完成记录，就仍然可能无法判断动作是否发生。

在这种情况下，自动再做一次与自动认定成功都缺少依据。对于不能接受重复效果的动作，应暂停自动执行并向应用暴露未确认结果，必要时交由现场核对。对于允许重复应用的设置，可以在检查当前版本和有效期后重新协调。

结果查询也有边界。当前料仓重量、当前亮度或“设备现在在线”并不必然证明某条命令的历史结果；只有与原请求可靠关联的执行记录，或满足业务约定的独立证据，才能补充该命令的结论。

## 5.4.5 乱序消息与状态更新

去重回答“是不是同一件事”，顺序判断回答“不同事情之间谁先谁后”。消息编号互不相同，仍可能因缓存、重传或并发处理而颠倒到达。

例如设备在同一启动周期内先报告序号 41、亮度 70，再报告序号 42、亮度 30。平台先收到 42，随后收到 41 时，应保留 41 的历史观测，但不能用它覆盖已经更新为 30 的当前亮度。判断与写入应作为一个条件更新完成，否则两个线程分别判断后，较旧数据仍可能最后写入。

**顺序比较必须限定在可比较的来源、代次与数据范围内。** 序号重启归零时，需要结合启动代次；随机启动标识可以区分两个周期，却不能单凭字符串大小判断哪个周期更晚。平台应通过受信的会话建立或恢复流程确定当前代次，再识别旧周期数据。设备时钟不可靠时，也不能只按 `occurred_at` 排序；`received_at` 则只能表达平台收到消息的先后。

局部属性上报还需缩小比较范围。如果序号 41 只包含温度，序号 42 只包含电量，收到 42 并不表示已经掌握更新的温度。可以按属性维护观测版本；若业务要求整组数据一致，则应使用完整快照或能够补齐缺口的更新协议，不能直接丢弃所有小于设备最大序号的局部报告。

事件与当前状态使用不同规则。迟到的“开门”事件仍是一次历史事实，应按事件标识保存；是否触发即时通知，要结合发生时间的可信度和业务时效决定。不能因为后来已经收到“关门”，就把先前的开门事件当作无效数据。业务要求完整顺序时，可以有限等待并补取缺失记录；无法补齐时，应暴露缺口，不能无限等待。

下行控制也存在相同问题。旧的“设为 70”在新的“设为 30”之后到达，两个操作各自幂等，最终结果仍会错误。对允许新目标替代旧目标的设置，可沿用目标版本并由设备拒绝已经落后的版本。必须逐次执行的动作则需约定执行顺序与缺口处理，不能套用“只保留最大版本”而跳过中间动作。

平台串行发送只能限制自己发出的顺序。一次命令超时后仍可能留在远端缓存中，随后再发新命令，仍需要设备侧期限、版本或执行序列支持，才能控制旧请求的迟到效果。

## 5.4.6 故障交错下的闭环判断

异常规则需要放回同一条链路核对。以 `cmd_301` 设置亮度为 70 为例，设备完成执行但反馈丢失；随后用户提交 `cmd_302` 设置为 30，并获得完成确认。此时平台若仅因为 `cmd_301` 超时就重发，会把已经确认的新状态改回旧值。

对于本例这种允许新值替代旧值的设置，平台应停止旧目标的自动投递，设备依据已获知的版本阻止迟到旧目标生效。若之后找到了 `cmd_301` 的执行结果，可以补记它曾经完成；当前亮度仍由最新有效观测决定，不能因旧命令补记成功而回写成 70。

表 5-6 给出进一步核对规则的故障位置。它们是机制推演及预期结果，不代表已经运行过设备实验。

表 5-6：故障交错、恢复依据与预期结果。

| 故障位置 | 恢复依据 | 预期结果 |
| --- | --- | --- |
| 平台已保存命令，受理响应丢失 | 应用重用请求标识 | 返回原命令，不新增操作 |
| 命令已保存，发送进程重启 | 持久化待发送记录 | 检查有效期后恢复投递 |
| 设备已保存结果，完成反馈丢失 | 命令编号与设备执行记录 | 查询或重发返回原结果，不重复动作 |
| 设备动作后断电，结果尚未保存 | 可恢复执行记录及现场证据 | 无可靠证据时保持未确认 |
| 事件已保存，后续处理进程退出 | 各处理方的完成记录 | 恢复未完成工作，不跳过整个事件 |
| 新观测先到，旧观测后到 | 同一属性的可比较版本 | 当前状态不回退，历史仍可保留 |
| 旧目标迟到，设备已采用新目标 | 设备保存的目标版本基线 | 拒绝旧目标，分别保留两次请求的证据 |

实际验证时，应同时核对命令记录、设备动作次数、当前状态、历史事件和下游处理次数。只检查最终亮度，会漏掉中间重复闪灯；只检查消息数量，也不能证明业务效果没有重复。去重窗口届满、设备重启丢失记录，以及多个线程同时处理同一编号，都应作为改变保证条件的故障场景。

**闭环的判断依据是能够恢复和关联的证据。** 已确认的结果可以返回，尚未确认的部分需要明确保留；重试、去重和版本检查各自保护特定边界，共同决定一次交互在故障之后还能得到什么结论。

本章至此建立了单次交互的处理规则。设备投入使用数年以后，同样的规则还要服务于配置变更、升级任务和退役等长期过程；这些管理流程需要在下一章进一步组织。
