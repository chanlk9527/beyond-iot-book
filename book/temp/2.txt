# 1.1 IoT 的边界：我们究竟在讨论什么

[返回第 1 章：IoT 世界地图](../01-iot-world.md)

一盏可以用手机控制的灯、一台上报位置的物流终端、一套楼宇里的空调控制系统，都可以被称为 IoT。它们使用的硬件、网络和软件各不相同，却有一个共同问题：怎样让数字系统持续观察现实中的对象，并在需要时对其施加作用。

本书就从这种现实对象与数字系统之间的关系出发，理解 IoT 为什么需要设备、连接、平台和应用，以及它们分别承担什么责任。

## 1.1.1 一盏灯怎样变成系统的一部分

普通的灯由墙壁开关控制，用户按下开关，电路接通，灯亮起来。这个过程不需要账号，也不需要后台知道灯的状态。

换成一盏支持远程控制的智能灯，用户在手机 App 上点击“开灯”，命令经过网络到达设备，设备执行动作，再上报状态。用户还可以设置定时任务，让灯和传感器联动，或在离家以后查看它是否关闭。

灯的照明功能没有改变，它与其他对象的关系却增加了。系统需要识别具体是哪一盏灯、允许谁控制它、怎样理解它上报的数据，以及一次控制有没有产生预期结果。设备进入 IoT 系统以后，这些关系也成为产品需要维护的内容。

一盏仅靠内置人体传感器自动亮灭的灯，可以作为独立的智能硬件工作；当它把观察结果提供给其他设备或软件，或接受外部控制时，就开始参与更大范围的协作。参与协作并不要求每台设备都同时具备感知和执行能力：只上报读数的温度传感器，同样可以是 IoT 系统的一部分。

## 1.1.2 一个 IoT 系统，至少要把什么连起来

分析一个 IoT 系统，可以先找出几类要素：现实中的对象、负责感知或执行的设备、传递信息的连接、处理信息的软件，以及使用这些能力的人或业务。

现实对象可能是车辆、冷库、水泵或生产线。设备把它们的变化转换为数据，也可能把控制要求转换为动作；连接负责传递信息；软件识别设备、解释数据，并把这些信息用于监测、管理或控制。

这些工作形成两个常见方向：

- **观察：现实对象 → 设备 → 连接 → 软件 → 人或业务。** 例如，冷库传感器上报温度，系统记录温度变化并产生超限告警。
- **控制：人或业务 → 软件 → 连接 → 设备 → 现实对象。** 例如，管理员调整目标温度，控制器据此调节制冷设备。

这两个方向可以形成闭环，也可以只实现其中一个。冷库只做温度监测、由工作人员现场处理告警，仍然构成有用的 IoT 服务。持续关系也不意味着持续联网：电池传感器可以按计划唤醒、采样和上报，其余时间休眠。

## 1.1.3 联网，不等于 IoT；智能，也不等于 IoT

“互联网”“联网设备”和“智能硬件”经常与 IoT 一起出现。区分它们的用途，是帮助我们判断系统承担了哪些工作，而不是给产品划分互斥的类别。

### 互联网关注信息怎样交换

互联网为信息交换提供基础。电脑访问网站、手机观看视频、服务器交换数据，都可以使用这些基础能力。IoT 系统还需要解释信息怎样对应现实中的对象和动作。

例如，远程锁门时，接口返回成功，可能只表示请求已被接受；设备收到命令、执行上锁、检测到锁舌到位，是后续不同的事实。普通软件系统也会遇到异步处理、失败和状态不一致，IoT 的额外难点在于：软件记录之外，还有一个无法仅凭请求响应确认的物理过程。

### 联网设备只说明它能通信

联网设备能够通过网络交换数据，但这个称呼没有说明谁在管理设备、数据用于什么，以及系统怎样处理设备变化。理解一个 IoT 系统，需要沿着连接继续追问：消息来自哪个对象，谁会使用它，出了问题由谁处理。

这里的网络可以是本地网络，也可以连接到互联网。能否直接访问云服务，不是判断设备能否参与 IoT 系统的前提。

### 智能硬件关注产品本身

智能硬件通常指具有计算、感知或自动控制能力的产品，它可以完全独立工作。相反，一个本地功能很简单的插座，也可以通过远程管理参与 IoT 系统。

因此，与其判断一件设备“够不够智能”，不如说明它观察什么、和谁交换信息、可以执行什么动作。这些具体能力，才决定软件需要怎样与它协作。

## 1.1.4 IoT 也不一定意味着“设备直接上云”

IoT 系统可以在本地网络内完成采集、判断和控制。例如，家庭传感器把信息发送给网关，网关根据本地规则控制灯光；只要规则、必要数据和控制路径都在本地，互联网中断就不必导致这条自动化失效。依赖云端判断的其他功能则可能受影响。

现场系统也可以只向上层平台上传一部分数据，把对时延和连续运行有要求的控制保留在现场。是否使用云、哪些处理放在网关、断网后保留哪些功能，需要根据具体目标决定。

云是部署选择之一。设备、本地网关、云平台和应用可以共同参与一个系统，没有哪一个位置天然承担所有责任。

## 1.1.5 同样是 IoT，不同场景关心的事情并不一样

家庭场景通常围绕人和空间组织：灯装在哪个房间，谁可以控制门锁，访客权限何时失效，回家时哪些设备应该联动。系统除了连接设备，还要组织家庭成员、房间、场景和隐私边界。

在工厂、能源或大型楼宇中，设备还会进入资产和运行流程：哪台泵需要维修，哪次操作影响生产，告警由谁接收，网络中断时现场怎样继续运行。家庭产品同样需要可靠和安全，行业系统也同样需要易用；两者的区别在于具体的业务目标、后果和责任安排。

表 1-1 IoT 与相关概念的关注重点。

| 说法 | 主要关注什么 |
| --- | --- |
| 互联网 | 信息怎样通过网络交换 |
| 联网设备 | 设备是否能够通过网络交换数据 |
| 智能硬件 | 产品具有怎样的计算、感知或自动控制能力 |
| IoT | 现实对象、设备和软件怎样持续交换信息并参与管理或协作 |
| 智能家居 | 设备能力怎样服务家庭、成员、房间和生活场景 |
| 工业互联网 | 连接与数字技术怎样服务工业运行及其业务过程 |

这张表只比较本章需要辨认的关注点，不为这些领域给出完整定义。一把智能门锁可以同时属于其中多个类别；分析它时，仍应回到具体功能和责任。

## 1.1.6 本书所说的 IoT，边界在哪里

本书重点讨论通过设备、连接和软件，把现实对象纳入持续监测、管理或协作的系统。这是一条方便分析平台问题的工作边界，不是判定所有产品是否“算 IoT”的资格清单。

例如，物流终端上传坐标以后，系统还需要知道终端对应哪辆车、坐标何时产生，以及运营人员怎样据此判断车辆位置。路线告警和调度功能可以继续建立在这些信息上。只保存读数供以后分析也可以有价值，不必为了构成闭环而增加远程控制。

后文关心的是这些关系如何长期保持有效：设备怎样被识别，数据怎样被解释，用户怎样获得权限，以及设备断网、升级或转移以后，原有记录还能否支持正确判断。硬件电路、无线通信细节和具体行业算法，仅在它们影响这些设计判断时展开。

## 1.1.7 设备、连接、平台和应用分别做什么

为了定位问题，可以把系统中的工作分为设备、连接、平台和应用四类责任。

### 设备：观察和作用于现实世界

传感器把温度、亮度、位置等变化转换成数据；执行器把控制要求转换成开关、移动或调节等动作。设备报告的是它能够测量或判断的结果，测量范围、精度和故障也会限制软件能够知道什么。

### 连接：让信息能够到达另一个地方

Wi-Fi、蓝牙、蜂窝网络或以太网等技术提供通信路径。消息送达并不自动解释业务含义：收到 `4.2`，软件仍需要知道它表示温度还是电压、使用什么单位，以及对应哪次观察。

### 平台：组织大量设备和共同能力

多种产品会反复需要设备身份、接入、状态、控制、升级和权限等能力。平台把适合共享的部分组织起来，让产品团队复用。是否值得建设独立平台，取决于共享需求和维护成本，也取决于产品差异能否被合理保留，并非只由设备数量决定。

### 应用：把能力变成具体用途

应用面向具体的人和业务目标，可以是家庭控制 App，也可以是楼宇管理或工厂维护系统。同一条温度数据，在不同应用中可能用于实时显示、能耗分析或维修判断。

表 1-2 设备、连接、平台和应用的分工。

| 部分 | 主要解决什么问题 |
| --- | --- |
| 设备 | 怎样观察现实，以及怎样产生实际动作 |
| 连接 | 信息怎样在参与方之间传递 |
| 平台 | 设备和可复用的共同能力怎样被组织与管理 |
| 应用 | 这些能力怎样服务具体用户和业务目标 |

这四类责任不等于四个独立部署的系统。家庭网关可以同时转发消息和执行规则，手机可以同时提供界面和参与配网，一个后台也可以同时包含平台能力与产品业务。

遇到问题时，先判断缺失的是设备能力、通信条件、平台管理还是应用规则，再决定技术、部署和供应商。下一节会沿着这些责任走进产业链，看看谁提供部件、谁组织产品，以及设备售出以后由谁继续服务。
